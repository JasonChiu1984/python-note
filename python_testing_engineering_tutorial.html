從「溫度越界要告警」到可驗收的品質迴路

假設一個工廠閘道讀取本機 UTF-8 JSON：只有狀態良好且有限的讀值，達到 30 ℃（含）才輸出告警事件。資料品質不良、NaN 或低於閾值不得發布；格式錯誤走 stderr 並回傳退出碼 2。本例只用合成資料，不接觸現場設備，不能代替正式控制系統的驗收。

一張圖看依賴邊界

規則 exceeds() 不讀時鐘或檔案。process() 明確接收 publish；正式入口以 JSON 行輸出，本機整合使用 list.append，契約檢查使用 Mock。把外部副作用集中到邊界，可縮小失敗發生的範圍。

品質迴路：先讓缺陷可重現

新需求或事故檢討會回到第一步。先跑只含「等於門檻」的回歸例，錯誤版得到 False、正確版得到 True；再跑包含大量一般案例的完整 suite，防止改對一個條件卻破壞其他條件。

比較表｜測試層不是配額

  • 單元｜規則

    直接呼叫 exceeds()：29.99 不報、30.00 報、30.01 報；另驗 stale、NaN 不報。它無法驗證真實 JSON 編解碼。

  • 整合｜檔案＋解碼

    用暫存目錄寫一個實際 UTF-8 JSON，把「冰水」經過檔案、解碼與規則傳入真實清單。它不測服務啟動或設備。

  • 契約｜發布介面

    告警時 assert_called_once_with() 驗呼叫次數及事件鍵值；stale 時 assert_not_called() 驗沒有副作用。這只驗本地介面，不證明外部接收方相容。

  • 端到端｜CLI

    以獨立直譯器執行 CLI，核對 stdout JSON、stderr 和退出碼。它覆蓋範例 CLI 的可見契約，不是全站或全廠端到端。

選擇能以最低成本偵測該風險的層，並保留少數真實邊界測試。不要把 70/20/10 或測試金字塔當成固定比例。若有外部事件消費端，應另驗版本、樣本資料、可接受的向後相容變更與失敗回傳。

可重跑範例及常用 API

下載單檔標準庫實驗（Python 3.10+，不用安裝外部套件）。同一檔亦可用作 CLI；執行下列第一行會跑六個測試方法，其中規則方法有五個命名案例。

python python_testing_quality_loop_lab.py --test
python -m unittest -v python_testing_quality_loop_lab.QualityLoopTests.test_rule_boundaries
python -m unittest -v python_testing_quality_loop_lab.QualityLoopTests.test_publisher_contract
  • unittest.TestCase.subTest()

    以 name 標記迴圈案例。失敗時會顯示哪個邊界壞掉，後續案例仍能執行。

  • Mock.assert_called_once_with()

    驗公開事件與呼叫次數，不要對私有輔助函式的順序建立脆弱依賴。需要限制可用方法時可用 create_autospec()；它不會替你驗證遠端 schema。

  • TemporaryDirectory()

    每次測試新建目錄，在 context 離開時清除。不依賴上一輪留下的檔案。

  • subprocess.run()

    用 sys.executable、參數陣列及有限的 timeout，收集程序退出碼和輸出；此範例無 shell、無網路。

  • pytest.mark.parametrize()

    已採用 pytest 時，把相同案例表變成可獨立列出與選取的測試。用 tmp_path 隔離檔案，fixture 負責準備及清理，而不是隱藏多層依賴。

  • pytest.raises()

    驗例外類型與必要訊息，例如 with pytest.raises(ValueError, match="範圍"):。不要用 Exception 掩蓋非預期錯誤。

展開 pytest 等價參數化（選用；核心實驗不需要 pytest） 
import pytest
from python_testing_quality_loop_lab import Reading, exceeds

@pytest.mark.parametrize("value,quality,expected", [
    pytest.param(29.99, "good", False, id="below"),
    pytest.param(30.0, "good", True, id="equal"),
    pytest.param(30.01, "good", True, id="above"),
    pytest.param(99.0, "stale", False, id="stale"),
])
def test_alarm_boundary(value, quality, expected):
    assert exceeds(Reading("T10", value, quality), 30.0) is expected

將此段放在同目錄的 test_alarm.py，於已安裝 pytest 的隔離環境執行 python -m pytest -q test_alarm.py。故意以 > 代替 >= 時，equal 應失敗；修復後將這個案例保留為回歸測試。

CI 驗收與不穩定測試

  1. 短路與分層：PR 先跑語法、單元與核心離線契約；有版本與依賴鎖定才跑隔離整合與 smoke。發布前再對目標環境、產物及可回退版本驗證。任何必過步驟退出碼非零應讓閘門失敗。
  2. 證據最小組合：紀錄 commit SHA、直譯器和 OS、命令、退出碼、案例數、報告及可重跑 fixture。pytest 可用 python -m pytest --junitxml=artifacts/test-results.xml 供 CI 收集；這是證據格式，不是品質證書。機密、完整請求與現場憑證不要進日誌。
  3. coverage ≠ 正確：> 與 >= 都可能讓同一行覆蓋率達標，只有等於門檻的斷言能區分兩者。以 branch coverage 找盲區，再看斷言和風險；mutation 實驗可檢驗測試是否能拒絕有意修改。
  4. Flaky 排查：先保存失敗訊息與重跑環境；注入時鐘或明確固定種子、每案例使用獨立資料，不用 sleep() 假定跨程序時序。用可觀察條件與有限等待。若需暫時隔離，記錄 owner、原因、失敗比例及復原期限；多次重試轉綠不能證明修復。

驗收重點不只是「全綠」。先證明錯誤實作會被明確的案例拒絕，再證明正確實作穩定通過。

官方參照：unittest、unittest.mock、pytest 參數化、pytest JUnit XML。

Strategy

先決定風險，再決定測試形狀

資深工程師不追求測試數量，而是讓高風險行為有快速、穩定、可診斷的回饋。

Fixtures

測試資料要可讀、可重跑、可定位

穩定測試從可控資料、時間、檔案與外部依賴開始。

Unit Tests

Unit test 鎖住業務規則與錯誤路徑

好的 unit test 應該快、窄、對題，並且能指出是哪個規則壞掉。

Integration

整合測試驗證邊界，不取代 unit test

資料庫、檔案、API、message queue 都是邊界；測試要證明邊界契約可用。

Quality

測試品質要能被量測與改進

coverage 只是一個訊號，還要看 assertion、mutation thinking、flaky triage 與缺口紀錄。

CI Gate

品質閘門要快速、清楚、可重現

CI 應把 compile、unit、integration、smoke 與 release evidence 串成可追蹤的交付流程。
