Python 加密與程式碼保護深度研究

真正不能交付的邏輯與金鑰留在服務端。必須交付的程式則優先保護更新真偽、資料機密性並管理授權；封裝不能保證客戶端看不到可執行內容。

01｜先分清楚保護目標

原始碼與商業邏輯
以原始碼存取權限、未公開倉庫及服務端運算為主要邊界；交給客戶執行的程式不能視為完全保密。
授權與離線政策
服務端每次檢查帳號／租戶權限。離線授權可用獨立簽章金鑰發布限期授權聲明，檢查產品、功能、到期日；在使用者掌控的裝置上，不等於不可繞過的強制邊界。時鐘回撥與撤銷延遲須納入設計。
靜態檔案機密性
儲存時的機密資料可用認證加密（AEAD，例如 AES-GCM），保存 I/O 格式版本、nonce、密文與驗證標籤；同一把金鑰不可重用 nonce，AAD 可綁定租戶或資料用途。部署時由 KMS 或受控服務授權取用，不把共用解密金鑰硬編在安裝檔。應用有權解密時，明文仍可能出現在該信任域。
發布完整性與來源
以私鑰簽署精確 manifest 位元組，再以 manifest 中的 SHA-256 綁定成品。SHA-256 單獨不驗證發布人；簽章也不提供保密。受信任公鑰必須來自不同於不受信任下載檔的信任來源。

02｜架構圖：分開建置、簽署與發布

部署時先把公鑰或信任根隨可信安裝管道發放；不能使用和檔案一起由同一不可信位置提供、且未經驗證的新公鑰。真正機密的模型、規則與明文資料留在獨立服務和權限邊界，離線工控要另規劃故障行為，不能讓授權查詢導致基本控制或安全功能停擺。

03｜流程圖：先驗證再解析與啟用

驗章時使用收到的原始 manifest 位元組，不先把 JSON 格式化重存；同一份資料必須先驗章再解析。正式版另限制結構與大小，指定發布通道、平台、目標檔、簽署金鑰 ID、到期與可接受的最小版本。安裝程式應使用同一份已驗證位元組或妥善保護的暫存成品，不要驗完後再打開可被替換的路徑。

回退與金鑰輪替：保存可信的版本下限與支援通道；不能僅因舊包有簽章就回退。正式輪替先用既有信任根或獨立受控管道分發新版信任集，再妥善撤銷老金鑰。允許的緊急回退應有獨立授權、期限、理由和稽核紀錄；客戶端只信任可管理的預先信任資料。

04｜比較圖表：各方法該用在哪裡

.py / .pyc

作用：原始碼或 CPython bytecode；利於部署與載入。

邊界：不是加密；bytecode 與直譯器版本相關，具可分析性。

PyInstaller

作用：打包程式、直譯器與相依項目以簡化交付。

邊界：不是保密工具；單檔執行也通常會解出內容到暫存位置。需測目標 OS、權限與實際執行模式。

Nuitka / Cython

作用：編譯程式或擴充模組，改變交付方式，可能提高分析成本。

邊界：不是密碼學保證；需要管理平台、Python ABI、建置及測試矩陣，不保證任意場景更快。

服務端 API

作用：不把受保護的實作交給用戶端。

邊界：增加可用性、離線、身分授權與維運要求；客戶端仍只送必要資料。

AES-GCM

作用：保護獲准解密之前的靜態資料，並驗證資料。

邊界：不能保證執行中的明文不可見。不要自製演算法，也不要在現有金鑰下重用 nonce。

簽章＋雜湊

作用：驗證可信發布者與實際下載位元組。

邊界：不保密。版本、目標與可接受信任根需額外驗證，不只檢查簽章成功。

05｜離線實作：簽署並驗證合成發行檔

需要 Python 3.10+ 與安裝好的 OpenSSL 3.x；不連網，不執行發行成品。私鑰只在暫存資料夾生成，執行結束即清理。臨時用戶端公鑰是用來示範預先配置的信任根，不是從更新區下載的資料。

"""Offline synthetic release verification; Python 3.10+ and OpenSSL 3.x."""
from __future__ import annotations
import argparse
import hashlib
import json
from pathlib import Path
import subprocess
from tempfile import TemporaryDirectory

def ssl(*args: str, verify_only: bool = False) -> bytes:
    result = subprocess.run(["openssl", *args], check=False, capture_output=True, timeout=10)
    if result.returncode:
        if verify_only:
            raise ValueError("驗章失敗：拒絕發布資料")
        raise RuntimeError(result.stderr.decode(errors="replace"))
    return result.stdout

def verify(root: Path, pinned_key: Path, floor: int, expected_product: str) -> bytes:
    # Verify the exact bytes held in memory; do not parse until verified.
    manifest = (root / "manifest.json").read_bytes()
    signature = (root / "manifest.sig").read_bytes()
    with TemporaryDirectory() as tmp:
        data, sig = (Path(tmp) / name for name in ("manifest", "signature"))
        data.write_bytes(manifest)
        sig.write_bytes(signature)
        ssl("pkeyutl", "-verify", "-pubin", "-inkey", str(pinned_key), "-rawin",
            "-in", str(data), "-sigfile", str(sig), verify_only=True)
    meta = json.loads(manifest)
    if (meta["product"] != expected_product or meta["file"] != "example.bin"
            or type(meta["version"]) is not int or meta["version"] < floor):
        raise ValueError("發行目標或版本不符：拒絕發布資料")
    payload = (root / "example.bin").read_bytes()
    if hashlib.sha256(payload).hexdigest() != meta["sha256"]:
        raise ValueError("檔案雜湊不符：拒絕發布資料")
    return payload  # In production install precisely these verified bytes, not a reopened file.

def demo() -> None:
    with TemporaryDirectory() as tmp:
        root = Path(tmp)
        publisher, client, release = (root / name for name in ("publisher", "client", "release"))
        for folder in (publisher, client, release):
            folder.mkdir()
        private, pinned = publisher / "key.pem", client / "trusted.pem"
        ssl("genpkey", "-algorithm", "ED25519", "-out", str(private))
        ssl("pkey", "-in", str(private), "-pubout", "-out", str(pinned))
        payload = release / "example.bin"
        payload.write_bytes(b"synthetic release example\n")
        manifest, sig = release / "manifest.json", release / "manifest.sig"
        meta = {"product": "tutorial", "file": "example.bin", "version": 2,
                "sha256": hashlib.sha256(payload.read_bytes()).hexdigest()}
        manifest.write_text(json.dumps(meta, sort_keys=True), encoding="utf-8")
        ssl("pkeyutl", "-sign", "-inkey", str(private), "-rawin", "-in", str(manifest), "-out", str(sig))
        assert verify(release, pinned, 2, "tutorial") == payload.read_bytes()
        print("PASS: 正常發行物通過驗章、版本與雜湊")

        def rejects(floor: int, expected: str) -> None:
            try:
                verify(release, pinned, floor, "tutorial")
            except ValueError as exc:
                if expected not in str(exc):
                    raise
                print("PASS:", str(exc))
                return
            raise AssertionError("錯誤檔案被接受")

        rejects(3, "版本不符")
        payload.write_bytes(b"edited release example\n")
        rejects(2, "雜湊不符")
        payload.write_bytes(b"synthetic release example\n")
        manifest.write_text(json.dumps({**meta, "version": 3}), encoding="utf-8")
        rejects(2, "驗章失敗")

if __name__ == "__main__":
    parser = argparse.ArgumentParser(description=__doc__)
    parser.parse_args()
    demo()

06｜上線驗收清單

  1. 盤點要保護的資料與攻擊者位置；用原始碼祕密掃描與最小權限，避免配置與憑證進入任何發布品。
  2. 分離部署金鑰、更新簽署金鑰及授權簽署用途；規劃離線信任根、簽署審核、版本下限與紀錄保存。
  3. 以乾淨目的平台試裝，對未信任金鑰、破損檔、過期資料、舊版、錯平台做拒絕測試。
  4. 在預備環境演練撤銷、輪替、更新中斷與安全回退；以實際部署結果驗收，而非只看封裝成功。

延伸學習：實作、現場案例與自我檢查

程式碼保護最實際的一步，往往不是混淆，而是確認現場安裝的就是你發行的版本。本節示範發行清單：逐檔 SHA-256、簽署清單、安裝前驗證，並偵測被修改、被刪除與多出來的檔案。

可實跑範例：發行清單簽署與逐檔驗證

build_manifest() 產生每個檔案的 SHA-256 並簽署整份清單；verify() 先驗清單簽章，再逐檔比對，最後找出清單外的檔案。為了只用標準函式庫，範例用 HMAC；正式發行應改用非對稱簽章，讓現場只持有公開金鑰。

下載範例 example.py

"""發行檔完整性清單：產生 SHA-256 清單、用 HMAC 簽署清單，安裝前逐檔驗證（標準函式庫）。

真實發行應使用非對稱簽章（例如 Ed25519 或 Sigstore），讓驗證端只持有公開金鑰；
本例為了只用標準函式庫改用 HMAC，示範的是「清單＋逐檔雜湊」的流程。
"""
import hashlib
import hmac
import json
import tempfile
from pathlib import Path

SIGNING_KEY = b"\x42" * 32


def sha256(path: Path) -> str:
    h = hashlib.sha256()
    with path.open("rb") as f:
        for chunk in iter(lambda: f.read(65536), b""):
            h.update(chunk)
    return h.hexdigest()


def build_manifest(root: Path) -> dict:
    files = {p.relative_to(root).as_posix(): sha256(p) for p in sorted(root.rglob("*")) if p.is_file()}
    body = json.dumps(files, sort_keys=True).encode()
    return {"files": files, "sig": hmac.new(SIGNING_KEY, body, hashlib.sha256).hexdigest()}


def verify(root: Path, manifest: dict) -> list[str]:
    body = json.dumps(manifest["files"], sort_keys=True).encode()
    if not hmac.compare_digest(hmac.new(SIGNING_KEY, body, hashlib.sha256).hexdigest(), manifest["sig"]):
        return ["清單簽章錯誤：清單本身被修改"]
    problems = []
    actual = {p.relative_to(root).as_posix() for p in root.rglob("*") if p.is_file()}
    for name, digest in manifest["files"].items():
        if name not in actual:
            problems.append(f"缺少檔案：{name}")
        elif sha256(root / name) != digest:
            problems.append(f"內容不符：{name}")
    problems += [f"多出未列管檔案：{n}" for n in sorted(actual - manifest["files"].keys())]
    return problems


if __name__ == "__main__":
    with tempfile.TemporaryDirectory() as tmp:
        root = Path(tmp) / "gateway-2.4.1"
        (root / "app").mkdir(parents=True)
        (root / "app" / "main.py").write_text("print('gateway')\n")
        (root / "app" / "points.json").write_text('{"SAT": {"addr": 0, "scale": 0.1}}\n')
        (root / "README.txt").write_text("v2.4.1\n")
        manifest = build_manifest(root)
        for name, digest in manifest["files"].items():
            print(f"{digest[:16]}…  {name}")
        print("原始發行檔：", verify(root, manifest) or "全部通過")
        (root / "app" / "points.json").write_text('{"SAT": {"addr": 0, "scale": 1.0}}\n')
        (root / "app" / "debug_shell.py").write_text("import os\n")
        print("被修改後：")
        for p in verify(root, manifest):
            print("  -", p)
        manifest["files"]["app/points.json"] = sha256(root / "app" / "points.json")
        print("攻擊者同步改清單：", verify(root, manifest))

工程現場案例：現場閘道器多了一個除錯腳本

某閘道器軟體以 zip 交付，現場人員為了除錯自行加了 debug_shell.py，並把點位倍率改成 1.0。半年後系統異常，沒有人記得改過什麼。若安裝與每次開機都執行清單驗證，這兩個變更會立即被列出：points.json 內容不符、多出未列管檔案。

攻擊者若連清單一起改，因為沒有簽署金鑰，清單簽章就會失敗。這也說明了金鑰的分工：簽署金鑰只在建置主機，現場只需要驗證能力；用 HMAC 時兩者是同一把，因此正式環境應改用 Ed25519 等非對稱演算法。

  1. 在 CI 建置時產生清單並簽署，清單與發行檔一起交付。
  2. 安裝程式與服務啟動時都執行驗證，失敗就拒絕啟動並告警。
  3. 設定檔若需要現場修改，與程式檔分開管理並另外簽署或納入變更管理。
  4. 保存每個版本的清單，事故調查時可比對現場與發行版本。

版本與法規更新（核對日期 2026-11-28）

  • Python 套件生態的發行簽署正轉向 Sigstore 與 PEP 740 數位證明（attestations）：PyPI 支援以 Trusted Publishing 上傳並附帶證明，使用者可驗證套件確實由指定的 CI 流程建置。內部發行可參考同樣的模式。另依 NIST IR 8547 定稿，RSA、ECDSA、EdDSA 簽章將於 2030 年後 deprecated，長期維護的簽章流程要預留換成 ML-DSA 等後量子演算法的彈性。 來源：PEP 740 來源：CSA：NIST IR 8547 定稿摘要

練習題與自我檢查

  1. verify() 為什麼要先驗清單簽章，再逐檔比對？

    看解答

    若清單本身不可信，逐檔比對沒有意義：攻擊者可以把清單裡的雜湊改成被竄改後檔案的雜湊。範例最後一行就是這個情境，簽章檢查讓它失敗。

  2. sha256() 為什麼分塊讀取，而不是 path.read_bytes()？

    看解答

    大型檔案（例如韌體映像或模型檔）一次讀進記憶體可能耗盡資源。分塊更新雜湊的結果與一次計算完全相同，記憶體用量固定。

  3. 若要允許現場修改 points.json，但其他檔案仍必須與發行版一致，要怎麼設計？

    看解答

    把可修改的設定檔從程式清單中移出，另建設定清單並由現場的設定發布流程簽署（參考加密深度研究頁的 HMAC 設定檔簽章範例）。程式清單驗證失敗拒絕啟動；設定驗證失敗則保留上一版有效設定。

  4. Python 原始碼經 PyInstaller 打包或編譯成 .pyc，就不需要完整性驗證了嗎？

    看解答

    仍需要。打包或編譯只增加閱讀難度，不能防止替換或修改；檔案被換掉時程式照樣執行。完整性驗證回答的是「這是不是我發行的檔案」，和保密是兩個不同目標。

  5. 在原始發行檔上只刪除 README.txt，其他檔案與清單都不動，verify() 會回報什麼？若攻擊者沒有簽署金鑰，能不能把 README.txt 從清單中一併刪掉來掩蓋？

    看解答

    實際執行結果是 ['缺少檔案：README.txt']。清單簽章仍正確，所以會走到逐檔比對，並在「存在嗎」這一步被抓到。

    從清單刪掉這一項會改變 files 的序列化結果，簽章隨之不符，verify() 只回報「清單簽章錯誤：清單本身被修改」。刪檔、改檔、加檔都逃不過，前提是簽署金鑰不在攻擊者手上。

  6. 若現場閘道器上也保存了 SIGNING_KEY（HMAC 的必然結果），有人改了 points.json、加入 debug_shell.py，再用同一把金鑰呼叫 build_manifest() 重簽清單，verify() 會回報什麼？這說明了什麼？

    看解答

    實際執行：verify() 回傳空清單 []，重簽後的清單列了 4 個檔案（含被改的 points.json 與新加的 debug_shell.py），全部「通過」。HMAC 的簽署與驗證用同一把金鑰，能驗證的一方就能偽造。

    這正是正式發行要改用 Ed25519 等非對稱簽章的原因：私鑰只在建置主機，現場只有公鑰，取得公鑰也無法產生有效簽章。公鑰本身要經獨立可信管道預先配置，不能和更新檔一起下載後直接信任（見本頁正文第 02 節）。
