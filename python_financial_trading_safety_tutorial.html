02 / PRE-TRADE CONTROLS

先確認單位與上限，再保留風險資源

檢核本機例子工程陷阱
價格／數量Decimal 從字串建立；價格為每單位，合成格線 0.01；數量是正整數。別以 Decimal(float) 消除二進位誤差。正式商品另查交易所／券商格線、交易單位、乘數及幣別；不要把股、張、口混用。
未保留現金可用現金 = 現金 − 所有未成交買單保留。新買單預留未成交量 ×（限價 + 合成單位費）。取消請求尚未確定不可釋放。此例不含結算、買賣交割期、保證金、匯率、賣空及券源。
曝險上限 400.00，採持倉成本 + 在途買單未成交名目額 + 新單名目額。這不是實盤曝險模型。行情跳空需用市值、集中度、相關性、槓桿或多幣風險重估；不能只拿現金當全部風險。
時間與新鮮度合成資料要求同 UTC 時基、年齡 0–2 秒；未附時區、過舊或未來事件拒絕。內部計時與 deadline 用 monotonic；跨主機事件留 UTC、來源及接收時間。同步時鐘與行情序號有缺口時先降級；不能以更新畫面的時間假裝行情新鮮。
手續費與滑價每成交單位合成費 0.02，實際回放價 39.50／39.80，買單封頂 40.00。紙上回放不模擬排隊位置、市場衝擊、部分流動性、稅費等。滑價應與明確基準價比較，而非用限價差直接估算報酬。

若規格以每筆或階梯費率計費，要按實際口徑、幣別與四捨五入規則採用 Decimal／整數子單位；不應假設所有市場都是兩位小數。本章沒有以合成門檻代表任何交易所現行規則。

03 / LIFECYCLE

ACK、成交與撤單是不同事件

小螢幕可左右捲動表格；鍵盤可用 Tab 進入後按方向鍵。

情境行為不能假設
Client Order ID 重送相同業務意圖回到同筆委託，不新增；相同 ID 卻改數量/限價，視為衝突。連線逾時不等於沒有接受；不可另建新 ID 自動送出。
執行 ID 重複相同 ID+內容去重；同 ID 異內容先停新單／告警、核對來源。不能用只看委託 ID 取代執行 ID，同委託能多次成交。
先成交再收到撤單結果有未成交量時才釋放；若已全成，帳務不能因撤單晚到而被覆蓋。市場實際更正、撤銷成交、亂序與多通路有各自規則；本模型不實作。
對帳不一致暫停新意圖；抓委託清單、成交明細、持倉與現金的同一一致點，保留原事件，查哪一層缺漏。現金與部位剛好相等，不代表 ACK 已解決；也不能直接清掉暫停旗標。

FIX 以 OrdStatus 表委託狀態、ExecType 表執行報告的目的。這是思考參考；本篇標籤是本地模型、自定命名，不是某券商或 FIX 實作。來源：FIX Trading Community：Order State Changes。

04 / SYNTHETIC LEDGER

撤單影響的是保留額，已成交不回滾

合成起始現金 1,000.00；掛買 5 單位、上限 40.00。先 2 單位以 39.50 成交、待撤中再 1 單位以 39.80 成交，最後取消剩餘 2 單位。圖表由同一 Python 腳本輸出產生。

兩筆成交費共 0.06，實際支出 2 × 39.50 + 1 × 39.80 + 0.06 = 118.86；結束時現金 881.14、部位 3、保留額 0。保留額是限制尚可使用的現金，不是費用或虧損。

"""Paper-only order lifecycle. Offline synthetic data; no broker integration."""
from dataclasses import dataclass
from decimal import Decimal
from datetime import UTC, datetime, timedelta
import argparse
import json
import unittest

D = Decimal
FEE_PER_UNIT = D("0.02")  # Synthetic; no fixed fee, taxes or rebates.
MAX_EXPOSURE = D("400.00")
CENT = D("0.01")
NOW = datetime(2026, 11, 25, 9, tzinfo=UTC)


def price(text):
    if not isinstance(text, str):
        raise ValueError("start from a decimal string")
    p = D(text)
    if not p.is_finite() or not D("0.01") <= p <= D("1000000"):
        raise ValueError("price out of lab range")
    if p != p.quantize(CENT):
        raise ValueError("price must match the synthetic 0.01 tick")
    return p


@dataclass
class Order:
    order_id: str
    qty: int
    limit: Decimal
    filled: int = 0
    state: str = "PENDING_ACK"


class PaperBook:
    def __init__(self):
        self.cash = D("1000.00")
        self.position = 0
        self.position_cost = D("0.00")
        self.orders = {}
        self.executions = {}
        self.blocked = False

    @staticmethod
    def active(order):
        return order.state not in {"FILLED", "CANCELED"}

    @property
    def reserved(self):
        return sum(((o.qty - o.filled) * (o.limit + FEE_PER_UNIT)
                    for o in self.orders.values() if self.active(o)), D("0.00"))

    @property
    def reserved_notional(self):
        return sum(((o.qty - o.filled) * o.limit
                    for o in self.orders.values() if self.active(o)), D("0.00"))

    def submit(self, order_id, qty, limit, observed_at, now):
        if not isinstance(order_id, str) or not order_id or type(qty) is not int or qty < 1:
            raise ValueError("expect order ID and a positive integer quantity")
        ceiling = price(limit)
        if order_id in self.orders:
            old = self.orders[order_id]
            if (old.qty, old.limit) != (qty, ceiling):
                raise ValueError("client order ID conflicts with previous intent")
            return old  # Same intent, not a new order.
        if self.blocked or any(o.state == "UNKNOWN_ACK" for o in self.orders.values()):
            raise ValueError("reconcile before accepting new orders")
        if observed_at.utcoffset() is None or now.utcoffset() is None:
            raise ValueError("timestamps require an offset")
        if not timedelta(0) <= now - observed_at <= timedelta(seconds=2):
            raise ValueError("stale or future market snapshot")
        if qty * (ceiling + FEE_PER_UNIT) > self.cash - self.reserved:
            raise ValueError("insufficient unreserved cash")
        if self.position_cost + self.reserved_notional + qty * ceiling > MAX_EXPOSURE:
            raise ValueError("cost-basis exposure cap exceeded")
        result = Order(order_id, qty, ceiling)
        self.orders[order_id] = result
        return result

    def unknown_ack(self, order_id):
        order = self.orders[order_id]
        if order.state != "PENDING_ACK":
            raise ValueError("only pending acknowledgments can time out")
        order.state = "UNKNOWN_ACK"  # Keep cash reserved.

    def confirm_open(self, order_id):
        # Only after a trusted reconciliation source says the order exists.
        order = self.orders[order_id]
        if order.state not in {"PENDING_ACK", "UNKNOWN_ACK"}:
            raise ValueError("cannot re-open an order")
        order.state = "OPEN"

    def request_cancel(self, order_id):
        order = self.orders[order_id]
        if order.state not in {"OPEN", "PARTIAL"}:
            raise ValueError("cannot request cancel in current state")
        order.state = "CANCEL_PENDING"

    def fill(self, execution_id, order_id, qty, execution_price):
        if type(qty) is not int or qty < 1:
            raise ValueError("invalid fill quantity")
        if not isinstance(execution_id, str) or not execution_id:
            raise ValueError("invalid execution ID")
        paid = price(execution_price)
        payload = (order_id, qty, paid)
        if execution_id in self.executions:
            if self.executions[execution_id] != payload:
                self.blocked = True
                raise ValueError("execution ID has contradictory payload")
            return False
        order = self.orders[order_id]
        if not self.active(order) or paid > order.limit or qty > order.qty - order.filled:
            self.blocked = True
            raise ValueError("fill contradicts current ledger; reconcile")
        order.filled += qty
        self.executions[execution_id] = payload
        self.cash -= qty * (paid + FEE_PER_UNIT)
        self.position_cost += qty * paid
        self.position += qty
        if order.filled == order.qty:
            order.state = "FILLED"
        elif order.state != "CANCEL_PENDING":
            order.state = "PARTIAL"
        return True

    def confirm_cancel(self, order_id):
        order = self.orders[order_id]
        if order.state == "FILLED":
            return  # Terminal state is not downgraded by a late response here.
        if order.state != "CANCEL_PENDING":
            raise ValueError("missing cancel request")
        order.state = "CANCELED"

    def reconcile(self, cash, position):
        if self.cash != cash or self.position != position:
            self.blocked = True
            return False
        # Matching total cash and position do not by themselves resolve
        # an UNKNOWN_ACK or clear an existing integrity hold.
        return True


def scenario():
    ledger = PaperBook()
    output = []
    order = ledger.submit("client-01", 5, "40.00", NOW, NOW)

    def snapshot(label):
        output.append({"step": label, "state": order.state, "filled": order.filled,
                       "cash": str(ledger.cash), "reserved": str(ledger.reserved),
                       "position": ledger.position})

    snapshot("收到委託")
    ledger.unknown_ack(order.order_id)
    snapshot("ACK 不明")
    ledger.confirm_open(order.order_id)
    ledger.fill("e-1", order.order_id, 2, "39.50")
    snapshot("部分成交 2")
    ledger.request_cancel(order.order_id)
    snapshot("撤單待確認")
    ledger.fill("e-2", order.order_id, 1, "39.80")
    snapshot("撤單途中再成 1")
    ledger.confirm_cancel(order.order_id)
    assert ledger.reconcile(D("881.14"), 3)
    snapshot("撤單完成／對帳")
    return output


class LabTests(unittest.TestCase):
    def test_dedup_client_and_execution(self):
        ledger = PaperBook()
        order = ledger.submit("o", 3, "20.00", NOW, NOW)
        self.assertIs(order, ledger.submit("o", 3, "20.00", NOW, NOW))
        with self.assertRaises(ValueError):
            ledger.submit("o", 4, "20.00", NOW, NOW)
        self.assertTrue(ledger.fill("e", "o", 1, "19.50"))
        self.assertFalse(ledger.fill("e", "o", 1, "19.50"))
        self.assertEqual(ledger.cash, D("980.48"))
        with self.assertRaises(ValueError):
            ledger.fill("e", "o", 1, "19.40")
        self.assertTrue(ledger.blocked)

    def test_unknown_ack_keeps_reserve_and_blocks_new_orders(self):
        ledger = PaperBook()
        order = ledger.submit("o", 3, "20.00", NOW, NOW)
        ledger.unknown_ack(order.order_id)
        self.assertEqual(ledger.reserved, D("60.06"))
        self.assertTrue(ledger.reconcile(D("1000.00"), 0))
        with self.assertRaisesRegex(ValueError, "reconcile"):
            ledger.submit("new", 1, "10.00", NOW, NOW)
        ledger.confirm_open("o")
        self.assertEqual(order.state, "OPEN")

    def test_cancel_race(self):
        rows = scenario()
        self.assertEqual(rows[-2]["state"], "CANCEL_PENDING")
        self.assertEqual(rows[-1]["filled"], 3)
        self.assertEqual(rows[-1]["cash"], "881.14")
        self.assertEqual(rows[-1]["reserved"], "0.00")

    def test_pretrade_checks(self):
        ledger = PaperBook()
        for order in [(41, "30.00", NOW, "cash"),
                      (11, "40.00", NOW, "exposure"),
                      (1, "40.00", NOW-timedelta(seconds=3), "stale"),
                      (1, "40.001", NOW, "tick"),
                      (1, "NaN", NOW, "range")]:
            qty, limit, timestamp, message = order
            with self.assertRaisesRegex(ValueError, message):
                ledger.submit("o", qty, limit, timestamp, NOW)
        self.assertEqual(ledger.orders, {})

    def test_invalid_fill_and_reconcile_freeze(self):
        ledger = PaperBook()
        ledger.submit("o", 1, "40.00", NOW, NOW)
        with self.assertRaises(ValueError):
            ledger.fill("e", "o", 2, "40.00")
        self.assertEqual((ledger.cash, ledger.position), (D("1000.00"), 0))
        self.assertFalse(ledger.reconcile(D("999.00"), 0))
        self.assertTrue(ledger.blocked)


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--self-test", action="store_true")
    args = parser.parse_args()
    if args.self_test:
        unittest.main(argv=["lab"], verbosity=2)
    else:
        print(json.dumps(scenario(), ensure_ascii=False, indent=2))


if __name__ == "__main__":
    main()

06A / PAPER INCIDENT PLAYBOOK

常見交易系統錯誤：症狀、處置與紙上驗收

先保留事實、再恢復作業。狀態未知時保留委託與曝險，先核對權威紀錄，不用本機畫面代替成交事實。本節只用合成事件研判與測試，不接券商、不下單，亦非投資建議。真實語意、識別碼作用範圍和市場規則須依實際系統與官方文件核對。

送單逾時，狀態未知

症狀
本機沒有收到 ACK，但 UI 想顯示「未成交」或允許重按。
可能原因
要求可能未送出，也可能已被接收、甚至成交，只是回覆遺失或延遲。HTTP 成功與交易接受是不同訊號。
安全處置
使用原委託識別碼保留風險額，標成「狀態未知」並暫停同一意圖；先以受信委託/成交查詢與實際回報核對。未證實原委託未受理前不另送新單，也不假定任意 API 有冪等保證。
紙上驗收
在合成情境丟棄 ACK 後注入已成交紀錄，確認不衍生第二筆委託、原保留額未提前釋放。

重複或亂序回報

症狀
同一筆成交出現兩次，累積量減少，或較舊回報蓋掉新狀態。
可能原因
重送、重接、快照與事件流交錯；不同時鐘、識別碼作用範圍或跨日重設被混為一談。
安全處置
依權威來源定義事件／成交 ID 範圍，重複不重複入帳；遇序號缺口暫停不完整視圖並補查。不要只按本機收到時間排序，也不要丟掉有明確語意的成交更正或沖銷。
紙上驗收
同一合成成交重放兩次、再倒置兩個回報；核對成交量、現金與曝險不被重複計入，更正則有可追蹤補償事件。

部分成交與取消交錯

症狀
送出取消後仍出現成交，或畫面顯示取消成功就把成交量改成零。
可能原因
Pending Cancel 只是取消請求尚未確認；交易所在完成取消前可能仍成交。
安全處置
保留已成交部位；在權威終態與相關成交都對帳後，只釋放剩餘未成交額。若整筆已成交，已無餘量可取消；矛盾回報先標記待查。
紙上驗收
用「先成交 4、送取消、再成交 2、最終取消餘量 4」的合成 10 單位事件，核對已成交 6，未成交餘額不再保留，且 6 的帳務不回滾。

撤改限額沒有保留

症狀
改價、增加數量或以取消重下代替改單後，兩筆委託可能同時占用限額。
可能原因
把「改單送出」當成已生效，忽略舊委託仍可成交、改單可能遭拒或帳務更新延遲。
安全處置
以可同時存在的曝險做保守預留；若現行介面不能證明改單原子性，不先釋放舊保留額，也不因畫面顯示成功就改寫已成交歷史。
紙上驗收
固定一筆待改價單，模擬舊單成交、改單被拒及取消回覆晚到；檢查各事件順序都不允許保留額出現負數或未預期釋放。

費用、幣別與捨入錯位

症狀
紙上成交已對，現金或損益卻差少量；將跳動單位用四捨五入默認改價。
可能原因
把二進位浮點當貨幣，或混淆手續費、稅、最低費用、幣別、每筆或彙總捨入；市場格線不是帳務精度。
安全處置
以 Decimal 從字串或最小貨幣整數表示金額，分開校驗交易價格格線、費率來源、幣種及帳務捨入時點。非法價先拒絕並提示，不能偷偷改成有效價。
紙上驗收
使用自訂測試費率與小數邊界，核對「逐筆捨入」與「彙總後捨入」的差，將成交、費用、稅額、淨額分項比對。

交易時段、停牌、跳動與整零股

症狀
價格看似合法卻被拒、零股委託套用整股條件、排程在假日送出。
可能原因
市場、商品、交易制度與委託種類套錯；誤把本機時間、一般日曆或單一價位格線當市場規則。
安全處置
依官方市場行事曆、公告、商品規格以及券商可用介面核對，保留規則版本及生效日期。辨別停牌、休市、盤中/盤後及整股/零股；規則或狀態缺失先停新風險操作。本章不提供實際下單限制。
紙上驗收
使用虛構格線和假日表，測邊界前後、休市與停牌、整零股設定分離；覆核拒絕事件不影響既有部位。

行情有值，卻不是新鮮資料

症狀
收盤後畫面仍有最後成交價，重連後快照時間反而更早。
可能原因
來源時間、接收時間、交易日與時區混淆；市場暫停、緩存、缺序或時鐘漂移使資料陳舊。
安全處置
分別保存來源和接收時間、時區及品質旗標。超過允許時效、時間倒退、序號不連續或來源不明時，標成 stale/unknown 並暫停依賴該行情的新操作。
紙上驗收
合成即時、過期、缺序、時鐘偏移及盤後樣本；確認只有符合指定資料契約的樣本可通過。

斷線重連與頻率限制

症狀
重新登入就當作可送單，或查詢錯誤後瞬間大量重試，讓狀態更不完整。
可能原因
只看傳輸連線、不看事件恢復；外部介面有速率或流量限制，歷史回補可能不全。
安全處置
重連先查未結委託、最近成交、部位與資金，依官方支援能力及退避規則補齊；查詢重試與委託送出分開，不能以通用 HTTP 重試機制重送有副作用的操作。
紙上驗收
模擬限流、斷線及快照發布期的回報交錯。確認沒有無限循環查詢，恢復條件不達成時保持受限狀態。

日終對帳仍有未解決差異

症狀
本機委託數對，但成交、現金、可用額或隔日開帳不一致。
可能原因
不同截點、時區、交割日、修正、費用或未結委託未按同一份權威資料比對。
安全處置
用相同帳戶、商品、幣別及報表截點，逐項對權威委託／成交／帳務報表。差異列例外並凍結相關新增風險操作，交由授權人處理；必要的風險降低動作依獨立預案。
紙上驗收
故意漏掉一筆費用或成交；確認例外清單保留原因及決策人，對帳前不默默調帳或歸零開隔日。

重啟後忘了未結委託

症狀
程式更新後，前一天的狀態未知、ID 去重集合或風控保留不見。
可能原因
狀態只存記憶體；寫檔／資料庫提交與接收事件之間有失敗窗口。
安全處置
持久化委託意圖、已處理事件識別、游標及風控狀態，以可重做的順序從本機快照和可信外部紀錄恢復。不能承諾網路上的天然「恰好一次」。
紙上驗收
把合成程序在儲存前後兩點模擬中止，重新重放並對帳；同一成交不重複，待處理未結狀態不消失。

資料洩漏與回測偷看未來

症狀
除錯日誌看到券商密鑰、帳號；回測讀到當時尚未發布的收盤值。
可能原因
把原始回報全部印出，或把事件時間與可取得時間視為同一個欄位。
安全處置
日誌依需求保留遮罩、關聯 ID 與錯誤；憑證及個資不得進出測試資料。回測以當時可取得的版本與時間戳為準，預先設定切分區間、交易時段及成本。
紙上驗收
用假憑據檢查遮罩；放入一筆晚發布合成行情，驗證它不會在較早時點被讀取。

驗收順序：邊界、重放、延遲、對帳

  1. 設計可重複的測試：同 ID 同內容、同 ID 不同內容、部分成交、撤單競態與資料缺口。用輸入序號和最終現金、持倉作驗收證據。

延伸學習：實作、現場案例與自我檢查

本頁說明委託、成交、撤單是不同事件。本節用一個簡化帳戶實作保留額機制：下單前先檢查上限並保留資金，部分成交扣款，撤單只釋放未成交部分，全程以 Decimal 計算。

可實跑範例：委託前風控、保留額與撤單

可用資金 = 現金 − 保留額。每筆委託先檢查單筆上限與可用資金，接受後保留；成交時從保留轉為扣款；撤單釋放未成交部分。這是教學模擬，不連接任何交易系統，也不構成投資建議。

下載範例 example.py

"""委託前風控與保留額：下單時先保留資金，成交扣款、撤單釋放未成交部分；所有金額用 Decimal（教學模擬，不連任何券商）。"""
from decimal import Decimal as D


class Account:
    def __init__(self, cash):
        self.cash, self.reserved, self.orders = D(cash), D(0), {}

    @property
    def available(self):
        return self.cash - self.reserved

    def place(self, oid, qty, price, max_order_value=D("200000")):
        value = D(qty) * D(price)
        if qty <= 0 or D(price) <= 0:
            return f"{oid} 拒絕：數量與價格必須為正"
        if value > max_order_value:
            return f"{oid} 拒絕：單筆金額 {value:,} 超過上限 {max_order_value:,}"
        if value > self.available:
            return f"{oid} 拒絕：可用資金 {self.available:,} 不足 {value:,}"
        self.reserved += value
        self.orders[oid] = {"qty": qty, "price": D(price), "filled": 0}
        return f"{oid} 接受，保留 {value:,}，可用 {self.available:,}"

    def fill(self, oid, qty):
        o = self.orders[oid]
        qty = min(qty, o["qty"] - o["filled"])
        cost = D(qty) * o["price"]
        o["filled"] += qty
        self.reserved -= cost
        self.cash -= cost
        return f"{oid} 成交 {qty}，扣款 {cost:,}，現金 {self.cash:,}"

    def cancel(self, oid):
        o = self.orders[oid]
        left = o["qty"] - o["filled"]
        release = D(left) * o["price"]
        self.reserved -= release
        o["qty"] = o["filled"]
        return f"{oid} 撤單，釋放未成交 {left} 股的保留 {release:,}；已成交 {o['filled']} 股不回滾"


if __name__ == "__main__":
    acct = Account("300000")
    for step in (lambda: acct.place("A1", 100, "1050"),
                 lambda: acct.place("A2", 1000, "250"),
                 lambda: acct.place("A3", 200, "1100"),
                 lambda: acct.fill("A1", 60),
                 lambda: acct.cancel("A1"),
                 lambda: acct.place("A3", 150, "1100")):
        print(step())
    print(f"最終：現金 {acct.cash:,}、保留 {acct.reserved:,}、可用 {acct.available:,}")
    print("浮點數陷阱：0.1 + 0.2 =", 0.1 + 0.2, "；Decimal：", D("0.1") + D("0.2"))

A2 拒絕：單筆金額 250,000 超過上限 200,000
A3 拒絕：單筆金額 220,000 超過上限 200,000
A1 成交 60，扣款 63,000，現金 237,000

工程現場案例：撤單回報延遲，系統以為資金已釋放而重複下單

某自動化程式送出撤單後，立即把整筆委託金額加回可用資金並下新單。實際上撤單回報晚了幾秒，原委託在這期間又成交了一部分，結果兩筆委託同時成交，資金透支。問題在於把「送出撤單」當成「撤單成功」，並且忽略撤單前的部分成交。

範例中 A1 先成交 60 股、再撤單，只釋放未成交 40 股的保留額；已成交部分不會回滾。正確的保留額流程是：撤單回報確認後才釋放，而且只釋放確認時的剩餘數量。

  1. 每筆委託在送出前先保留資金，並檢查單筆與單日上限。
  2. 成交、撤單都以交易所或券商的回報為準，送出請求不等於狀態改變。
  3. 保留額、現金與持倉每日與券商對帳，不一致時停止自動下單。
  4. 金額與價格一律使用 Decimal，並明確設定四捨五入規則。

  • Python 標準函式庫的 decimal 模組實作 IEEE 754-2008 十進位浮點與 General Decimal Arithmetic 規格，可設定精度與捨入方式，適合金額計算；float 的二進位表示無法精確表示 0.1。 來源：Python 文件：decimal

練習題與自我檢查

  1. A3 第一次以 200 股被拒絕，第二次 150 股被接受。若第二次仍是 200 股，會因為什麼原因被拒絕？

    看解答

    200 × 1,100 = 220,000，超過單筆上限 200,000，與可用資金無關。風控檢查的順序決定回報的原因，通常先檢查規則性上限，再檢查資金。

  2. fill() 中 qty = min(qty, …) 的用意是什麼？

    看解答

    防止成交回報數量超過剩餘委託數量（例如重複收到回報），避免扣款超過保留額。實務上這種情況應該告警，因為代表回報處理有問題。

  3. 撤單時若原委託已全部成交，cancel() 會釋放多少？

    看解答

    left 為 0，釋放 0。撤單請求在全部成交後到達很常見，系統要能處理「撤單失敗：已成交」的回報，而不是當成錯誤。

  4. 為什麼保留額要在送出委託前扣，而不是成交後才扣？

    看解答

    若成交後才扣，多筆委託可能在成交前都通過資金檢查，同時成交時就會透支。先保留確保所有在途委託的最大可能支出都被計入。
