要量哪種「快」？三條測試線，不混成單一分數

  1. 交易延遲：記錄從 Python 發出到收到結果的 p50／p95／p99、成功數、逾時、重試及鎖等待；連線取得時間與 SQL 執行時間可分開觀測。
  2. 寫入吞吐：固定資料大小、索引數、批次、併發與提交頻率。用「已確認提交的列數 ÷ 經過秒數」算 rows/s，失敗數分列。並註明磁碟與同步持久性，不能拿關閉持久性的數字比正式配置。
  3. 報表和保留：固定資料筆數、時間窗、晚到比例、聚合粒度、資料新鮮度；分別量原始查詢與預聚合。另記錄磁碟量、背景作業和還原演練所需時間。

合成算式：30 秒內成功提交 18,000 列，吞吐為 600 rows/s，不能因此得出 p95。實測應固定初始資料、硬體、暖機與快取狀態，重複測試並保留版本。SQLite 嵌入式與網路型引擎的端到端測試可分兩組：「各自實際部署」和「盡量相同併發與耐久配置」。

工控選型：若需要斷網繼續緩衝，邊緣可選 SQLite；中心庫先依既有團隊、HA 和交易需求選。只有在時窗查詢、保留或大量補灌確實成為瓶頸，且回放測試優於現有方案時，再加入時序擴充。

Modeling

資料庫不是儲存細節，而是專案契約的一部分。schema、constraint、index 與資料生命週期都要能被 review。

Migration

把 schema 演進做成可回放流程

正式專案不能靠手動改資料表。每次欄位、索引與約束都要有版本、驗收與 rollback 思路。

Transaction

交易邊界要比函式邊界更清楚

commit、rollback、retry、idempotency 與 lock 行為決定資料是否可靠。

Transaction Walkthrough

從請求到提交：交易生命週期

目標不是「每句 SQL 都成功」，而是「新增筆記＋稽核紀錄」兩步一起成立。下面的流程對應本頁可下載、可執行的 Python 程式。

共同路徑

  1. 1. 驗證輸入

    Service 拒絕空標題；先做不需要資料庫的檢查，縮短持鎖時間。

  2. 2. 建立連線

    UoW 設定 timeout 與 foreign_keys，確保每次連線的約束設定一致。

  3. 3. BEGIN IMMEDIATE

    明確開始寫入交易。若其他寫入者仍持鎖，等待到 timeout 後可能失敗，不會自動重試。

  4. 4. Repository 寫入兩張表

    先 INSERT notes，再 INSERT audit；兩次 SQL 共用同一個 connection。

  5. 5. 離開 with，交給 UoW 判斷

    正常結束走提交；任何步驟拋出例外走回滾。如下方兩條結果路徑。

成功路徑 → COMMIT → CLOSE → 回傳 ID

兩筆資料一起提交。Service 在 with 區塊外才回傳成功，避免 commit 尚未完成就宣告操作成功。

失敗路徑 → ROLLBACK → CLOSE → 拋出例外

若稽核寫入失敗，已執行的筆記 INSERT 也要撤回；先前其他交易已提交的筆記仍保留。COMMIT 本身若失敗，也嘗試 rollback，再把錯誤傳回呼叫者。

為什麼 Repository 不提交？

假如 add() 立刻 commit，接著 audit 寫入失敗，第一筆已提交的資料就無法由這次 rollback 撤回。Repository 負責「怎麼寫」，Service 決定「做哪些事」，UoW 負責「什麼時候一起生效」。

原子性，不等於萬用復原

這個交易只涵蓋同一個 SQLite 資料庫中的 SQL 寫入。寄信、HTTP 呼叫、設備控制或寫入另一個資料庫，不會跟著 rollback。要處理外部副作用，可用 transactional outbox 先在同一交易寫入待發送事件，另由工作程序發送並以冪等鍵防重。

BEGIN IMMEDIATE 適合本範例的短寫入交易；不是所有查詢都應搶寫入鎖。SQLite 同時只允許一個寫入交易，WAL 也不會變成多寫入者。不要在交易中等待人員輸入或慢速網路；正式系統仍要測量競爭、錯誤與重試上限。

Defensive SQLite / DB-API Lab

常見 Python 資料庫錯誤：從症狀找到修正方式

先判斷是程式、資料、連線還是交易狀態，不要把所有例外都轉成重試。以下以合成電表事件示範；跨引擎行為須在各目標驅動程式與實際版本上再驗證。

01｜參數用字串插值，或使用錯的佔位符

症狀：名稱含特殊字元就失敗，或資料型別在傳送前被轉成文字。正確：SQL 與值分開，交由驅動程式綁定；單一值要傳 (meter_id,)。表名、欄名與排序規則不是值；使用固定白名單對應，或使用驅動程式提供的識別字 API，例如 Psycopg 的 sql.Identifier。

02｜把交易上下文當成關閉連線

症狀：SQLite with conn 結束後仍占資源。正確：with conn 處理交易而不關閉連線，生命週期另用 contextlib.closing 或 try/finally。不同驅動的上下文並不完全相同；租用池連線也應在 finally 歸還。

03｜捕捉例外後忘了回滾

症狀：前三筆入庫、第四筆壞掉，資料半套。正確：先定義整批是否原子，錯誤離開交易邊界並回滾；若使用交易上下文管理器，不要在內部吞掉需要回滾的例外。明確選用原生交易或驅動管理模式，不混用。

04｜不知道 COMMIT 有沒有成功就重送

症狀：送出 commit 後連線中斷，沒收到回應，重試卻出現兩筆。正確：以唯一事件 ID 加資料庫約束，從能確認最新寫入的查詢路徑核對結果。相同 ID 不同資料視為衝突；若仍不確定，記為待對帳。不要僅因逾時就重送付款等不可逆副作用。

05｜每筆都查一次：N+1

症狀：列 200 台電表，一個列表外再查 200 次。正確：用集合查詢、分批載入，或 JOIN／GROUP BY 在資料庫彙總。用測試量查詢次數與結果，不單看執行時間。大量結果分頁或串流，不把所有資料同時載入。

06｜長交易、鎖等待與無界重試

症狀：交易開著等外部 HTTP，其他工作拿不到鎖。正確：鎖內只做必要資料庫操作，分開設定連線、鎖等待或陳述式逾時（依驅動與引擎）。可重試錯誤要在回滾後才於外層重跑完整交易，設有限次數與退避。SQLite 即使使用 WAL，仍同時間只有一個寫入者。

07｜每個工作都建池，或多人共用同一連線

症狀：尖峰耗盡連線，交易互相干擾。正確：每個程序管理池生命週期，請求借出、短期使用、完成便歸還；總連線預算乘上程序數。查驅動 threadsafety，不要假設連線或 cursor 可同時使用。SQLite 的 check_same_thread=False 不會自動序列化應用的寫入。

08｜把時間與金額當成任意字串或浮點數

症狀：跨日或 DST 對帳差一小時，總額尾數不一致。正確：輸入驗證時區、統一 UTC；報表依需求轉回地方時間。SQLite 沒有專屬時間儲存類別，本例統一 UTC ISO 字串；伺服器型 DB 依型別與連線政策處理。金額或表讀值使用最小整數單位或適當的定點型別，不用二進位浮點假裝精確。

09｜變更索引之前沒看查詢計畫

症狀：資料量增加後才大量掃描，或每加一個索引就拖慢寫入。正確：先擷取代表性查詢、篩選與排序，再對照執行計畫和資料分布。SQLite 用 EXPLAIN QUERY PLAN。會執行陳述式的計畫功能先在測試環境用唯讀查詢驗證，勿直接套在正式寫入。

10｜批次太大，或在部署時一次做完遷移

症狀：大量寫入鎖住前台，或欄位切換使舊服務失效。正確：以可復原批次、事先定義提交邊界，並走新增 → 回填 → 驗收 → 切流 → 移除；回填用進度與一致性核對。executemany 不等於所有驅動會發單一請求；遷移是否可交易須依 DDL 與引擎驗證。

from __future__ import annotations

from dataclasses import dataclass
import sqlite3


@dataclass(frozen=True)
class Note:
    id: int
    title: str
    status: str


class NoteRepository:
    def __init__(self, conn: sqlite3.Connection) -> None:
        self._conn = conn

    def add(self, title: str, status: str = "open") -> Note:
        cursor = self._conn.execute(
            "INSERT INTO notes(title, status) VALUES (?, ?)",
            (title, status),
        )
        return Note(id=int(cursor.lastrowid), title=title, status=status)

    def list_by_status(self, status: str = "open") -> list[Note]:
        rows = self._conn.execute(
            "SELECT id, title, status FROM notes WHERE status = ? ORDER BY id",
            (status,),
        ).fetchall()
        return [self._map_row(row) for row in rows]

    def mark_done(self, note_id: int) -> None:
        self._conn.execute(
            "UPDATE notes SET status = 'done' WHERE id = ?",
            (note_id,),
        )

    @staticmethod
    def _map_row(row: sqlite3.Row) -> Note:
        return Note(id=int(row["id"]), title=str(row["title"]), status=str(row["status"]))

class NoteService:
    def __init__(self, database_path: str | Path) -> None:
        self._database_path = database_path

    def create_note(self, title: str) -> Note:
        normalized_title = title.strip()
        if not normalized_title:
            raise ValueError("title must not be blank")

        with UnitOfWork.open(self._database_path) as uow:
            note = uow.notes.add(normalized_title)
            uow.commit()

        with UnitOfWork.open(self._database_path) as uow:
            uow.notes.add(title.strip())
            raise RuntimeError("simulated failure before commit")

        with UnitOfWork.open(self._database_path) as uow:
            notes = uow.notes.list_by_status("open")
            uow.commit()
            return notes

from __future__ import annotations

from pathlib import Path
import sqlite3
from types import TracebackType

from .repository import NoteRepository
from .schema import initialize_database


class UnitOfWork:
    def __init__(self, conn: sqlite3.Connection) -> None:
        self._conn = conn
        self.notes = NoteRepository(conn)
        self._committed = False

    @classmethod
    def open(cls, database_path: str | Path) -> "UnitOfWork":
        conn = sqlite3.connect(str(database_path))
        conn.row_factory = sqlite3.Row
        initialize_database(conn)
        return cls(conn)

    def __enter__(self) -> "UnitOfWork":
        self._conn.execute("BEGIN")
        return self

    def commit(self) -> None:
        self._conn.commit()
        self._committed = True

    def rollback(self) -> None:
        self._conn.rollback()

    def __exit__(
        self,
        exc_type: type[BaseException] | None,
        exc: BaseException | None,
        tb: TracebackType | None,
    ) -> None:
        if exc_type is not None or not self._committed:
            self.rollback()
        self._conn.close()

2. 讀懂程式的四個邊界

  1. initialize：建 notes 與 audit 表。NOT NULL、UNIQUE、CHECK 和 foreign key 防止錯誤資料落地。建表獨立於業務交易；executescript 不應直接搬進這個 UoW 的交易區塊。
  2. NoteRepository：add() 回傳 lastrowid；record() 用該 ID 寫稽核。SQL 中的 ? 只綁定值，不可用來綁定表名、欄位名；動態識別字必須來自明確允許清單。
  3. UnitOfWork：isolation_level=None 搭配明確 BEGIN IMMEDIATE，不依賴 INSERT 的隱式 BEGIN；foreign_keys 在 BEGIN 前開啟。__enter__ 若失敗會關閉連線，__exit__ 無論成功與否都釋放連線。
  4. create_note：驗證後在同一 with 裡完成兩次寫入。測試旗標故意在第一次 INSERT 後丟錯，觀察第一筆是否真的消失。

sqlite3.connect() 在這份程式未設定 Python 3.12 新增的 autocommit 參數，使用目前預設的 legacy transaction control 配合 isolation_level=None。若改用 autocommit=True，不能直接照抄這裡的 connection.commit()/rollback()，應重新設計並驗證交易控制方式。

3. 七個測試各自證明什麼？

  1. 正常提交：一筆 notes 和一筆 audit 都能從新連線讀到。
  2. 中途例外：第一次 INSERT 不會殘留，兩張表仍為空。
  3. 參數綁定：包含引號與 DROP TABLE 字樣的標題只是文字，資料表不會被刪除。
  4. 唯一約束：同一交易先新增、再插入重複標題時，新筆記也撤回；舊資料保留。
  5. 外鍵約束：不存在的 note_id 使交易失敗，先前 INSERT 同樣撤回。
  6. Service 驗證：空白標題在開始交易前被拒絕。
  7. 資料庫防線：繞過 Service 直接插入空字串，CHECK 仍拒絕寫入。

read_state() 每次開啟新連線，不只檢查寫入連線自己的未提交視圖。測試未涵蓋斷電、磁碟已滿、COMMIT 故障注入或多程序寫入競爭；正式部署前需另外驗證，不能把七個單元測試當成所有可靠性證明。

"""Python 3.10+ / standard library only. Run: python3 database_uow_walkthrough.py"""
import sqlite3
import tempfile
import unittest
from pathlib import Path


def initialize(path):
    # Schema setup is separate from business transactions.
    conn = sqlite3.connect(path, isolation_level=None)
    try:
        conn.executescript('''
        CREATE TABLE IF NOT EXISTS notes (
            id INTEGER PRIMARY KEY,
            title TEXT NOT NULL UNIQUE CHECK(length(trim(title)) > 0)
        );
        CREATE TABLE IF NOT EXISTS audit (
            id INTEGER PRIMARY KEY,
            note_id INTEGER NOT NULL REFERENCES notes(id),
            action TEXT NOT NULL
        );
        ''')
    finally:
        conn.close()


class NoteRepository:
    def __init__(self, conn):
        self.conn = conn

    def add(self, title):
        # Values are bound, never interpolated into SQL.
        cursor = self.conn.execute('INSERT INTO notes(title) VALUES (?)', (title,))
        return cursor.lastrowid

    def record(self, note_id):
        self.conn.execute(
            'INSERT INTO audit(note_id, action) VALUES (?, ?)',
            (note_id, 'created'),
        )


class UnitOfWork:
    def __init__(self, path):
        self.path = path

    def __enter__(self):
        # Explicit SQL transactions avoid reliance on implicit BEGIN behavior.
        self.conn = sqlite3.connect(self.path, timeout=5.0, isolation_level=None)
        try:
            self.conn.execute('PRAGMA foreign_keys = ON')
            self.conn.execute('BEGIN IMMEDIATE')
            self.notes = NoteRepository(self.conn)
            return self
        except BaseException:
            self.conn.close()
            raise

    def __exit__(self, exc_type, exc, tb):
        try:
            if exc_type is None:
                try:
                    self.conn.commit()
                except BaseException:
                    self.conn.rollback()
                    raise
            else:
                self.conn.rollback()
        finally:
            self.conn.close()
        return False  # Never hide the original business exception.


def create_note(path, title, fail_after_insert=False):
    if not isinstance(title, str) or not title.strip():
        raise ValueError('title must not be empty')
    with UnitOfWork(path) as uow:
        note_id = uow.notes.add(title)
        if fail_after_insert:
            raise RuntimeError('simulated failure before audit')
        uow.notes.record(note_id)
    # Return success only after __exit__ commits successfully.
    return note_id


def read_state(path):
    # A fresh connection proves what another reader can actually observe.

class ReadingRepository:
    def __init__(self, cursor, namespace, marker):
        self.cursor = cursor
        self.ns = namespace  # selected from source-code constants only
        self.marker = marker

    def insert(self, device_id, observed_at, temperature):
        params = ", ".join([self.marker] * 3)
        self.cursor.execute(
            f"INSERT INTO {self.ns}lab_reading "
            f"(device_id, observed_at, temperature_c) VALUES ({params})",
            (device_id, observed_at, temperature),
        )

    def audit(self, event_id, device_id, observed_at):
        params = ", ".join([self.marker] * 3)
        self.cursor.execute(
            f"INSERT INTO {self.ns}lab_audit "
            f"(event_id, device_id, observed_at) VALUES ({params})",
            (event_id, device_id, observed_at),
        )

    def exists(self, table, key, value):
        # Table/column come from these exact allowlisted pairs.
        if (table, key) not in {("lab_reading", "device_id"), ("lab_audit", "event_id")}:
            raise ValueError("unsupported check")
        self.cursor.execute(
            f"SELECT COUNT(*) FROM {self.ns}{table} WHERE {key} = {self.marker}",
            (value,),
        )
        return self.cursor.fetchone()[0] > 0


def save_reading(conn, repo, device_id, observed_at, value, event_id):
    try:
        repo.insert(device_id, observed_at, value)
        repo.audit(event_id, device_id, observed_at)
        conn.commit()
    except Exception:
        # If rollback itself fails, the caller closes/discards the connection.
        # A network error during COMMIT can leave the outcome unknown.
        conn.rollback()
        raise


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("engine", choices=("mysql", "sqlserver", "postgresql", "timescale"))
    args = parser.parse_args()
    ns = {"mysql": "", "sqlserver": "dbo.", "postgresql": "public.", "timescale": "public."}
    marker = "?" if args.engine == "sqlserver" else "%s"
    now = datetime.now(UTC)
    if args.engine == "mysql":
        now = now.replace(tzinfo=None)  # DATETIME uses the app's UTC contract
    if args.engine == "sqlserver":
        # ISO 8601 string with explicit offset, converted to datetimeoffset by SQL Server.
        now = now.isoformat(timespec="microseconds")
    event_id = str(uuid4())
    conn, conflict = connect(args.engine)
    with closing(conn), closing(conn.cursor()) as cur:
        if args.engine == "sqlserver":
            cur.execute("SET XACT_ABORT ON")
        repo = ReadingRepository(cur, ns[args.engine], marker)
        save_reading(conn, repo, 101, now, Decimal("12.50"), event_id)
        try:
            # A fresh reading passes first; duplicate audit PK must roll it back.
            save_reading(conn, repo, 102, now, Decimal("13.25"), event_id)
        except conflict:
            pass
        else:
            raise RuntimeError("expected duplicate audit primary key")
        if not repo.exists("lab_reading", "device_id", 101):
            raise RuntimeError("committed reading is missing")
        if not repo.exists("lab_audit", "event_id", event_id):
            raise RuntimeError("committed audit is missing")
        if repo.exists("lab_reading", "device_id", 102):
            raise RuntimeError("second reading leaked through rollback")
        conn.rollback()  # end the verification's read transaction explicitly
    print(f"PASS {args.engine}: commit visible, duplicate audit rolled back reading")


if __name__ == "__main__":
    main()

Delivery · Recovery

遷移流程：Expand → Backfill → Verify → Contract

案例：為量測表的取樣來源新增 source_quality。先加可空欄位／相容介面，舊程式仍能寫；再部署新程式、分批回填、驗證缺值與延遲；最後才加強約束並在舊版本不再可回退後清掉舊路徑。每步都有變更單、版本紀錄、前置檢查與監控門檻。

  1. Expand
    允許舊版、新版並存。
  2. Backfill
    小批、可重入、記錄游標。
  3. Verify
    比對總數、缺值、p95 和副本延遲。
  4. Contract
    確認無舊讀寫端與還原演練後收斂。
引擎遷移策略失敗時的回復
SQLite使用短、顯式 DDL 交易；修改限制較多時在停寫視窗重建表，做 foreign_key_check。不要把既有交易和 executescript() 誤當同一原子單位。未提交 rollback；提交後走 forward fix 或還原一致性的 DB 備份並補資料。
MySQL先查 DDL 是否隱含提交，再選受版本和操作支援的 ALTER 演算法；交易式 DML 回填與 DDL 分開。許多 DDL 即使 atomic DDL 也不能由使用者 rollback；用前向修補、切回相容版本或備份＋binlog 還原。
SQL Server先驗證操作能否在顯式交易內執行；即使支援 rollback 也要評估 schema lock、日誌成長與阻塞。設定有限鎖等時間。能回滾且尚未提交時依交易狀態 rollback；已提交用相容應用／修補遷移，必要時依復原模式還原。
PostgreSQL多數一般 DDL 可放短交易；CREATE INDEX CONCURRENTLY 必須分開不包 transaction block。排查未完成的無效索引後再重跑。交易式且未提交可 rollback；跨交易步驟須先查實際 schema 狀態。PITR 要先驗證 WAL 與備份。
TimescaleDB先檢查 PG／擴充版本矩陣；非空表轉 hypertable 需評估 migrate_data 與鎖，較大庫先演練新表＋分批搬遷。保留政策刪除的 chunk 不靠 DDL rollback 還原。測試重新建立索引、彙總刷新與政策啟停後的資料缺口。

import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE reading(
    point_id TEXT NOT NULL,
    ts       INTEGER NOT NULL,          -- UTC epoch 秒
    value    REAL,
    quality  TEXT NOT NULL CHECK (quality IN ('good','uncertain','bad')),
    PRIMARY KEY (point_id, ts)
) WITHOUT ROWID;
""")

rows = [(f"P{p:03d}", 1_795_800_000 + i * 60, 20 + (i % 10) * 0.1, "good") for p in range(50) for i in range(200)]
db.executemany("INSERT INTO reading VALUES (?,?,?,?)", rows)
print(f"寫入 {len(rows):,} 筆")

db.execute("INSERT INTO reading VALUES ('P001', 1795800000, 25.0, 'good') "
           "ON CONFLICT(point_id, ts) DO UPDATE SET value=excluded.value")
print("改用 UPSERT 後的值：", db.execute("SELECT value FROM reading WHERE point_id='P001' AND ts=1795800000").fetchone()[0])

q2 = "SELECT avg(value) FROM reading WHERE ts BETWEEN 1795800000 AND 1795803600"
for name, q in (("依點位＋時間", q1), ("只依時間", q2)):

工程現場案例：一年後，「昨天所有點位的平均值」要跑 3 分鐘

某系統的讀值表只有自動遞增的 id 主鍵。資料量小時一切正常，一年後累積上億筆，按時間範圍查詢要掃描整張表。另一個問題是閘道器重送時同樣的資料被寫入兩次，平均值與加總都偏了。

以（點位, 時間）為主鍵同時解決重複與「單一點位查詢」的效能；若常需要跨點位依時間查詢，再加上時間索引。每次新增查詢都用 EXPLAIN QUERY PLAN（其他資料庫用 EXPLAIN）確認，而不是等資料變多才發現。

  1. 時序表以業務鍵（點位、時間）作為主鍵或唯一索引。
  2. 寫入使用 UPSERT，讓重送具有冪等性。
  3. 用 CHECK 或外鍵限制欄位的合法值。
  4. 為常用查詢檢查查詢計畫，並用接近真實規模的資料測試。

練習題與自我檢查

  1. 為什麼主鍵是 (point_id, ts) 而不是 (ts, point_id)？

    看解答

    最常見的查詢是「某個點位在某段時間的資料」，主鍵第一欄為 point_id 時可以先定位點位，再在該點位內依時間範圍搜尋。若第一欄是 ts，單一點位的查詢就要掃過該時間範圍內所有點位的資料。

  2. ON CONFLICT … DO UPDATE 與 INSERT OR IGNORE 該怎麼選？

    看解答

    重送的資料與原資料相同時兩者結果一樣。若重送可能帶有更正後的值（例如補值），用 DO UPDATE；若第一次寫入的值才是權威，用 IGNORE。這是業務規則，要明確決定。

  3. ts 用整數 epoch 秒而不是文字日期，有什麼好處？

    看解答

    比較與範圍查詢快、不受時區格式影響、占用空間小。顯示時再轉成當地時間。重要的是全系統統一使用 UTC。

  4. 加上時間索引後，寫入會變慢嗎？

    看解答

    會，每次寫入都要多更新一個索引。是否值得要看查詢頻率與寫入量；大量寫入的系統通常只建立必要的索引，或改用依時間分區的資料表。
