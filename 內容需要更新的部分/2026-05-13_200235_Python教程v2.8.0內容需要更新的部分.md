## 4. Configuration

型別契約教材要明確說明以下設定：

| 設定 | 建議內容 |
|---|---|
| static policy | production code 建議逐步導入 type checker；教材先以 contract report 示範 |
| payload boundary | 外部 payload 先經 runtime validation，再進 domain dataclass |
| Protocol boundary | repository、publisher、gateway adapter 以 Protocol 表達依賴 |
| dataclass invariant | 使用 frozen dataclass 與 `__post_init__` 保護非法狀態 |
| CI policy | type check 可先 warning，核心 schema/contract smoke 應 blocking |
| evidence policy | contract report 寫入 schema version、required keys、status 與 alarm/fail-safe 結果 |

## 7. Troubleshooting

| 狀況 | 補強方向 |
|---|---|
| 學生以為 type hints 會自動做 runtime 驗證 | 明確區分 static contract 與 runtime validation |
| Protocol 看不出價值 | 用 fake publisher 測試 alarm 邊界 |
| schema 變更沒有版本化 | 加入 schema version 與 contract report |
| 工業 payload 直接進 business logic | 加入 IO mapping、unit、range、stale timeout 與 fail-safe |
| CI 過度嚴格導致導入困難 | 教材說明 warning lane 到 blocking lane 的漸進策略 |

## 8. Best Practices

- 外部輸入先 validation，再建立 domain model。
- domain model 不應允許非法狀態。
- Protocol 用於依賴反轉，不用於包裝所有小函式。
- static analysis policy 應逐步導入，先從核心 domain 與 API boundary 開始。
- 對工業資料流，型別契約應包含單位、量測範圍、timeout、alarm 與 fail-safe 描述。
