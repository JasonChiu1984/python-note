1｜研究問題、假說與變因

並發是多個工作的生命週期交錯；平行是同一時刻有多個運算單位實際工作。單執行緒事件迴圈能讓 I/O 並發，不會讓不含讓出點的純 Python 迴圈在多個核心平行。本文把「效率」拆成一批完成時間、穩態吞吐、單筆尾端延遲、峰值資源與故障後行為；它們可能互相衝突。

  • H1：固定等待工作，四個工作者可重疊等待，整批耗時應低於序列。
  • H2：一般 GIL 下，純 Python CPU 工作放進同直譯器執行緒不會因此多核加速；程序與隔離直譯器可能受複製、排程和序列化抵消。
  • H3：關掉 GIL 的建置允許執行緒同時執行 Python bytecode；加速幅度仍取決於工作量、核心額度與共享資料爭用。

主要依變數：每次 16 筆整批完成毫秒，非單筆服務延遲。速度比 S = 同建置序列批次中位數 ÷ 該模式批次中位數；S>1 才代表此批次更快。比率不是線性擴張保證。

2｜五種執行界線與 GIL 機制

方式共享與 CPU 限制成本、取消與適用條件
序列同工作序列逐筆完成；為正確性與起始計時參考。低排程成本、易回溯；I/O 等待無法重疊。
asyncio／TaskGroup同一事件迴圈以 await 交錯；資料共享仍有跨 await 的邏輯競態。合適大量非阻塞 I/O。用 timeout 驗證截止；阻塞 API 放到有界 executor，不要吞 CancelledError。
ThreadPoolExecutor同程序同 heap；一般 CPython 同一 GIL 中不保證 Python bytecode 多核平行，I/O 與可釋放 GIL 的原生核心例外。I/O 適用、低啟動成本；共享狀態用鎖／所有權。Future.cancel() 通常無法停止已執行的函式，需合作取消。
ProcessPoolExecutor不同程序及位址空間，可多核運算；參數與回傳需可序列化，獨立 RAM 與 IPC。適合可切分 CPU 工作；分批可攤薄傳輸成本，太大則拉高尾延遲。起始方式及入口保護影響可移植性。
InterpreterPoolExecutor同一程序中的工作執行緒，各有隔離直譯器；一般建置各直譯器有自己的 GIL，不共享可變 Python 物件，透過序列化分派。不同模組實例與初始化，原生擴充需驗證多直譯器相容。不是獨立程序的故障隔離或安全沙箱。
free-threaded 建置部署選擇而非第六種調度器；實際 GIL 可因啟動選項或未宣告相容的擴充而啟用。直接量 sys._is_gil_enabled()。留意鎖爭用、記憶體與原生套件 wheel／ABI；不以容器內部實作當應用原子性。

把 NumPy、BLAS 或其他原生核心測試與純 Python 分開，因為 C 實作可能釋放 GIL 或另起執行緒。限制其原生並行數（依套件設定）以避免「外層 4 worker × 內層多執行緒」超額訂閱，並記下編譯／運算函式庫版本。

3｜Windows、macOS、Linux：預設值不等於同一條路

平台multiprocessing 常見預設重做研究時先查的差異
Windowsspawn；不使用 POSIX fork。子程序重開直譯器並匯入模組；函式放模組頂層、以 if __name__ == "__main__" 保護入口。實測 worker 啟動、Handle/IPC 成本。
macOS3.8 起預設 spawn；官方特別提醒系統函式庫可能建立執行緒，直接 fork 有風險。確認硬體與執行架構，例如原生 arm64 或轉譯；不要為追求啟動速度而任意切回 fork。
Linux3.13 及前的常見 POSIX 預設 fork；3.14 起支援 FD 傳遞的 POSIX（如 Linux）常見 forkserver。3.15.1 起若沒有可寫暫存目錄會選 spawn。實查可用與實際 start method；容器 CPU quota、cpuset、forkserver socket 權限以及程序額度都可能變成限制，不能假定相同主機配置。

同時報 multiprocessing.get_all_start_methods()、multiprocessing.get_start_method() 與程式實際使用的 get_context(...).get_start_method()。函式庫應讓呼叫端提供 multiprocessing context，別在匯入時改寫全程序預設。

4｜控制條件與重跑方法

兩工作負載：16 個各 8 ms 的 sleep 等待（無實體網路），以及 16 個各 180,000 次有相依性的 32 位元整數迴圈。每模式最多 4 個 worker；asyncio CPU 路徑刻意不 offload，以觀察同一事件迴圈的序列 CPU 行為。函式結果逐筆相同才接受一組量測。

  1. 同建置、同工作量輪換五模式的執行先後；預熱一輪、有效計時 7 輪，使用單調 perf_counter_ns()。
  2. 重用執行器及事件迴圈；不把第一次啟動或最後關閉計入，仍包含每批分派、等待與結果回收。另做冷啟動研究不能拿本表代替。
  3. 留下全部樣本、最小值、中位數與最大值；7 筆不是可信尾端延遲估計。採集每請求延遲時再另報 p95/p99 和樣本量。
  4. 明確指定 --start spawn。本隔離環境拒絕 forkserver 的 AF_UNIX 建立，不把沙箱行為假說成 Linux 不支援。

6｜把實驗搬到實務：背壓、記憶體與取消

穩態與容量

每筆 enqueue、實際開始、完成、持久化分別打時間戳，分離佇列與服務時間。在相同穩態與時間窗可用 L ≈ λW 檢查平均佇列／在途量是否合理。過載時另統計丟棄、timeout、重試及資料年齡；不只看成功樣本。

有界背壓

Semaphore 只限制同時工作，不會自動阻止先建立百萬個 Task。真實串流宜用 asyncio.Queue(maxsize=N) 搭配固定 consumers，或 3.14+ Executor.map(..., buffersize=N)；定義等待、拒絕、降頻與過期策略。

記憶體可比較性

另量 process tree PSS（Linux）或同平台的等價指標；累加 RSS 會重複計入共享頁。tracemalloc 主要涵蓋被追蹤的 Python 配置，不能當原生擴充或全程序記憶體。不把本表解讀成記憶體比較。

停止與安全

逾時可能只停止等待而不停止遠端已執行的命令。配合 TaskGroup、取消訊號、有限期限與冪等；工控寫入不要盲重送，先確認設備狀態。已開始的執行緒／程序工作要有清理方案。

後續可否證試驗：將主機／Python 版本／build 分層固定，分別測 workers 1、2、4、8，掃描任務大小及 IPC payload；每層至少報重複試驗與完整原始值。冷快取、穩態、CPU affinity、核心配額、熱降頻和共置背景程序不可混為一層。

深入解析與評估邊界

先定義計數範圍：提交窗含已排隊、執行中與已完成但尚未退役的 Future。它不是 worker 活躍負載，也不是整體記憶體上限：實驗把結果保存到 list，服務若需限制儲存量應逐筆下游消費，另限 payload 大小。

兩條時間線：對每筆記錄入列、開始、完成三個單調時間；排隊延遲＝開始−入列，服務延遲＝完成−開始。固定輸入、池大小與過載政策，分別測冷啟動和熱池；至少列測試次數、p50、p95 和丟棄率，不用單一最快值。

不把正確執行誤成 CPU 平行：本 lab 是 ThreadPoolExecutor 的提交界線，不測 thread、process、free-threaded 或 interpreter 的速度勝負。純 Python CPU、原生會釋放 GIL 的運算、等待型負載要分開比較；程序與子直譯器還需把資料移動與啟動成本算進去。

處理取消和錯誤：future.result() 會把工作錯誤帶回呼叫者。本例離開 executor context 會等待，不承諾正在執行的工作可取消。正式服務應定義拒絕新任務、合作式取消、收尾期限、監控與客戶的可預期回應。

延伸學習：實作、現場案例與自我檢查

本頁以實測比較各種執行方式。本節補上實測之前應該先算的理論上限：可平行比例決定了加開工作者最多能快幾倍，並整理各平台 multiprocessing 預設啟動方式的差異。

可實跑範例：Amdahl 與 Gustafson 加速比上限

Amdahl 定律假設總工作量固定，Gustafson 定律假設工作量隨工作者增加而增加。範例只做計算，不量測本機時間，因此在任何機器上輸出都相同。

下載範例 example.py

"""加速比的上限：Amdahl 定律與 Gustafson 定律，並列出各平台 multiprocessing 預設啟動方式（標準函式庫）。

輸出不量測本機時間，因為不同機器結果不同；量測方法請見本頁第 4 節。
"""


def amdahl(p, n):
    """固定工作量：可平行比例 p、n 個工作者的加速比上限。"""
    return 1 / ((1 - p) + p / n)


def gustafson(p, n):
    """工作量隨工作者數增加：可平行比例 p 時的擴展加速比。"""
    return (1 - p) + p * n


if __name__ == "__main__":
    workers = (1, 2, 4, 8, 16, 64)
    print("可平行比例 |" + "".join(f"{n:>7}" for n in workers))
    for p in (0.5, 0.8, 0.95, 0.99):
        print(f"Amdahl {p:4.0%} |" + "".join(f"{amdahl(p, n):7.2f}" for n in workers))
    print(f"Gustafson 95% |" + "".join(f"{gustafson(0.95, n):7.2f}" for n in workers))
    print()
    print("例：資料解析 95% 可平行，其餘 5% 是讀檔與彙總。8 核心最多約", f"{amdahl(0.95, 8):.1f}", "倍，",
          "即使 64 核心也只有", f"{amdahl(0.95, 64):.1f}", "倍（上限 20 倍）。")
    print()
    defaults = [("Linux（Python 3.14 起）", "forkserver"), ("Linux（3.13 以前）", "fork"),
                ("macOS（3.8 起）", "spawn"), ("Windows", "spawn")]
    print("multiprocessing 預設啟動方式：")
    for plat, method in defaults:
        print(f"  {plat:<22} {method}")

工程現場案例：報表從 4 核心換到 16 核心，只快了 1.6 倍

某能源報表程序用 multiprocessing 平行解析 200 個點位的月資料，搬到 16 核心伺服器後預期快 4 倍，實際只快約 1.6 倍。剖析後發現讀取原始檔與最後彙總寫 Excel 占了約 20% 的時間，而且只能單一程序執行。依 Amdahl 定律，可平行比例 80% 時，4 核心上限 2.5 倍、16 核心上限 4.0 倍，兩者相比只多 1.6 倍，與實測一致。

改善方向是縮小序列部分：讀檔改成各工作者直接讀自己負責的檔案，彙總改成先在各工作者內部分彙總，最後只合併少量結果。之後可平行比例提高到約 95%，16 核心的上限就提高到約 9 倍。

  1. 先用剖析工具量出序列部分（讀檔、彙總、寫檔）占總時間的比例。
  2. 用 amdahl() 算出目標核心數的理論上限，判斷加硬體是否值得。
  3. 優先縮小序列部分，再增加工作者數。
  4. 跨平台部署時明確指定 multiprocessing 啟動方式，不依賴預設值。

版本與法規更新（核對日期 2026-11-28）

  • Python 3.14 起，Linux 等 POSIX 平台（macOS 除外）的 multiprocessing 預設啟動方式由 fork 改為 forkserver。依賴 fork 繼承全域狀態的程式（例如在主程序開好的連線或已載入的大型物件）在升級後可能行為改變，應以 multiprocessing.get_context('fork') 明確指定或改寫成不依賴繼承。 來源：What's new in Python 3.14：multiprocessing

練習題與自我檢查

  1. 可平行比例 99% 時，Amdahl 的理論上限是多少倍？

    看解答

    1 ÷ (1 − 0.99) = 100 倍。64 核心時約 39 倍，離上限還很遠；這類工作才值得投資大量核心。

  2. 為什麼 Gustafson 定律的數字比 Amdahl 樂觀得多？

    看解答

    Gustafson 假設工作者增加時，問題規模也跟著放大（例如處理更多點位或更長期間），序列部分所占比例因此變小。Amdahl 則假設問題規模固定。兩者回答的是不同問題。

  3. 程式從 Python 3.13 升到 3.14 後，子程序讀不到主程序在 if __name__ == '__main__' 之前建立的全域快取，可能原因是什麼？

    看解答

    Linux 預設啟動方式從 fork 改為 forkserver。fork 會複製主程序的記憶體，forkserver 不會，子程序需重新匯入模組並重建狀態。可改為在子程序初始化函式中建立快取，或明確指定 fork。

  4. I/O 密集的工作（例如輪詢 100 台設備）適合用 Amdahl 定律估算嗎？

    看解答

    不太適合。I/O 等待時間主要由設備回應決定，瓶頸可能在網路或設備併發上限，而不是 CPU 核心數。這類工作要用 asyncio 或執行緒，並量測設備端的可承受併發數。
