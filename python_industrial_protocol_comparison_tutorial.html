十個通訊協定家族比較

協定 傳輸與拓樸 資料模型／更新 典型場景 Python 整合位置與驗收
Modbus RTU 多站序列匯流排；TCP 透過 IP 網路。逐項比較 RTU／TCP Coil、Discrete Input、Input／Holding Register；請求與回應 VFD、電表、流量計、PLC 由 client 輪詢。確認 Unit ID、FC、零起算位址、跨字順序

OPC UA 此範例使用 Client/Server、SecureChannel 與 Session Namespace URI、NodeId、DataValue；Read 與 Subscription PLC／SCADA、MES、Historian UA client。核對信任、型別、StatusCode、時間戳與失聯恢復

Zigbee IEEE 802.15.4；協調器、路由器與末端裝置，可建網狀路由 Endpoint、cluster、attribute；裝置報告或命令 電池溫溼度、占用、門磁 接協調器橋接端。驗證配對、裝置支援、上報週期及 stale
PROFINET IO 工業乙太網路；IO Controller、IO Device，可配工程拓樸 Slot／Subslot、循環 I/O、非循環 Record、診斷 分散 I/O、PLC、伺服與驅動 PLC／主站執行循環，Python 讀資料快照。驗證 GSDML、站名、子模組品質
PROFIBUS DP 常見 RS-485 多站匯流排，依配置可有光纖 Master/Slave 循環 I/O，DP-V1 另可用非循環服務 既有 PLC、遠端 I/O、變頻器 用 DP 主站。驗證 GSD、站號、模組資料長度、Data_Exchange 與診斷
CC-Link Classic 專用 RS-485 型現場網路；主站與遠端站 循環 RX/RY 位元與 RWr/RWw 字；依站種及占用站數配置 三菱 PLC、遠端 I/O、驅動設備 PLC 主站模組交換資料，Python 讀對應 PLC 區。須辨識 Classic 與 CC-Link IE 家族
EtherNet/IPEthernet；CIP Scanner／AdapterImplicit I/O 循環；Explicit 請求回應PLC、遠端 I/O、驅動由 Scanner 處理控制 I/O；Python 從閘道或 PLC 快照讀取已驗收資料。
EtherCATMainDevice、SubDevice；常用 100BASE-TX 物理鏈路循環過程資料、按設備能力同步時鐘伺服、分散 I/O、同步取樣控制器執行循環；Python 讀控制器映射區或上層介面。

依需求分層。VFD 電流可由 Modbus 讀取，AHU 測點與告警可由 BACnet 取得，SCADA 或 MES 可用 OPC UA 取結構化資料，而 MQTT 用於發布已加上時間、單位及品質的遙測。PROFINET、PROFIBUS DP 與 CC-Link 的循環時間、watchdog 與故障輸出由主站與裝置工程配置驗收。非即時的 Python 採集不應承擔控制迴路或消防連鎖。

十種協定的優缺點與使用場景

協定優點限制使用場景
Modbus TCP／RTU設備支援廣，連續暫存器可批次讀取，RS-485 可共用既有配線。單位、比例、有號值及字序依設備點表。多站串行輪詢時，一站逾時會拖長整輪。變頻器頻率、電表功率、流量計瞬時量與累積量。既有 RTU 設備可用 TCP／RTU 閘道集中採集。
BACnet樓控物件可帶單位、品質與告警。支援的點可用 COV 推送變更，減少持續輪詢。裝置對 COV、批讀及分段的支援有差異。跨 VLAN 要處理探索、BBMD／路由，或規劃 SC Hub。AHU、DDC、冰水系統、BMS。以 EBO 聚合送風溫度、設備狀態、排程與告警。
OPC UA資料有型別、品質、時間戳及可瀏覽的結構，適合跨系統訂閱。須維護 NodeId 與憑證。大量訂閱需要伺服器資源，資料採樣與發布各有週期。PLC／工業閘道到 SCADA、Historian、MES。把溫度、設備狀態與品質一併提供給上位系統。
MQTT發布端和訂閱端可獨立部署，同一批遙測可被多個系統接收，支援 QoS 和會話設定。需要 broker 與 topic 規劃。資料格式、去重、逾期及業務確認由應用處理。各機房閘道上送遙測、跨站告警、能源資料與資料平台整合。
Zigbee低功耗，適合電池端裝置。具路由能力的節點可以延伸覆蓋。訊號受牆面、金屬櫃和同頻干擾影響。電池裝置會休眠，更新受回報條件與週期影響。既有空間加裝室溫、濕度、門磁或占用感測。透過協調器橋接到 MQTT。
PROFINET IO循環 I/O 更新可配置，有模組／通道診斷，RT 和 IRT 支援不同即時要求。設備、GSDML、組態工具及網路配置須相容。IRT 需要支援的硬體與拓樸。PLC 遠端 I/O、驅動器與機台控制。需要同步的多軸運動則核對 IRT 支援。
PROFIBUS DP成熟的主站循環 I/O，既有 DP 設備多，可直接讀站與模組診斷。RS-485 線長受速率限制，終端、接頭或站號配置錯誤可影響整段。既有產線的 DP 變頻器、ET 200 遠端 I/O 或控制設備保留與改造。
CC-LinkClassic 以位元和字交換循環 I/O，三菱 PLC 的 Link Refresh 便於映射到 CPU。須核對站種、占用站數與刷新區；Classic、IE Field Basic、IE Field 和 IE TSN 的設備與配置不同。三菱 PLC、遠端 I/O、變頻器。既有 Classic 用專用匯流排，乙太網路案依設備支援選 IE 版本。
EtherNet/IP使用標準 Ethernet 傳輸 CIP，結合循環 I/O 與非循環服務。依裝置與 Scanner 核對 RPI、通訊負載及支援的安全 Profile。PLC 與工業乙太網路 I/O、驅動、診斷。
EtherCAT同一幀交換多站過程資料，支援 Distributed Clocks 的裝置可同步。週期和整體延遲由主站、站數、資料量及 PLC 任務影響，並非固定值。多軸同步、快速遠端 I/O、量測。

速度快慢比較

延伸實作：100M／1GbE 傳送時間與吞吐計算 · 工業通訊塞車診斷。

線速是實體鏈路每秒可傳的位元數。更新週期是連續兩次取樣、輪詢或循環 I/O 之間的時間。端到端延遲從來源變化到 Python、SCADA 或 BMS 看見新值為止，還會受到 PLC 掃描、閘道、排隊、重送及上位系統刷新影響。

協定相對速度與比較條件驗收時量哪一段
PROFINET IO若需求是短週期且低抖動的控制 I/O，優先比較 RT／IRT。部分 RT 設備可配置至 250 µs，需核對控制器及裝置支援。實際 I/O 更新週期、最大抖動、watchdog 超時及故障恢復。
PROFIBUS DP專用主站可循環交換 I/O，適合有固定掃描預算的控制。站數、資料量和線速會改變週期，與 CC-Link 的快慢要按相同 I/O 負載實測。從站輸入變化到 PLC 程序映像更新及最壞循環時間。
CC-LinkClassic 與 IE 版本均有循環資料交換。Classic 的 link scan 與 PLC refresh 都影響速度。選 IE 版本時需分辨 IE Field Basic、IE Field 和 IE TSN。從遠端站變化到主站 RWr／RX，再到 PLC 刷新區的時間。
ModbusTCP 在同一區網讀單一連續點塊時，通常較低速 RTU 更快。若 TCP 之後仍要轉 RTU，多站串行掃描及逾時通常主導更新。同時記錄單次請求往返與全部站點掃描 P95／P99。
BACnetIP／SC 的 COV 可在變化後通知，免等下次輪詢。採輪詢時受排程與批讀影響，MS/TP 還要等 token。數值越過 COV 增量後到 BMS 入庫的時間，並比較批讀的整輪時間。
OPC UA在同一區網，訂閱速度主要看採樣及發布設定。例：100 ms 採樣加 500 ms 發布，兩層等待在理想無積壓時合計可接近 600 ms，另加來源及網路時間。來源變化到訂閱端接收的時間，核對伺服器實際採用的兩個週期。
MQTT同一區網且 Broker 無積壓時，立即發布可比等待固定掃描更早到達。跨站、重送與離線積壓會增加延遲。Publisher 到 Subscriber 的延遲，分開記錄固定發布週期及恢復後補送。
Zigbee電池感測器通常以事件或上報週期更新。即使無線封包很快到達，長上報週期仍會使溫度資料更新較慢。從感測器實際變化到 MQTT 橋接端的新鮮讀值，另記上報間隔與漏報。
EtherNet/IP循環 I/O 以 RPI 配置，Explicit 訊息不等同循環；RPI 不是端到端延遲保證。量 PLC 程式映像更新、最大循環間隔、連線逾時及恢復。
EtherCAT典型 100 Mbit/s 全雙工 EtherCAT 段；線速不是過程資料週期。量物理事件至控制程式／輸出、循環抖動與裝置同步誤差。

上位監控可用同一個來源變化、相同網段與相同點數，比對 Modbus TCP 輪詢、BACnet COV、OPC UA 訂閱與 MQTT 即時發布的端到端 P95／P99。比如 1 秒輪詢單是等待下次輪詢就可能接近 1 秒，COV 或立即發布則在各自條件成立後送出。

通訊速度、安全性與驗收

協定線速、更新與延遲安全能力現場驗收
ModbusRTU 常見 9,600／19,200 bit/s。TCP 使用乙太網路，更新取決於點塊、站數、設備回應與逾時設定。傳統 Modbus TCP／RTU 無原生驗證或加密。支援 Modbus Security 的 TCP 端點可用 TLS 與 X.509 憑證。傳統設備用 OT 分區及存取規則限制讀寫。量測一整輪、單站逾時時的掃描，以及寫入是否被限制。
BACnetMS/TP 常見設備檔位如 38.4／76.8 kbit/s，更新受 token 週期、站數與負載影響。IP／SC 仍要量測實際 COV 或批讀延遲。傳統 BACnet/IP、MS/TP 本身無加密。BACnet/SC 使用 TLS WebSocket 和憑證，跨入傳統 BACnet 分段後依該段的能力保護。確認 Device Instance、COV 續訂、跨網單播與探索、憑證過期，以及重連取回目前值。
OPC UA由伺服器採樣與 publishing interval 決定更新。例：100 ms 採樣、500 ms 發布，另加 PLC 與網路延遲。查 Server 實際接受的參數。正式端點使用 SignAndEncrypt、信任清單及應用憑證，再按使用者角色授權。SecurityPolicy=None 不提供通訊簽章或加密。記錄 SourceTimestamp、狀態碼、訂閱遺漏。檢查不受信任憑證及未授權寫入是否被拒。
MQTT無固定週期。延遲由發布頻率、QoS、Broker 排隊、網路與重連決定。部署 TLS 驗證 Broker，按需啟用 mTLS。由 Broker 實作帳號與 topic ACL；跨 Broker 轉送時逐段驗證。從發布到訂閱端量測延遲，測重複、離線積壓、訊息逾期及沒有授權的 topic。
Zigbee2.4 GHz 原始速率 250 kbit/s。感測點實際更新受上報條件、休眠、多跳與重送影響。使用 AES-128 與金鑰機制。限制加入期間，保護金鑰及協調器，另為橋接 Broker 設 TLS 與 ACL。核對上報間隔、漏報、離線與電量。分開測射頻連線及橋接發布。
PROFINET IO常見 100 Mbit/s 乙太網路。PI 列出的 RT 可配置週期範圍為 250 µs 到 512 ms，實際由控制器與設備共同決定。IRT 依硬體與同步配置驗收。確認控制器、設備與工程工具支援的 PROFINET Security Class 與功能。既有裝置以 OT 分區、限制工程存取、保護交換器埠為主。量測循環更新、抖動、watchdog 與恢復時間。驗證資料狀態 IOPS／IOCS 與診斷。
PROFIBUS DP典型銅纜 DP RS-485 為 9.6 kbit/s 至 12 Mbit/s。主站循環受速率、站數、I/O 長度和重試影響。傳統 DP 無原生加密或裝置鑑別。限制匯流排實體接入及 PLC 工程介面存取。核對線長與終端，量測 Data_Exchange、週期及一站中斷對其他站的影響。
CC-LinkClassic 為 156 kbit/s 至 10 Mbit/s。IE Field Basic 使用 100 Mbit/s 乙太網路，循環需按站數與 CPU 實測。兩者的線速都只是掃描時間的其中一項因素。Classic 無原生加密或裝置鑑別。保護匯流排及工程介面。IE 系列依版本和設備規格確認，使用 OT 網路分區。量測 link scan、CPU refresh、站離線後舊值的品質標示，以及恢復時間。
EtherNet/IP量實際循環、RPI 與 PLC 工作週期。CIP Sync 可提供時鐘同步，但不保證端到端延遲。CIP Security 須端點支援並啟用；依模式或政策核對加密、鑑別及完整性。在正常及負載高時核對更新、逾時、重連和未授權操作是否被拒。
EtherCAT典型 100BASE-TX 段為 100 Mbit/s，全雙工。Distributed Clocks 的同步精度與反應延遲分開。不因使用 Distributed Clocks 或功能安全機制就假定網路加密；限制工程與主站介面。量最長更新間隔、watchdog、資料失效與故障恢復。
20 台 RTU 的輪詢估算。若每台讀取兩個 Holding Register，請求 8 bytes、回應 9 bytes，在 9,600 bit/s、8E1 下，每台光是 17 bytes 的傳輸就約 19.5 ms。20 台合計約 390 ms，還要加幀間靜默、設備處理及例外等待。如果輪詢目標是 1 秒，需實測正常及單站離線情境。

以正常負載、尖峰負載及單站離線三種情境記錄完整掃描週期、端到端 P95／P99、逾時率與恢復時間。對需要確定時限的控制 I/O，另核對規定的最長更新與 watchdog。跨設備量測端到端時間時，先同步並確認時鐘誤差。

安全性與可靠性：依用途選候選

資安問誰能連線、讀寫，及封包能否防竄改或保密；可用性問掉線或故障能否在期限內恢復；確定性問最壞更新間隔；功能安全另須按應用完成合格設計與驗證。四者不能互相替代，以下不是安全分數排名。

延伸閱讀：OT 資安與網路分區。

場景／候選資安前提可靠性驗收
樓控 BMS：BACnet/SC使用 TLS 與可信憑證；舊 BACnet 分段不可視作自動受到保護。若採備用 Hub，驗證兩個故障域、Hub 切換及 COV／資料恢復。
監控／語意資料：OPC UA選用 SignAndEncrypt、信任清單、撤銷流程及細部授權。只在產品支援且配置完成時使用備援；用故障演練驗證 Subscription 重建、品質與資料遺漏。
遙測上送：MQTT驗證 Broker TLS、必要時採 mTLS、限制 topic ACL。核對所需 QoS、會話效期、持久化及 Broker 備援設計。測恢復後重複、補送、過期與積壓；QoS 不保證即時。
遠端／循環 I/O：PROFINET、EtherCAT、EtherNet/IP核對設備安全能力，限制設備及工程介面跨區存取。需要安全通訊時使用受支援的機制和政策。以已支援的 MRP、線路備援或 DLR 配置為例，在隔離測試台或經核准維護窗口模擬單一路徑中斷，驗證恢復、watchdog、輸出狀態與抖動；網路備援不是控制器備援。
既有 Modbus TCP：Modbus Security只在相容雙端啟用 TLS／X.509；不相容端點須隔離／限制存取，不能貼上「已加密」標籤。連線重建後驗證真正讀到新值、整輪延遲與一站故障；不要拿來承諾硬即時控制。

若是急停等安全功能，用合格的控制器、裝置、工程配置與系統驗證；FSoE、PROFIsafe、CIP Safety 處理的是功能安全，不取代網路鑑別、授權或加密。

Modbus TCP：封包、架構與只讀驗收

Modbus TCP 與 RTU 都使用 Modbus 功能碼及暫存器模型，但承載方式不同。1979 年 Modicon 推出 Modbus；2006 年 Modbus Organization 的 TCP/IP 實作指南 V1.0b 記載 MBAP 封裝及網路閘道模式；2018 年 10 月公布獨立的 Modbus Security 選項。2006 是該指南版本日期，不是 TCP 版本的首發年份。

項目Modbus TCPModbus RTU
承載TCP/IP；傳統服務通常使用 TCP 502。線速依網路埠，與上位更新無直接等號。常見 RS-485 多站匯流排；鮑率、同位元與停止位元需一致。
分幀MBAP＋PDU；依 Length 讀完整訊息。一次 TCP read 可能拿到半包或多包。站號＋PDU＋CRC；依序列幀與靜默間隔辨識。
地址IP／埠選端點。Unit ID 無意義時，TCP 指南對直連伺服器建議 0xFF；實際以設備設定為準。透過閘道常用它選下游 RTU 站。站號選擇序列裝置；功能碼和位址選資料區或暫存器。
延遲量單次 request/response、全輪 P95／P99、逾時及恢復；若後接 RTU，要把排隊與串列等待算進去。整輪累加串列傳輸、間隔、設備處理及失聯等待。
安全傳統 TCP 無原生鑑別和加密；Modbus Security 需相容端點、TLS 與 X.509，通常採 TCP 802。傳統 RTU 無原生鑑別或加密；管控匯流排及閘道。TCP 側 TLS 不延伸到 RTU 線路。

FC03：讀 Unit 7 的兩個 Holding Register

示例以 PDU offset 0 起算。面板或手冊可能寫 40001；兩者的對應仍須看原廠。交易識別碼可由 Client 分配，此處固定為 0x002A 方便核對。

請求：00 2A | 00 00 | 00 06 | 07 | 03 00 00 00 02
回應：00 2A | 00 00 | 00 07 | 07 | 03 04 41 B0 00 00
      交易ID  協定ID   長度    單元       PDU

MBAP 長度欄計算「後續位元組」：包含 Unit ID 與 PDU，不含前六個位元組。回應中的 04 是資料的位元組數；依教材指定的高位字在前解讀 41B0 0000 才得到 IEEE 754 的 22.0。傳統 Modbus TCP ADU 不附 RTU CRC。應分別驗證交易 ID、Protocol ID=0、Length、Unit ID、功能碼及例外回應。

  1. 用工程資料確認 Device Instance，例如 420101；物件為 analogInput:1。真正的讀取鍵是裝置位址、物件類型、實例與 property，Device Instance 與 IP 位址是不同欄位。

  3. 支援 COV 的點設 lifetime 並提前續訂，重連後先讀當前值，再重建訂閱。若訂閱失敗，可用受限輪詢作回退；持續評估讀值新鮮度。
  4. BACnet/IP 跨 IP 子網的廣播按拓樸使用 BBMD、FD，跨 BACnet 網路依路由器設定。BACnet/SC 依部署採 Hub 與信任憑證；下例使用 BACnet/IP。
python protocol_lab.py bacnet
# 終端 A
python lab_endpoints.py bacnet
# 終端 B
python read_live.py bacnet 127.0.0.1:47809 --bind 127.0.0.1/32 --instance 1
python read_live.py bacnet 192.0.2.41 --bind 192.0.2.10/24 --instance 1

本機預期讀到 Analog Input 1 的 22.0 °C、攝氏單位與四個 status flags。實機可另加 --bbmd 192.0.2.2:47808 --bbmd-ttl 300 驗證已配置的 Foreign Device 路徑。先確認固定 IP 的單播讀取，接著分開驗證跨網探索與 COV 續訂。

OPC UA 實作

  1. 從 Server 取得 Endpoint 與安全策略。正式驗收用雙端信任的憑證與 SignAndEncrypt；範例支援 Basic256Sha256，落地前核對 Server 實際提供的策略。
  2. 配置 Namespace URI + String Identifier。連線後透過 URI 解析 namespace index，避免把某台 Server 的 ns=2 硬寫成跨 Server 常數。
  3. 讀 DataValue 保留 Variant、StatusCode、SourceTimestamp。離線範例故意產生 Uncertain，確認上層仍帶品質。Bad 不當有效值輸出。
  4. 連續監看使用 Subscription 與 MonitoredItem，分開設定 sampling interval、publishing interval 和 queue size，核對 Server 修訂值，測試斷線恢復與缺值。
python protocol_lab.py opcua
# 終端 A
python lab_endpoints.py opcua
# 終端 B
python read_live.py opcua opc.tcp://127.0.0.1:4840/lab/ urn:example:plant AHU01.SAT --watch 4 --timeout 15
python read_live.py opcua opc.tcp://192.0.2.42:4840 urn:example:plant AHU01.SAT \
  --certificate client.der --private-key client-key.pem --server-certificate server.der

本機 Server 每兩秒輪播三種溫度與 BadNoData。訂閱範例輸出四次通知，保留 quality、UA 狀態碼與 source_timestamp。BadNoData 的值為 null。未指定 --watch 時執行一次 Read。

MQTT 實作

  1. 先訂 topic，例如 site/lab/ahu01/telemetry。定義 schema 版本、點位、單位、品質、值；正式資料再帶 UTC 時間戳與訊息 ID。
  2. 發布端採 QoS 1 可能重複投遞，以 event_id 或來源＋序號做應用層去重。Retained 是快照，Session Expiry 管會話存續，兩者需分別驗收。
  3. 接收範例透過 TLS 等待精確 topic 的一則非 retained 訊息，避免把開機收到的快照當作新點值。驗收 broker 憑證、權限、錯誤 JSON、錯誤單位、逾時與重連。

以 mosquitto -c mosquitto-lab.conf -v 啟動本機 broker。設定檔只在 127.0.0.1 監聽，使用以下兩行。

listener 1883 127.0.0.1
allow_anonymous true
python protocol_lab.py mqtt
# 開另一個終端先訂閱，再從第三個終端發布
python read_live.py mqtt 127.0.0.1 site/lab/ahu01/telemetry --loopback-plaintext --wait 60
mosquitto_pub -h 127.0.0.1 -V mqttv5 -q 1 -t site/lab/ahu01/telemetry \
  -m '{"schema":1,"point":"AHU01.SAT","value":22.0,"unit":"degC","quality":"good"}'
python read_live.py mqtt broker.lab.example site/lab/ahu01/telemetry --ca lab-ca.pem

先送 retained 快照，再啟動讀取程式。在另一個終端發布新訊息後，程式才應輸出 22.0 °C。真正的資料新鮮度仍依來源時間戳與應用 TTL 判定。QoS 1 驗收包含重複訊息，避免歷史資料重複入庫。

Zigbee 實作

  1. 將支援的協調器接到 Zigbee2MQTT；於受管測試網路短暫開啟加入、讓裝置配對、再關閉加入。電池末端裝置可能睡眠，應以主動上報週期判斷是否逾期。
  2. 以裝置 expose 清單確認 temperature。若使用原生 ZCL，Temperature Measurement cluster 0x0402 的 measured value 0x0000 通常是 0.01 °C；本例訂閱 Zigbee2MQTT 的 JSON，值已是 °C。
  3. 映射 friendly name 與設備唯一識別，記下 temperature、availability 及最近上報時間。linkquality 屬無線鏈路指標，無法單靠它判定溫度是否仍有效。
python protocol_lab.py zigbee
# 沿用前段本機 broker，兩個終端分別訂閱與發送橋接測試訊息
python read_live.py zigbee 127.0.0.1 zigbee2mqtt/ahu01-room --loopback-plaintext --wait 60
mosquitto_pub -h 127.0.0.1 -t zigbee2mqtt/ahu01-room -m '{"battery":95}'
mosquitto_pub -h 127.0.0.1 -t zigbee2mqtt/ahu01-room -m '{"temperature":22.0,"battery":95}'
python read_live.py zigbee broker.lab.example zigbee2mqtt/ahu01-room --ca lab-ca.pem --wait 120

預期忽略只有電池欄位的訊息。實機驗收還要核對裝置加入、IEEE 位址、Exposes、實際 report interval 和 zigbee2mqtt/ahu01-room/availability。橋接器若附帶快取溫度，另依裝置上報來源判斷溫度時間。

PROFINET IO 實作

  1. 匯入 IO Device 的 GSDML，依安裝插槽配置 module/submodule。配置設備站名，將 slot 2／subslot 1 的輸入映射到 PLC；該位置是教學用配置。

PROFIBUS DP 實作

  1. 使用支援 DP 的 PLC 主站介面或獨立 Gateway。匯入 GSD、設定實際站號、選擇模組與 I/O 長度，核對 RS-485 物理接線、總線兩端終端與 baud rate 下的線長限制。
  2. 確認站 5 進入 Data_Exchange、無診斷錯誤，將兩個一致的 input bytes 與站狀態交給上層。循環讀 input image；需要參數或診斷資料時核對 DP-V1 能力。
  3. 將 input_offset 定義成站映射區內偏移。測站離線及診斷告警後，不能把上一筆良好值當作當前值。

CC-Link Classic 實作

  1. 確認設備標示為 CC-Link Classic 並匹配主站／遠端站、版本、站號、baud、占用站數與設備手冊。CC-Link IE Field、IE Field Basic、IE TSN 各自依對應規格配置。
  2. 主站視角中，RX／RWr 從遠端讀回，RY／RWw 向遠端送出。於 PLC link refresh 區讀站 1 的 RWr0 與鏈路狀態；實際 RWr 起點、點數及刷新位址以模組參數為準。
  3. rwr0=220 在此快照契約中表示帶符號 0.1 °C。用設備文件確認有號值、比例與遠端診斷，再核對 0xFFCE 是否正確回報 −5.0 °C；link_ok=false 時拒用讀值。
{"station":1,"rwr0":220,"link_ok":true}

PLC 快照格式與故障驗收

PLC 或閘道按一個掃描的狀態建立 [valid, high_byte, low_byte]，其中後兩個 byte 表示有號 16-bit、每單位 0.1 °C。使用一次 OPC UA Read 或 Subscription 取得完整欄位。可用下列對照驗證。

封包預期值品質驗收條件
01 00 DC22.0 °Cgood感測器與站有效，現場顯示一致。
01 FF CE−5.0 °Cgood確認 signed Int16 與 byte order。
00 00 DCnullbad站離線仍留有 22.0 的原始資料，上位監控顯示失效。

Overview

先比角色，不先背欄位

現場最容易出錯的不是記不得 port，而是拿錯心智模型。先知道每個協定站在哪一層，後面才不會把 polling、subscription、routing、broker 混在一起。

Architecture

協定差異本質上是責任邊界差異

同一筆溫度資料，在四個協定中會呈現為 register、NodeId、BACnet object、MQTT payload。比較時要從責任邊界看，不是只看是否可讀寫。

Modbus

Modbus：register-based polling

最常出現在 PLC、meter、VFD 與 RTU/TCP 網段。Python 常扮演 poller、decoder、gateway adapter。

OPC UA

OPC UA：semantic model + subscription

最常出現在 SCADA、MES、historian 與跨系統語意整合。Python 常扮演 client、integration agent、edge translator。

閱讀 OPC UA 深度研究：資訊模型、訂閱復原與憑證

BACnet

BACnet：object model + building automation routing

最常出現在樓宇自控、HVAC、BMS。Python 常扮演 gateway、監控側 integration、資料轉換器，而不是直接替代全部現場控制。

MQTT

MQTT：publish/subscribe uplink

最常出現在 edge uplink、cloud telemetry、event publish。Python 常扮演 publisher、subscriber、payload normalizer 或本地 buffer manager。

閱讀 MQTT 深度研究：QoS、會話、重送與 Broker
