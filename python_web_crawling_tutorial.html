Python 爬蟲教程：從授權擷取到結構化資料

同一個本機 HVAC 測試站，對照 HTML 與 JSON API 的擷取、節流、欄位驗證及交付證據。實驗不允許輸入外部網址。

來源選擇流程圖架構圖robots.txt實驗圖表資料契約與交付程式實作

01｜先決定是否需要爬蟲

爬蟲會發現候選 URL、依範圍挑選後擷取；資料解析則將回應轉成欄位。一支程式可以只做其一。先確認站點管理者或資料授權允許自動存取、使用和保存；公開可見不等於可任意收集。只取必要欄位，不擷取個資，不繞過登入、付費牆或驗證。

資料來源與工程取捨
方式適用條件應注意
正式資料匯出能定期取得合法授權的 CSV 或 JSON。確認發布週期、欄位版本和授權。
正式 API有文件、穩定 ID 與結構化欄位。依配額與分頁規格；不要猜測未公開端點。
授權 HTML沒有受支援 API，且站方允許自動擷取範圍。版面或欄位可能改變，須做測試與異常停機。

02｜擷取流程圖

  1. 1｜讀規則 →先確認授權邊界，再讀來源的 robots.txt；失敗就停止這堂實驗。
  2. 2｜取目錄 →HTML 模式查 5 個連結候選，只接受指定本機頁面。API 模式直接查固定 JSON。
  3. 3｜過濾與擷取 →排除重複、禁止、外部路徑；每個實際 GET 都耗用請求預算。
  4. 4｜解析與輸出驗證內容類型與大小，依 HTML 屬性或 JSON 結構抽欄位，以 ID 去重後出 JSON。

03｜元件架構圖與失敗選擇

  • 本機測試站 →合成溫度、HTML 目錄、資料頁、固定 JSON、robots.txt。只綁 127.0.0.1 的臨時埠。
  • 擷取控制器 →固定白名單，單工；請求間隔至少 150 ms、socket timeout 2 秒、單次最多 16 KiB、整次最多 8 次請求。
  • HTML／JSON 解析 →HTMLParser 不執行 JavaScript；JSON 使用 json.loads；內容類型不符即停止。
  • 結果與驗證摘要保留丟棄原因、可重跑測試；實際部署另需總截止時間、欄位契約、保存期限與變更告警。

收到 429，只在第一次按 Retry-After（秒數或 HTTP 日期）再試一次；無效時用教學預設 1 秒，等待預算 2 秒，若超過預算就停止，不把伺服器要求的等待截短再提早重試。其他非 200、轉址、非預期 MIME 都中止。2 秒是 socket I/O timeout，不等於端到端截止時間；程式不會跟隨任何轉址。

04｜robots.txt 不是授權或存取控制

RFC 9309 定義以來源的根路徑 /robots.txt 提供規則。先比對爬蟲產品代碼的群組（無相符群組時才看 *），再按路徑最具體的規則，等長衝突建議優先 Allow。2xx 時遵循可解析規則；4xx 代表規則不可用，規範允許但不強制可抓取，並不表示站方同意；5xx 或網路無法連到來源時原則上先視為全面禁止。RFC 另有轉址和快取規則。本機實驗更嚴格：任何 robots 載入失敗都停止，不跟轉址；RobotFileParser 僅示範簡單規則，不宣稱完整符合 RFC 9309。

主動擷取前，規則可用、授權範圍與站方的流量限制缺一不可。無授權、疑似個資、站方要求停止或遇到封鎖時，應停機或改採授權匯出。

05｜本機實測計數

HTML 目錄的 5 個候選中，排除重複、robots 禁止與外部各 1 個，留下兩個資料頁。第一筆 25.5°C，第二筆 24.8°C；第二頁先收到一次模擬 429。總 HTTP = robots（1）＋目錄（1）＋兩資料頁（2）＋重試（1）。API 只回傳 AHU-A，因此本例不能將 5 比 2 當作兩種技術的效能結論。

06｜資料契約：保留候選，驗證後才交付

HTTP 200 只說請求成功，不保證回應仍是正確資料。有些來源改版、回代理錯誤頁，或 API 漏欄位，爬蟲仍可能「有回應、零有效結果」。先保留原始候選與來源，再以明確契約驗證；不要用 setdefault() 靜默保留第一筆，掩蓋同一識別碼出現不同數值。

實務契約｜在擷取前就定義判定方式
關卡可接受不符合時
來源與用途站方核准的主機、路徑、欄位、頻率、用途與保存期。無授權、遇登入／驗證、或站方要求停止就停。不要更換身分、走代理或繞過限制。
HTTP 回應只收合約定義的狀態、MIME、大小；已協商時可用 ETag 條件式請求。本機程式遇轉址即停。正式方案若獲准跟隨，下一跳須重新驗證範圍；401／403 不自動重試。
回應內容採明確欄位路徑。HTML 不執行腳本；JSON 不假設所有回應都是陣列。來源換結構、欄位缺漏或解析失敗，加入品質告警，不把空結果當成功。
資料身分與品質同一批次用設備 ID，數值相等可去重；跨批次時間序列另需可信的樣本時間或版本。同 ID 不同值視為衝突，不擅選第一筆；只有擷取時間時，不把它寫成設備端來源時間。
交付與留痕可核對 schema 版本、候選／接受／重複／拒絕數、快照摘要和執行時間。不公布未過閘門的暫存資料；保留最少診斷資訊，避免把原始頁面或祕密寫入日誌。

用 HTTP 降低負載，而不是突破限制

若站方正式支援 ETag，保存上一份已驗證快照及對應 ETag；下次向同一資源送 If-None-Match。收到 304 Not Modified 時重用對應快照，不解析不存在的新資料，也不改原樣本時間。若沒有對應快取，應記錄不一致並依授權採下一次正常重取。本機實驗沒有實作 ETag。

收到 429 Too Many Requests，遵守 Retry-After；等待超過自己的時間預算就暫停，不把對方的等待要求縮短。記同一主機的最小間隔、執行總請求數、總時間與回應大小上限；單次 socket timeout 不等於整批截止時間。正式排程不同工作共用站方配額時需合併管控，不用每個程序各自限速混充全站限制。

用同一批合成資料驗收輸出

AHU-A 的 25.50 與 25.5 是同值；AHU-B 的 24.8 合格；AHU-C 的 NaN 被拒絕。即使有 2 筆合格，這次仍是 release_ready: false，結束碼為 2。指紋只涵蓋排序後的暫存資料，用於復算與比對，不是資料真實性的證明。temperature_c 在輸出中用十進位字串保留契約格式。

report = quality_report(raw_rows)

if not report["release_ready"]:

正式管線提交時以暫存檔或交易寫入完整批次，通過後才切換可見版本。限制後端日誌的欄位與保留時間；採集內容只能當資料，不將其中的 URL、文字或指令交給自動化執行。這套實驗只輸出報告，不寫資料庫、不做遠端擷取或正式發布。

延伸學習：實作、現場案例與自我檢查

本節完全離線，示範一個「好鄰居」爬蟲的三個習慣：先讀 robots.txt、對同一主機限速，以及用 ETag 條件請求避免重複下載沒有變更的頁面。

可實跑範例：robots.txt、速率限制與條件請求快取

用 urllib.robotparser 解析一份內嵌的 robots.txt，針對特定 User-Agent 判斷能否擷取；用模擬時鐘實作 Crawl-delay；FakeServer 在 ETag 相同時回 304，統計可省下多少傳輸量。

下載範例 example.py

"""離線示範：robots.txt 判讀、每主機速率限制、ETag 條件請求快取（標準函式庫）。"""
import urllib.robotparser

ROBOTS = """
User-agent: *
Disallow: /admin/
Disallow: /search
Crawl-delay: 5

User-agent: bms-report-bot
Allow: /public/energy/
Disallow: /
Crawl-delay: 10
""".splitlines()

UA = "bms-report-bot"


class FakeServer:
    """模擬伺服器：資料沒變時回 304，並統計傳輸位元組。"""
    def __init__(self):
        self.version = 1
        self.bytes_sent = 0

    def get(self, path, if_none_match=None):
        etag = f'"v{self.version}"'
        if if_none_match == etag:
            self.bytes_sent += 120                       # 只有標頭
            return 304, etag, None
        body = f"<table><tr><td>{path}</td><td>{self.version * 1000} kWh</td></tr></table>"
        self.bytes_sent += 120 + 48_000                  # 假設完整頁面約 48 KB
        return 200, etag, body


class Crawler:
    def __init__(self, robots_lines, server):
        self.rp = urllib.robotparser.RobotFileParser()
        self.rp.parse(robots_lines)
        self.server = server
        self.cache: dict[str, tuple[str, str]] = {}
        self.clock = 0.0                                  # 模擬時鐘（秒）
        self.next_allowed = 0.0

    def fetch(self, path):
        if not self.rp.can_fetch(UA, path):
            return f"{path}: robots.txt 不允許，跳過"
        delay = self.rp.crawl_delay(UA) or 1
        if self.clock < self.next_allowed:
            self.clock = self.next_allowed                # 等到允許的時間
        self.next_allowed = self.clock + delay
        etag = self.cache.get(path, (None, None))[0]
        status, new_etag, body = self.server.get(path, etag)
        if status == 200:
            self.cache[path] = (new_etag, body)
        return f"t={self.clock:>4.0f}s {path}: {status}{'（沿用快取）' if status == 304 else ''}"


if __name__ == "__main__":
    srv = FakeServer()
    c = Crawler(ROBOTS, srv)
    for p in ["/public/energy/2026-11", "/public/energy/2026-11", "/admin/users",
              "/public/energy/2026-10", "/search?q=kwh"]:
        print(c.fetch(p))
    srv.version = 2                                       # 伺服器資料更新
    print(c.fetch("/public/energy/2026-11"))
    print(f"總傳輸量約 {srv.bytes_sent / 1000:.1f} KB；若每次都完整下載約 {4 * 48.12:.1f} KB")
    print("請求時建議帶 User-Agent 與聯絡方式，例如：", f"{UA}/1.0 (+mailto:ops@example.com)")

執行方式：python example.py，只需 Python 3.10 以上，無第三方套件；不會連線到任何網站

工程現場案例：每天抓公開能源資料，被對方封鎖 IP

某整合商每天從公用事業網站抓公開的月用電統計，程式每次都重新下載所有歷史月份，也沒有限速。對方網站把這種流量視為異常並封鎖了來源 IP，導致整批報表中斷。

改成條件請求後，未變更的月份只回 304，範例中傳輸量從 192.5 KB 降到 144.5 KB；在真實情境中，歷史月份幾乎不變，節省比例會更高。再加上 User-Agent 聯絡資訊與固定間隔，對方也能在有疑慮時聯絡，而不是直接封鎖。

  1. 先確認資料是否有官方 API 或開放資料下載，有就不要爬網頁。
  2. 每次執行先讀 robots.txt，並遵守對方的使用條款；robots.txt 允許不等於授權。
  3. 保存每個 URL 的 ETag／Last-Modified，下次帶 If-None-Match／If-Modified-Since。
  4. 設定每主機的請求間隔與每日上限，User-Agent 帶聯絡方式。

練習題與自我檢查

  1. 把 bms-report-bot 群組的 Allow 與 Disallow 兩行對調（Disallow: / 在前），/public/energy/2026-11 還能擷取嗎？請分別用 Python 3.12 與 3.13 以上驗證。

    看解答

    Python 3.13 以上（實測 3.13.18）依 RFC 9309 採最長匹配，Allow: /public/energy/ 比 Disallow: / 更具體，判定允許。Python 3.12.13 依出現順序先遇到 Disallow: /，判定不允許。撰寫 robots.txt 時把較具體的 Allow 放在前面，兩種實作的結果才會一致；爬蟲程式也應在部署環境實測，不要假設行為。

  2. 為什麼 /admin/users 被拒絕，即使 * 群組也寫了 Disallow: /admin/？

    看解答

    爬蟲只採用最符合自己 User-Agent 的那一組規則。bms-report-bot 有專屬群組，所以 * 群組的規則不適用；被拒絕是因為專屬群組的 Disallow: /。

  3. 伺服器沒有提供 ETag，只有 Last-Modified，Crawler 要怎麼改？

    看解答

    快取改存 Last-Modified 的值，請求時帶 If-Modified-Since。注意 Last-Modified 只有秒級精度，同一秒內多次更新可能漏判；若頁面很重要，可再比對內容雜湊。

  4. 若一天要抓 2,000 個頁面、Crawl-delay 為 10 秒，至少需要多少時間？可以開多執行緒加速嗎？

    看解答

    2,000 × 10 = 20,000 秒，約 5.6 小時。對同一主機開多執行緒會違反對方的速率要求，不應該這樣做。應減少需要抓的頁面（條件請求、增量抓取），或洽詢對方是否提供批次下載。
