工業乙太網路：100M 與 1GbE 速度計算

比較埠速率、單個 frame 的傳送時間、有效吞吐與 PLC 回應時間。本文將「1000g」理解為常見的 1000 Mb/s（1 Gb/s、1GbE），不是 1000 Gb/s。所有數值為離線算式，不是現場量測。

架構圖｜快的上游埠不會改變慢的下游埠

若端點是 TCP→RS-485 閘道：另加閘道內部排隊、序列請求與回覆傳送、幀間隔、下游裝置處理、逾時與重試。TCP 接通不等於已拿到新鮮點值。

100BASE‑TX（例）是 100 Mb/s，1000BASE‑T（例）是 1,000 Mb/s。這裡是十進位 nominal MAC bit rate，100 Mb/s ÷ 8＝12.5 MB/s，1 Gb/s ÷ 8＝125 MB/s，尚未扣任何開銷。模型是點對點、全雙工、單方向；不把雙向相加當成單方向速度，也不另扣 PHY 實體編碼倍率。

先分清楚四個數：MAC 長度、序列化時間、佔用時間、有效吞吐

未加 VLAN 標籤的標準 Ethernet II frame：14 bytes MAC 標頭（6＋6＋2）、46 至 1500 bytes data/padding、4 bytes FCS。從目的 MAC 到 FCS 共 64–1518 bytes。標準 1500-byte Ethernet data 並非應用 payload；加一層 802.1Q 標籤時，最大標準 frame 常為 1522 bytes，且須區分介面實際設定、抓取器是否保留標籤／FCS、以及是否有 jumbo frame。

從前導到 FCS 傳完：tserialize（µs）＝ 8 × (MAC bytes ＋ 8) ÷ R（Mb/s）

連續同向發送的週期預算：tcycle（µs）＝ 8 × (MAC bytes ＋ 8 ＋ 12) ÷ R（Mb/s）

IFG 是 frame 之間的空檔，不是 12 個資料 bytes，也不算在 64/1518 bytes 內。本章使用標準的 96-bit-time 估算，不把 PHY 端實作、某些接收端可見的間隔變化或前面封包的排隊當定值。孤立單個 frame 的傳畢時間不把後面的 IFG 加進去；多筆連續 frame 的吞吐預算才使用含 IFG 的週期。

最小 64 bytes frame 每個佔 672 bit-times，理想每秒約 148,810（100M）或 1,488,095（1GbE）frames；這不是 PLC 每秒可讀的點數。

理想有效吞吐（Mb/s）＝ 埠速率 × 有效應用 bytes ÷ (MAC frame bytes + 20)

以下固定 IP MTU 1500、IPv4 無選項、TCP 無選項。每個 frame 都滿載時，TCP data 是 1500 − 20 − 20＝1460 B；UDP data 是 1500 − 20 − 8＝1472 B。未扣應用協定、加密封裝、小封包、ACK 策略、TCP 流量／壅塞控制和重傳，故只能當作單方向分子／分母的理想上限，不能拿去承諾傳輸速度。

合成往返時間：請求 MAC frame 100 B、回覆 120 B；兩段 store-and-forward，PLC／主機合計 2,400 µs，另假設交換處理 6 µs、傳播 4 µs、排隊 50 µs（均為整筆往返總和）。各段獨立串列化，無額外 ACK／重試，交換延遲參數不重複包含序列化。混速時序列化合計 20.768 µs，總計 2.480768 ms；兩段皆 1GbE 時為 2.463776 ms，只差 16.992 µs。真實排隊/處理也會隨負載變，不可從此例推斷現場保證或最壞值。

"""Offline bandwidth and application-response arithmetic; never opens a socket."""

import argparse
import json
import math
import unittest


def bits_time_us(octets: int, rate_mbps: float) -> float:
    if octets < 0 or not math.isfinite(rate_mbps) or rate_mbps <= 0:
        raise ValueError("位元組數不可為負，速率須為正的有限值")
    return 8 * octets / rate_mbps


def frame_model(frame_bytes: int, rate_mbps: float, useful_bytes: int = 0) -> dict:
    """Untagged Ethernet II, standard frame size; MAC frame includes FCS."""
    if not 64 <= frame_bytes <= 1518:
        raise ValueError("本模型僅接受 64–1518 bytes 的未加標籤 MAC frame")
    if not 0 <= useful_bytes <= frame_bytes - 18:
        raise ValueError("有效資料不能超過 MAC data/padding 區域")
    occupied_bytes = frame_bytes + 8 + 12
    return {
        "frame_bytes": frame_bytes,
        "rate_mbps": rate_mbps,
        "serialize_us": bits_time_us(frame_bytes + 8, rate_mbps),
        "busy_cycle_us": bits_time_us(occupied_bytes, rate_mbps),
        "frames_per_second": rate_mbps * 1_000_000 / (8 * occupied_bytes),
        "one_way_goodput_ceiling_mbps": rate_mbps * useful_bytes / occupied_bytes,
    }


def rtt_model(rates: tuple[float, ...], request: int, response: int,
              endpoint_us: float, switching_us: float,
              propagation_us: float, queue_us: float) -> dict:
    """Serial store-and-forward path; non-serialization inputs are round totals."""
    if not rates or any(not math.isfinite(x) or x < 0 for x in
                        (endpoint_us, switching_us, propagation_us, queue_us)):
        raise ValueError("至少一段鏈路，各項延遲須為非負有限值")
    tx_us = sum(frame_model(n, rate)["serialize_us"]
                for rate in rates for n in (request, response))
    totals = dict(serialization_us=tx_us, endpoint_us=endpoint_us,
                  switching_us=switching_us, propagation_us=propagation_us,
                  queue_us=queue_us)
    return {**totals, "application_response_us": sum(totals.values())}


def example() -> dict:
    return {
        "min_frame": [frame_model(64, r) for r in (100, 1000)],
        "full_ipv4_tcp_data": [frame_model(1518, r, 1460) for r in (100, 1000)],
        "full_ipv4_udp_data": [frame_model(1518, r, 1472) for r in (100, 1000)],
        "mixed_link_rtt": rtt_model((1000, 100), 100, 120, 2400, 6, 4, 50),
        "all_gigabit_rtt": rtt_model((1000, 1000), 100, 120, 2400, 6, 4, 50),
    }


class BudgetTest(unittest.TestCase):
    def test_minimum_and_full_frames(self):
        for n, r, expect in ((64, 100, 6.72), (64, 1000, 0.672),
                             (1518, 100, 123.04), (1518, 1000, 12.304)):
            with self.subTest(frame=n, rate=r):
                self.assertAlmostEqual(frame_model(n, r)["busy_cycle_us"], expect)

    def test_payload_and_gap_accounting(self):
        v = frame_model(1518, 1000, 1460)
        self.assertAlmostEqual(v["serialize_us"], 12.208)
        self.assertAlmostEqual(v["one_way_goodput_ceiling_mbps"], 1000 * 1460 / 1538)
        self.assertAlmostEqual(frame_model(64, 100)["frames_per_second"], 100_000_000 / 672)

    def test_mixed_rate_rtt(self):
        e = example()
        self.assertAlmostEqual(e["mixed_link_rtt"]["serialization_us"], 20.768)
        self.assertAlmostEqual(e["mixed_link_rtt"]["application_response_us"], 2480.768)
        self.assertAlmostEqual(e["all_gigabit_rtt"]["application_response_us"], 2463.776)

    def test_validation(self):
        for args in ((63, 100), (1519, 100), (64, 0), (64, float("nan")), (64, 100, 47)):
            with self.assertRaises(ValueError):
                frame_model(*args)
        with self.assertRaises(ValueError):
            rtt_model((), 100, 120, 0, 0, 0, 0)


def main() -> None:
    p = argparse.ArgumentParser(description=__doc__)
    p.add_argument("--test", action="store_true")
    args = p.parse_args()
    if args.test:
        unittest.main(argv=["lab"])
    else:
        print(json.dumps(example(), ensure_ascii=False, indent=2, allow_nan=False))


if __name__ == "__main__":
    main()

可實跑範例：Modbus TCP 交易時間預算

依 Modbus TCP 的 MBAP、TCP/IP 與乙太網路開銷計算請求與回應幀大小，再分別計算 100 Mbps 與 1 Gbps 的序列化時間，加上交換器轉送與設備回應時間（皆為假設值），觀察各段所占比例。

下載範例 example.py

"""Modbus TCP 輪詢時間預算：100 Mbps 與 1 Gbps 的差異在哪裡（標準函式庫）。

一次交易 = 請求在線上的序列化時間 + 交換器轉送 + 設備處理時間 + 回應序列化時間。
乙太網路每幀還有前導碼／SFD 8 bytes 與幀間隙 12 bytes，最小幀 64 bytes（含 FCS）。
"""
ETH_OVERHEAD = 14 + 4            # MAC 標頭＋FCS
WIRE_EXTRA = 8 + 12              # 前導碼/SFD＋幀間隙
IP_TCP = 20 + 20
MBAP = 7


def frame_bytes(pdu_len):
    payload = IP_TCP + MBAP + pdu_len
    frame = max(64, payload + ETH_OVERHEAD)
    return frame, frame + WIRE_EXTRA


def serialization_us(wire_bytes, mbps):
    return wire_bytes * 8 / mbps


if __name__ == "__main__":
    req_pdu = 5                                  # FC03：功能碼 1＋起始位址 2＋數量 2
    for regs in (10, 125):
        resp_pdu = 2 + regs * 2                  # 功能碼＋位元組數＋資料
        rq, rq_wire = frame_bytes(req_pdu)
        rs, rs_wire = frame_bytes(resp_pdu)
        print(f"讀 {regs} 個暫存器：請求幀 {rq} B，回應幀 {rs} B（線上另加 20 B）")
        for mbps in (100, 1000):
            wire = serialization_us(rq_wire, mbps) + serialization_us(rs_wire, mbps)
            switch = 2 * 2 * 5.0 if mbps == 100 else 2 * 2 * 1.0   # 兩台交換器、來回，假設轉送延遲
            device = 4000.0                       # 假設設備回應 4 ms
            total = wire + switch + device
            print(f"  {mbps:>4} Mbps：線上 {wire:6.2f} µs＋交換器 {switch:4.1f} µs＋設備 {device:.0f} µs"
                  f" = {total / 1000:.3f} ms（線上時間占 {wire / total:.2%}）")
    devices, per_tx_ms = 60, 4.03
    print(f"\n{devices} 台電表依序輪詢、每台一次交易約 {per_tx_ms} ms：一輪 {devices * per_tx_ms / 1000:.2f} s")
    print("升級 1 Gbps 幾乎不改變這個數字；要縮短輪詢週期，應合併讀取範圍、平行連線或減少點數。")

工程現場案例：電表輪詢一輪要 3 秒，升級 Gigabit 交換器沒有改善

某大樓 60 台多功能電表以 Modbus TCP 輪詢，每台讀 5 個區塊，一輪約 3 秒，無法滿足 1 秒更新的需量控制。業主把交換器全換成 Gigabit，結果幾乎沒變。範例顯示，設備回應 4 ms 時線上時間只占 0.4%，交換器速度不是瓶頸。

實際改善方式是：把分散的 5 個區塊依點位表重新排列成 1～2 次連續讀取（單次最多 125 個暫存器）、對不同電表開平行連線，並把不需要每秒更新的點（電能累計、諧波）改成較慢的輪詢群組。調整後一輪降到 0.6 秒。

  1. 用封包擷取或閘道器日誌量測每台設備的實際回應時間，而不是假設。
  2. 統計每台設備每輪的交易數，合併相鄰位址的讀取。
  3. 確認設備允許的同時連線數，再決定平行輪詢的程度。
  4. 依控制需求把點位分成快速與慢速群組，各自設定輪詢週期。

練習題與自我檢查

  1. 讀 10 個暫存器的回應幀為什麼是 87 bytes？請拆解。

    看解答

    PDU：功能碼 1＋位元組數 1＋資料 20 = 22；MBAP 7；TCP 20；IP 20；乙太網路標頭 14；FCS 4。合計 22 + 7 + 20 + 20 + 14 + 4 = 87 bytes。

  2. 若設備回應時間是 50 µs（例如高速 I/O 模組），1 Gbps 相對 100 Mbps 能省多少比例？

    看解答

    把 device 改成 50 後重新計算：100 Mbps 約 15.8 + 20 + 50 = 85.8 µs，1 Gbps 約 1.6 + 4 + 50 = 55.6 µs，縮短約 35%。設備越快，網路速度的影響越明顯。

  3. 請求幀計算出 70 bytes，為什麼程式裡還有 max(64, …)？

    看解答

    乙太網路規定最小幀長為 64 bytes（含 FCS），不足時要補零。Modbus TCP 請求剛好超過，但像 ARP 或很短的封包就會被補到 64 bytes。

  4. 把 60 台電表改成每台開一條連線、同時輪詢 10 台，一輪時間大約是多少？

    看解答

    理想情況下 60 ÷ 10 = 6 批，每批約 4.03 ms，一輪約 24 ms 加上排程開銷。實際上會受閘道器處理能力、設備同時連線上限與 RS-485 後端（若是 TCP 轉 RTU 閘道器，後端仍是序列匯流排）限制。

  5. 案例中一輪量到約 3 秒，但依範例的交易預算，60 台 × 每台 5 次 × 4.03 ms 只有 1.21 s。每筆交易實際花多少時間？合併成每台 2 次、再分 2 組並行後，一輪大約多久？

    看解答

    3 s ÷ 300 次 = 10 ms／筆，比預算多約 6 ms。這段多出來的時間不在線路上（1 Gbps 只省 0.03 ms），常見來源是輪詢程式在交易之間的固定等待、每次輪詢都重建 TCP 連線，或閘道內部排隊；要用封包時間戳或閘道日誌確認。

    若每筆仍約 10 ms：60 × 2 = 120 次 × 10 ms = 1.2 s，分 2 組並行約 0.6 s，正好對應案例調整後的結果。若先把每筆時間壓回 4.03 ms，同樣 120 次依序輪詢只要約 0.48 s，連平行都不需要；排程問題沒解決前，平行連線只是在掩蓋它。
