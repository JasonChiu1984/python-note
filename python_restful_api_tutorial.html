01｜從資源開始，不從 RPC 動詞開始

/v1/devices 是集合，/v1/devices/ahu-01 是單一資源。JSON 只是表示形式，REST 不是「用 JSON 傳輸」的同義詞。先定義資源名稱、可操作的表示、狀態碼、快取和授權，再選框架；無狀態指每個請求自帶處理所需的資訊，不是不能使用資料庫。

方法安全／冪等用途與容易搞錯的地方
GET是／是讀取資源；不能把應用寫入放進 GET。可另行設計 If-None-Match 與 304；本實驗未實作條件讀取。
POST否／否（預設）建立設備，成功回 201 與 Location。逾時後不能假設失敗；本實驗用呼叫者給的設備 ID 查回，沒有提供冪等鍵機制。
PUT否／是取代可編輯表示，不是只覆蓋 JSON 裡出現的欄位。重送可能收到不同狀態碼，如條件失效回 412；冪等描述效果，不保證回應相同。本 API 只更新既有設備。
PATCH否／由契約決定部分修改；例如設定值和遞增計數，重送效果不同。實作時須先決定媒體型別與 null 的語意，不能把任意 JSON 都當同一種 PATCH。
DELETE否／是同一目標多次刪除，最終狀態仍是不存在；首次可為 204、之後為 404。204 不附內容。

02｜設備清冊 API 契約

請求成功應驗收的失敗
GET /v1/devices?limit=2&after=ahu-02200、items、next_after422 超出 1–50 筆或游標格式錯。依 ID 以 > after 讀取；插入發生在游標之前時，後續頁不會看見它。不是跨頁一致快照。
POST /v1/devices201，Location 指向新資源409 ID 已存在；超時後用 ID 讀回並核對欄位，不能把所有 409 當作此次成功。
GET /v1/devices/ahu-01200、版本 ETag404 不存在；單筆 GET 設 Cache-Control: no-store，此處 ETag 用於後續寫入。
PUT /v1/devices/ahu-01200、新表示428 缺前置條件；400 版本標籤不符本 API 約定；412 版本已變；422 欄位不符契約。

本實驗的 If-Match 要求單一強標籤 "1"，不接受弱標籤、* 或清單。HTTP 支援 * 與標籤清單，但本實驗要求一個欄位行和一個標籤：逗號清單與重複的 If-Match 欄位行（即使內容相同）都回 400，不會更新設備。PUT 請求包含可編輯欄位，伺服器加入 id、revision 並會去除名稱頭尾空白，所以成功回應不附 ETag；需要新標籤時再 GET。

錯誤用 application/problem+json，提供 type/title/status/detail。客戶端看 HTTP 狀態與文件約定，不要剖析人讀用的 detail。本實驗不提供 instance；正式服務若要指出這次錯誤的唯一 URI，才填此欄位，或另外用 request ID 串接紀錄。

05｜工業場景：REST 到哪一層就該停？




監看與現場控制分開
設備／PLC → 閘道採集 → 快照或歷史儲存 → REST API → HMI／工務看板。清冊裡的 enabled 是資料欄位，不代表遠端啟停。即時控制、保護和聯鎖仍交給適當的現場控制器。


資料正確不等於資料新鮮
正式量測表示至少分開來源時間、收到時間、單位、品質與逾期門檻。清冊版本不是量測版本；裝置離線的最後值不能當成現在值。低頻讀快照用 REST，連續推送再評估 SSE、WebSocket 或 MQTT。


版本比對需跟著資料走
此例只示範單一程序內的鎖。多 worker 或多主機要用持久化儲存，把版本檢查和更新放同一筆交易，例如 UPDATE … WHERE id = ? AND revision = ?，再依受影響列數判斷結果。持久化版本必須避免資源重建後重複使用同一標籤。


驗收要涵蓋拒絕和未知結果
新增 TLS、身分驗證、逐資源授權、速率限制、輸入大小限制及稽核。401 是需驗證並帶適用的挑戰，403 是無權限；429 可搭配 Retry-After。不要在通用客戶端無條件重試寫入；每次逾時都須區分是否可能已提交。

延伸學習：實作、現場案例與自我檢查
前面各節從伺服器端定義契約。本節換到用戶端：BAS 整合程式呼叫別人的 API 時，怎麼處理分頁、限流與維護中的回應，以及哪些請求絕對不能自動重試。
可實跑範例：分頁讀取與 Retry-After 退避
程式在本機啟動一個模擬設備清冊 API，第 2、3 次呼叫分別回 429 與 503。用戶端依 Retry-After 退避後重試 GET，最後讀完 11 台設備；POST 收到 503 則直接回報，不自動重送。等待時間只記錄不實際等待，讓輸出可重現。
下載範例 example.py
"""REST 用戶端：分頁讀取、429／503 依 Retry-After 退避、非冪等請求不自動重試（標準函式庫）。

程式在本機啟動一個模擬設備清冊 API（127.0.0.1 隨機埠），用 urllib 呼叫它。
等待時間記錄下來而不是真的 sleep，讓輸出可重現。
"""
import json
import threading
import urllib.error
import urllib.request
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qs, urlparse

DEVICES = [{"id": f"AHU-{i:02d}", "status": "running" if i % 4 else "alarm"} for i in range(1, 12)]
STATE = {"calls": 0}


class Api(BaseHTTPRequestHandler):
    def log_message(self, *args):          # 不把存取紀錄印到輸出
        pass

    def _json(self, code, body, headers=()):
        data = json.dumps(body).encode()
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        for k, v in headers:
            self.send_header(k, v)
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        STATE["calls"] += 1
        if STATE["calls"] in (2, 3):        # 第 2、3 次呼叫模擬限流與維護
            code = 429 if STATE["calls"] == 2 else 503
            return self._json(code, {"error": "busy"}, [("Retry-After", "2")])
        q = parse_qs(urlparse(self.path).query)
        offset, limit = int(q.get("offset", ["0"])[0]), int(q.get("limit", ["5"])[0])
        page = DEVICES[offset:offset + limit]
        nxt = offset + limit if offset + limit < len(DEVICES) else None
        self._json(200, {"items": page, "next_offset": nxt})

    def do_POST(self):
        self._json(503, {"error": "maintenance"}, [("Retry-After", "5")])


def request(method, url, body=None, *, waits, max_attempts=4):
    idempotent = method in ("GET", "HEAD", "PUT", "DELETE")
    for attempt in range(1, max_attempts + 1):
        req = urllib.request.Request(url, method=method,
                                     data=None if body is None else json.dumps(body).encode(),
                                     headers={"Content-Type": "application/json"})
        try:
            with urllib.request.urlopen(req, timeout=5) as resp:
                return json.load(resp)
        except urllib.error.HTTPError as e:
            if e.code not in (429, 503) or not idempotent or attempt == max_attempts:
                raise
            delay = int(e.headers.get("Retry-After", "1"))      # 也可能是 HTTP 日期，這裡簡化
            delay = min(delay * attempt, 30)                     # 退避上限
            waits.append((e.code, delay))


if __name__ == "__main__":
    server = ThreadingHTTPServer(("127.0.0.1", 0), Api)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    base = f"http://127.0.0.1:{server.server_address[1]}/devices"

    waits, items, offset = [], [], 0
    while offset is not None:
        page = request("GET", f"{base}?offset={offset}&limit=5", waits=waits)
        items += page["items"]
        offset = page["next_offset"]
    print(f"共讀到 {len(items)} 台設備，告警中：{[d['id'] for d in items if d['status'] == 'alarm']}")
    print(f"重試紀錄（狀態碼, 等待秒數）：{waits}")
    print(f"伺服器實際收到 GET 次數：{STATE['calls']}")

    try:
        request("POST", base, {"id": "AHU-12"}, waits=waits)
    except urllib.error.HTTPError as e:
        print(f"POST 收到 {e.code}，Retry-After={e.headers['Retry-After']}；非冪等請求不自動重試，交由使用者確認")
    server.shutdown()

執行方式：python example.py，只需 Python 3.10 以上，無第三方套件；會暫時佔用一個本機埠
預期輸出（以 Python 3.13 實際執行產生）

工程現場案例：能源平台 API 限流，夜間報表少了一半設備
某專案每晚從雲端能源平台 API 抓所有電表資料產生日報。平台改版後加了每分鐘請求上限，超過時回 429 與 Retry-After。原本的程式遇到非 200 就跳過該頁，於是報表靜悄悄地少了一半電表，持續兩週才被發現。
修正方式是把錯誤分成三類：可重試（429、503、連線逾時）依 Retry-After 退避；不可重試（400、401、404）立即失敗並告警；結果不明（POST 逾時）不自動重送，改用查詢確認是否已建立。最後再比對抓到的筆數與清冊總數，不一致就讓排程失敗。
  1. 列出整合會用到的每個端點與方法，標註是否冪等（GET、PUT、DELETE 是；POST、PATCH 預設不是）。
  2. 設定重試次數上限與單次等待上限，避免伺服器回很大的 Retry-After 讓排程卡住。
  3. 寫入類請求帶冪等鍵（例如 Idempotency-Key 標頭或用戶端產生的 ID），讓伺服器能辨識重送。
  4. 排程結束前驗證完整性：筆數、最後時間戳、各分頁是否都成功，任何一項不符就回非零結束碼。
版本與法規更新（核對日期 2026-11-28）
  • 錯誤回應格式建議採 RFC 9457 Problem Details（application/problem+json），它在 2023 年取代 RFC 7807，欄位包含 type、title、status、detail、instance。用戶端應先依 HTTP 狀態碼判斷，再讀 detail 給人看。 來源：RFC 9457
  • 冪等方法的定義以 RFC 9110 第 9.2.2 節為準：PUT、DELETE 與安全方法（GET、HEAD、OPTIONS、TRACE）是冪等的。本頁核對時 FastAPI 最新版為 0.165.0、httpx 為 0.29.0。 來源：RFC 9110 §9.2.2 來源：PyPI：fastapi
練習題與自我檢查
  1. 範例的 GET 被呼叫了 5 次，但只有 3 頁資料。多出來的 2 次是哪裡來的？
    看解答
    第 2 次呼叫收到 429、第 3 次收到 503，都是同一頁（offset=5）的重試。成功的是第 1、4、5 次，分別取得 offset 0、5、10 三頁。
  2. Retry-After 也可以是 HTTP 日期（例如 Wed, 25 Nov 2026 08:00:00 GMT）。範例的 int() 會怎樣？要怎麼改？
    看解答
    int() 會丟出 ValueError。可以先嘗試轉整數，失敗時用 email.utils.parsedate_to_datetime() 解析日期，再減去現在時間得到秒數，最後套用上限。
  3. 為什麼 POST 收到 503 不應自動重試？什麼條件下可以？
    看解答
    POST 不是冪等的，伺服器可能已經處理但回應失敗，重送會建立重複資料。若 API 支援冪等鍵，用戶端每次重送都帶同一個鍵，伺服器就能辨識並回傳第一次的結果，這時才可以安全重試。
  4. 把 request() 的 max_attempts 改成 2，執行結果會變成什麼？
    看解答
    offset=5 那頁第一次收到 429，重試一次又收到 503，已達上限，HTTPError 會向外拋出，程式在分頁迴圈中中止。這正是希望的行為：與其產生不完整的報表，不如明確失敗。
