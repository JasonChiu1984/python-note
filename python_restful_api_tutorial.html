RESTful API：把設備狀態變成可驗收的 HTTP 契約

用一份虛擬設備清冊回答三個工程問題：哪些事是讀取、哪些事會寫入？網路逾時後能不能重送？兩個人同時編輯，怎麼避免後送出的請求蓋掉先前修改？

操作並行更新流程執行本機實驗FastAPI 主教程

01｜從資源開始，不從 RPC 動詞開始

/v1/devices 是集合，/v1/devices/ahu-01 是單一資源。JSON 只是表示形式，REST 不是「用 JSON 傳輸」的同義詞。先定義資源名稱、可操作的表示、狀態碼、快取和授權，再選框架；無狀態指每個請求自帶處理所需的資訊，不是不能使用資料庫。

方法安全／冪等用途與容易搞錯的地方
GET是／是讀取資源；不能把應用寫入放進 GET。可另行設計 If-None-Match 與 304；本實驗未實作條件讀取。
POST否／否（預設）建立設備，成功回 201 與 Location。逾時後不能假設失敗；本實驗用呼叫者給的設備 ID 查回，沒有提供冪等鍵機制。
PUT否／是取代可編輯表示，不是只覆蓋 JSON 裡出現的欄位。重送可能收到不同狀態碼，如條件失效回 412；冪等描述效果，不保證回應相同。本 API 只更新既有設備。
PATCH否／由契約決定部分修改；例如設定值和遞增計數，重送效果不同。實作時須先決定媒體型別與 null 的語意，不能把任意 JSON 都當同一種 PATCH。
DELETE否／是同一目標多次刪除，最終狀態仍是不存在；首次可為 204、之後為 404。204 不附內容。

02｜設備清冊 API 契約

請求成功應驗收的失敗
GET /v1/devices?limit=2&after=ahu-02200、items、next_after422 超出 1–50 筆或游標格式錯。依 ID 以 > after 讀取；插入發生在游標之前時，後續頁不會看見它。不是跨頁一致快照。
POST /v1/devices201，Location 指向新資源409 ID 已存在；超時後用 ID 讀回並核對欄位，不能把所有 409 當作此次成功。
GET /v1/devices/ahu-01200、版本 ETag404 不存在；單筆 GET 設 Cache-Control: no-store，此處 ETag 用於後續寫入。
PUT /v1/devices/ahu-01200、新表示428 缺前置條件；400 版本標籤不符本 API 約定；412 版本已變；422 欄位不符契約。

本實驗的 If-Match 要求單一強標籤 "1"，不接受弱標籤、* 或清單；後兩者是 HTTP 支援的形式，這裡是刻意更窄的 API 政策。PUT 請求包含可編輯欄位，伺服器加入 id、revision 並會去除名稱頭尾空白，所以成功回應不附 ETag；需要新標籤時再 GET。

錯誤用 application/problem+json，提供 type/title/status/detail。客戶端看 HTTP 狀態與文件約定，不要剖析人讀用的 detail。本實驗不提供 instance；正式服務若要指出這次錯誤的唯一 URI，才填此欄位，或另外用 request ID 串接紀錄。

04｜本機啟動、手動請求、測試重跑


下載 服務程式 和 契約測試 到同一目錄。先啟動虛擬環境再安裝；只綁定本機，重啟會清空資料，本練習不是生產服務。


python -m venv .venv
# macOS/Linux: source .venv/bin/activate
# PowerShell: .venv\Scripts\Activate.ps1
python -m pip install "fastapi==0.141.1" "uvicorn==0.52.1" "httpx2==2.16.2"
python -m unittest -v test_restful_api_lab
python -m uvicorn python_restful_api_lab:app --host 127.0.0.1 --port 8000


另開終端機貼下列請求（macOS/Linux Bash）。若不是全新程序，請用 GET 讀目前的標籤，不要照填 "1"。在服務執行時也可開啟 http://127.0.0.1:8000/docs 查看 OpenAPI。


base=http://127.0.0.1:8000
curl -i -H 'Content-Type: application/json' \
  -d '{"id":"ahu-01","name":"AHU primary","enabled":true}' "$base/v1/devices"
curl -i "$base/v1/devices/ahu-01"
curl -i -X PUT -H 'Content-Type: application/json' -H 'If-Match: "1"' \
  -d '{"name":"AHU standby","enabled":false}' "$base/v1/devices/ahu-01"
curl -i -X PUT -H 'Content-Type: application/json' -H 'If-Match: "1"' \
  -d '{"name":"AHU second editor","enabled":true}' "$base/v1/devices/ahu-01"


全新程序預期：依序為 201 → 200 → 200 → 412。最後重新 GET，應只看見第一位編輯者的名稱和版本 2。不能靠 GET 後等幾毫秒再無條件 PUT，也不能把 412 當暫時網路錯誤自動重試。






05｜工業場景：REST 到哪一層就該停？




監看與現場控制分開
設備／PLC → 閘道採集 → 快照或歷史儲存 → REST API → HMI／工務看板。清冊裡的 enabled 是資料欄位，不代表遠端啟停。即時控制、保護和聯鎖仍交給適當的現場控制器。


資料正確不等於資料新鮮
正式量測表示至少分開來源時間、收到時間、單位、品質與逾期門檻。清冊版本不是量測版本；裝置離線的最後值不能當成現在值。低頻讀快照用 REST，連續推送再評估 SSE、WebSocket 或 MQTT。


版本比對需跟著資料走
此例只示範單一程序內的鎖。多 worker 或多主機要用持久化儲存，把版本檢查和更新放同一筆交易，例如 UPDATE … WHERE id = ? AND revision = ?，再依受影響列數判斷結果。持久化版本必須避免資源重建後重複使用同一標籤。


驗收要涵蓋拒絕和未知結果
新增 TLS、身分驗證、逐資源授權、速率限制、輸入大小限制及稽核。401 是需驗證並帶適用的挑戰，403 是無權限；429 可搭配 Retry-After。不要在通用客戶端無條件重試寫入；每次逾時都須區分是否可能已提交。
