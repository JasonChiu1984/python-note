摘要與研究問題

研究對象：Docker Engine 啟動的 Linux 容器，以唯讀合成冰水遙測為案例。容器化改變的是程序的可見範圍、資源治理和部署單位，不會自動改善效能，也不會替應用建立完整的安全邊界。本文把規格保證、環境觀察和待驗假設分開，避免把教學配置寫成現場結論。

RQ1｜隔離到底由誰執行？

辨認 OCI 映像、runtime 組態與 Linux 核心三層。用程序 PID、UID、資源上限、掛載及端點對照各自的責任。

RQ2｜尾延遲從哪裡來？

比較同主機原生程序與容器化程序的主機端 HTTP 測量，再只改容器 CPU 配額。若 p99 上升且 throttling 同步出現，才支持「CPU 配額影響尾延遲」；單有 p99 不足以定位。

RQ3｜停止請求何時是安全退出？

分開查 listener 關閉、已接請求是否完成、退出碼及強制停止。若只有容器顯示 Exited，不能推論業務工作已完整交接。

RQ4｜容器化降低了哪些 OT 風險？

為映像、Engine、程序、網路、資料完整性分別定義威脅與證據。不能把同一個控制措施當成另一層的通過證明。

閱讀順序：先用三張圖建立模型，再看核心機制與架構取捨；實驗章提供原始 CSV、指標和判讀方式；最後用威脅模型與驗收表回查證據。

心智圖：Docker 容器的六條主線

架構圖：哪些工作由誰負責？

映像輸入Registry 提供 manifest、config 和 layers。多平台 index 對應各平台 manifest；Apple Silicon 常見是 arm64，生產映像要核對預期架構。

核心機制：從映像內容追到核心執行

1. 一份映像不等於一份執行中的容器

映像 index 可指向不同平台的 manifest；manifest 引用 config 與 layer blobs。Registry 所展示的 digest 可能指 index，也可能指單平台 manifest；docker image inspect .Id 不應當作替代的 registry manifest digest。Tag 只是可移動的名稱，內容固定須記錄核准的 digest 與選定平台。Digest 驗的是內容識別，不會回答「哪個團隊發布」「簽章是否可信」「含不含漏洞」。建置期才用的憑證不要放入環境層或映像層；使用為建置提供的 secrets 機制。[S01、S08]

啟動時，Engine 將容器組態委託典型的 containerd／shim／OCI runtime 執行鏈。Runtime 依程序、mount、namespace、cgroups 等設定建立可執行環境。runc 不是替 Python 長時間運算的 daemon；它完成建立與啟動後，容器程序的 I/O 和退出交由對應的 shim 與管理層處理。不同平台與 runtime 的實作可以不同。[S02、S03]

2. 可見性、配額、權限是三個維度

Namespace ∣ 看得見什麼

PID、network、mount、IPC、UTS 等是各自的視圖。User namespace 可重新映射 UID/GID；是否使用及如何映射依部署模式。容器中 UID 0 不應被當成沒有權限風險。

cgroups ∣ 能使用多少

cpus: 0.50 型態設定限制可用 CPU 時間，而不是綁定一顆特定核心。CPU 配額造成的 throttling 與記憶體逼近上限可能都使 p99 拉長，需用核心計數和對照組區分。

Capability／LSM／seccomp ∣ 允許做什麼

Capability 拆分部分特權；seccomp 限制可用系統呼叫；AppArmor／SELinux 依主機與政策提供強制存取控制。Non-root、rootless Engine 與唯讀掛載各有不同保護面，不互相替代。

原生 Linux 容器共享主機核心，macOS／Windows 的 Docker Desktop Linux 容器通常在 Linux VM 中共享該 VM 的核心。VM 有客體核心，通常適合需要分離核心的信任邊界；但 VM 也需維護 hypervisor 與客體。若比較 native Linux、容器與 Desktop，不能只把差異歸咎於 Docker：VM 路徑、host filesystem、CPU 架構／模擬、核心版本都可能同時變動。[S02、S04、S06]

3. I/O 路徑決定瓶頸與資料壽命

映像層＋容器可寫層
典型 OverlayFS 以多個唯讀下層提供 rootfs，可寫上層接住變更；第一次修改某些下層檔案時可能 copy-up。實際 snapshotter／儲存驅動應從 Engine 查，不可將 overlay2 當通則。停止保留可寫層，移除容器才失去它。
Volume／bind mount／tmpfs
Volume 由 Engine 管理，資料可獨立於容器存在，但不等於跨主機複寫或已有備份；bind mount 依附 Engine 主機路徑、權限與檔案共享機制；tmpfs 適合允許消失的暫存。對照量測須固定資料量、同步寫入政策、快取條件與底層媒體。[S05]
容器埠與發布埠
例：同 Compose 網路的客戶端找 telemetry:8080；主機程式走 127.0.0.1:18080。EXPOSE 是映像中的說明，不會自動發布或放行。現場 BACnet/IP 發現還要由網路管理面確認廣播域、路由、ACL 與產品具體設定；不把 Docker Desktop 的通訊結果外推到所在 VLAN。[S07]

4. PID 1、健康與終止的因果關係

用 exec-form CMD 或包裝腳本的 exec 讓應用接到預期訊號；有子程序時另驗訊號轉送和回收。停止要求一般先送 TERM（可改）、達上限後強制結束未退出的程序。容器 running、健康檢查、應用就緒與業務資料正確是四件事。配置一般 restart policy 也不代表只因 unhealthy 就會重啟。原部署教材的 SIGTERM 實測另外展示本機如何分辨成功收尾和超時；不能把該結果算成這個容器案例的預設能力。

實驗設計：測量之前先決定可推論什麼

證據狀態：此處是可重跑的比較設計，不是實測的 Docker 效能排名。測量程式僅對本機合成服務執行；不改動 PLC、不掃描網路、沒有預填數據。

A：原生 Linux 基線
同一台 Linux 主機、同一 Python 修訂版、同一份 app.py、同一請求內容／記錄設定。在本機以 loopback 啟動同一 Handler；將 18081 當作基線埠，避免和容器的 18080 混用。
B：同主機容器
在同樣的 Linux 主機上，用上一章 Compose 啟動同一 Handler；主機從 18080 走發布埠。A→B 衡量的是「原生路徑到這種部署路徑的總差」，不是純粹的 namespace 成本。若要拆分網路成本，另設同一程序／埠發布設定、只改一項暴露路徑的對照設計。
C：容器加 CPU 配額
對 B 使用只改 CPU 配額的 Compose 覆寫，不同時加入記憶體或 PID 限制。記下有效上限與 cpu.stat 的 nr_throttled、throttled_usec 在試驗前後的差。若主機無相容 cgroup v2 介面或計數不可讀，標記無資料，不當成零。資安章的多項強化檔不是此組的單一變因覆寫。

試驗控制：記錄 OS/kernel、Docker/Compose、Python、CPU 架構與頻率策略、映像 digest、cgroup 版本、測試時間與每組有效配置。每組先暖機，再以相同請求數、併發與逾時重跑至少 5 次；交錯 A/B/C 輪次以減少時間漂移。冷啟動另記快取映像與是否拉取，測「啟動命令 → 首次正確樣本」，不要把 pull 時間混成穩態請求延遲。桌面 VM、arm64/amd64 模擬或不同磁碟應作為獨立條件。

量測和判讀

  • 每輪原始資料：保留嘗試序號、單調時鐘起始、耗時、HTTP 狀態和結果。HTTP 200 但資料契約錯也要算失敗；沒有成功樣本時延遲報 null。
  • 分母：失敗率＝失敗嘗試／所有測量嘗試；吞吐＝成功數／測量牆鐘時間；p95/p99 以成功樣本的 nearest-rank 計算，須與失敗率並列。每輪 p99 至少建議 1,000 次成功樣本，仍是尾部估計，不是最大延遲。
  • 跨輪結果：不要把五輪請求當成五千個彼此獨立的實驗。比較各輪 p99 中位數、範圍或非參數區間；若設計為配對，應報告相同輪次的 B−A 或 C−B 差值。誤差較大時保留未決結論。
  • 負載邊界：本程式採固定 worker 的封閉式負載，每次新 TCP 連線，包含連線、讀回及 JSON 驗證；不量真正使用者到 OT 設備的端對端時間。變慢時發送率也可能下降；壓測排隊／大量逾時須另設到達率控制，不把此數字當成容量證明。

從 OCI 設定追到 Linux 核心

以 docker run 啟動多架構映像為例：Engine 建立容器設定並選擇平台；containerd 準備映像快照；shim 管理該任務，典型配置再由 runc 實作 OCI 的 create/start。Linux 核心依程序所屬的 namespace、cgroup 與安全原則執行限制。下表是責任順序，不是對所有 Engine/OCI 實作的系統呼叫順序保證。實驗不要以 runc 短命程序是否還在判斷容器健康。

程序樹、PID 1 與重啟

一個程序對容器內和主機可見的 PID 可能不同。使用 --init 時，小型 init 會成為 PID 1，終止訊號通常由它轉送；仍須實測應用是否停止收新任務、結清在途資料，以及背景子程序是否退出。單看退出碼 0 也不能證明最後一筆量測落盤。

cpuset、weight 與 quota

cpuset.cpus.effective 是現行可使用的 CPU 集合；cpu.weight 用在同層有競爭時的相對份額；cpu.max 是週期配額。例：50000 100000 代表每 100 ms 有 50 ms CPU 時間，可能由幾個執行緒合計用完，不是固定分配半顆實體核心。葉層顯示 max 不排除祖先群組已被限額。

RSS、回收壓力與 OOM

memory.current 是群組用量，不是單一 Python 程序 RSS，會含例如 page cache 等開銷；memory.high 施加回收壓力，memory.max 是硬上限。memory.events.local 的 high、oom、oom_kill 觀測不同事件，不能互換。若懷疑上層限制，以授權的主機監控查祖先群組，不能以葉層計數定案。

儲存與網路成本

把「修改既有映像檔」與「在 volume 建新檔」直接相比，會同時改操作與掛載。測 copy-up 時，同一種檔案大小、寫入偏移、持久化方式及裝置；第一寫和後續寫分開。同樣地，主機到發布埠通常多了 Engine 的轉送路徑；不要把 bridge、NAT、Desktop VM 和應用序列化的成本全算給容器抽象。

可重跑的因果驗證：CPU、記憶體與停止

驗證範圍：本教材驗證無 Docker 也能跑的採證測試、資料解析與頁面功能；下列 Docker Engine 對照組需在有權使用的本機 Linux 測試主機實跑。沒有填入假測量值，也不可對正式 Gateway／PLC 執行實驗。

D1｜延遲變長，真的被 CPU 限流嗎？

在前面的 B/C 組各跑至少五輪。每輪先記容器 ID，群組快照夾住同一輪請求，不跨重建相減。範例從本機終端把收集器經 stdin 傳給容器內 Python，工具不需要掛載 Docker socket。不使用 TTY，JSON 才不混雜終端格式。docker exec 本身會多一個短命程序；如果實驗只有幾毫秒，不能忽略這項擾動。

ctx=default  # 僅在確認這是本機實驗 Engine 時使用
cid="$(docker --context "$ctx" compose -p python-interop-lab ps -q telemetry)"
test -n "$cid" || exit 1
# 請先新建一個不存在的輪次目錄，防止覆寫前次證據。
mkdir round-c01 && (
  set -e
  snap() { docker --context "$ctx" exec -i "$cid" python - < cgroup_evidence.py; }
  snap > round-c01/before.json
  rc=0
  python3 bench_http.py --port 18080 --count 1000 --workers 4 --warmup 0 \
    --csv round-c01/requests.csv > round-c01/http.json || rc=$?
  snap > round-c01/after.json
  python3 cgroup_evidence.py --diff round-c01/before.json round-c01/after.json \
    > round-c01/delta.json
  exit "$rc"
)

比對 Δnr_throttled / Δnr_periods（分母為 0 時不計算）、Δthrottled_usec、p99 及錯誤率。支持配額假設的證據是：同一負載下 C 的有效配額確實較低，且多輪尾延遲與限流計數同步上升；若兩組都同樣節流，或只有延遲增加，先查客戶端 CPU、佇列積壓、記錄 I/O、主機層祖先 cgroup。比值不是請求被限流的百分比。前後配置若有變動，該輪不要混入穩態比較。

D2｜記憶體上限與退出原因

使用同一個本機已建好的範例映像。兩組同樣配置 32 MiB 合成 buffer，只有記憶體上限不同，兩組停用額外 swap；啟動後保留停止的容器供 inspect。不可在生產 context 執行。若主機無法限制記憶體／swap，跳過，不當成通過；Python 原先的 RSS、配置器是否碰到所有頁、架構或宿主壓力都會影響結果。命令以 Bash 和名稱唯一的測試標籤為例。

ctx=default
# 先在實驗主機建立本機映像；以下 run 不拉取映像或連外。
docker --context "$ctx" build -t docker-research-local:trial .
stamp="$(date +%s)-$$"
for limit in 24m 96m; do
  name="docker-research-mem-${limit}-${stamp}"
  docker --context "$ctx" run --pull=never --network none --name "$name" \
    --memory "$limit" --memory-swap "$limit" --pids-limit 16 \
    docker-research-local:trial python -c \
    'b=bytearray(32*1024*1024); b[::4096]=bytes(8192); print("allocated",len(b))'
  # 退出碼保留對照；命令本身報錯不等於成功重現 OOM。
  docker --context "$ctx" inspect --format     '{{.State.ExitCode}} OOM={{.State.OOMKilled}}' "$name" &&
    docker --context "$ctx" rm "$name"
done

高上限組應產生 allocated 標記；低上限組可能在配置前或配置中失敗。若 OOM=true，且受控主機同期的對應群組 oom_kill 或 OOM 紀錄相符，支持被 OOM 終止；exit=137 單獨只能作為 SIGKILL 型態的線索，不能單獨判 OOM。不要把失敗閾值推廣成 Python 記憶體需求。

D3｜測試停止預算，不碰正式資料

同一個 Python 合成工作以 exec-form 作為容器命令。在 SIGTERM handler 模擬 2 秒結清：5 秒寬裕組應見 drained 與 exit 0；1 秒組應見終止但沒有結清標記。執行 docker stop 前先確認該測試容器已寫出 ready；未出現時不要開始計時。排程高度負載時，應以實際觀察判讀。

ctx=default
stamp="$(date +%s)-$$"
name="docker-research-term-${stamp}"
docker --context "$ctx" run -d --pull=never --network none --name "$name" \
  docker-research-local:trial python -u -c '
import signal, time
def finish(signum, frame):
    print("draining")
    time.sleep(2)
    print("drained")
    raise SystemExit(0)
signal.signal(signal.SIGTERM, finish)
print("ready")
while True:
    time.sleep(0.1)
'
docker --context "$ctx" logs "$name"  # 確認 ready 後，再執行下一行
docker --context "$ctx" stop --timeout 5 "$name"
docker --context "$ctx" logs "$name"
docker --context "$ctx" inspect --format '{{.State.ExitCode}} OOM={{.State.OOMKilled}}' "$name"
docker --context "$ctx" rm "$name"
# 另開一個名稱不同的容器重跑，僅將 stop --timeout 改成 1。

正式採集程序應避免在 Python signal handler 裡做 I/O 或等待；通常只設停止旗標，由主迴圈關閉入口、限制排空時間並留下已提交序號。此處的 sleep 僅用來產生受控的退出差異。

展開唯讀採證程式：如何定位程序所屬群組

讀取 /proc/self/cgroup 與 /proc/self/mountinfo，從 cgroup v2 mount root 換算相對路徑；再要求 cgroup.procs 包含自身 PID，避免把上層群組當本容器。以前後 boot_id 與 cgroup inode 核對，並檢查計數未下降。已知限制：部分委派、受限 procfs 或混合 v1/v2 配置可能無法驗證；計數缺失一律保留 null。

           "memory.high", "memory.max", "memory.swap.max", "pids.current", "pids.max")
COUNTERS = {"cpu.stat": ("usage_usec", "nr_periods", "nr_throttled", "throttled_usec"),
            "memory.events.local": ("high", "max", "oom", "oom_kill", "oom_group_kill"),
            "pids.events": ("max",)}


def unescape(value):
    return re.sub(r"\\([0-7]{3})", lambda m: chr(int(m[1], 8)), value)


def read(path):
    try:
        return path.read_text().strip()
    except OSError:
        return None


def locate(proc, pid):
    if not proc.is_dir():
        return None
    membership = read(proc / "cgroup") or ""
    rows = [row[3:] for row in membership.splitlines() if row.startswith("0::/")]
    if len(rows) != 1:
        return None
    group = Path(rows[0])
    for line in (read(proc / "mountinfo") or "").splitlines():
        lhs, sep, rhs = line.partition(" - ")
        parts = lhs.split()
        if not sep or len(parts) < 5 or rhs.split()[:1] != ["cgroup2"]:
            continue
        root, mount = map(lambda x: Path(unescape(x)), parts[3:5])
        options = [group.relative_to("/")]
        if group.is_relative_to(root):
            options.insert(0, group.relative_to(root))
        for relative in options:
            # Never walk up to an ancestor or trust namespace-relative paths alone.
            if ".." in relative.parts:
                continue
            path = mount / relative
            try:
                inode = path.stat()
            except OSError:
                continue
            procs = read(path / "cgroup.procs")
            if procs is not None and str(pid) in procs.split():
                return path, [inode.st_dev, inode.st_ino]
    return None


def parse_counters(raw, keys):
    found = {}
    for row in (raw or "").splitlines():
        items = row.split()
        if len(items) == 2 and items[1].isascii() and items[1].isdigit():
            found[items[0]] = int(items[1])
    return {key: found.get(key) for key in keys}


def snapshot():
    base = {"schema": 1, "kernel": platform.release(), "sample_unix_ns": time_ns(),
            "boot_id": read(Path("/proc/sys/kernel/random/boot_id"))}
    result = locate(Path("/proc/self"), os.getpid())
    if result is None:
        return dict(base, status="unavailable", reason="verified cgroup v2 leaf not readable")
    path, obj = result
    return dict(base, status="ok", identity=obj, scalars={k: read(path / k) for k in SCALARS},
                counters={f: parse_counters(read(path / f), keys) for f, keys in COUNTERS.items()})


def compare(a, b):
    if any(s.get("schema") != 1 or s.get("status") != "ok" or not s.get("boot_id") for s in (a, b)):
        raise ValueError("both samples must be readable v2 snapshots with boot identity")
    if (a["boot_id"], a["identity"]) != (b["boot_id"], b["identity"]):
        raise ValueError("samples belong to different cgroup instances")
    if a["sample_unix_ns"] >= b["sample_unix_ns"]:
        raise ValueError("sample order invalid; check clock or input")
    delta = {}
    for f, keys in COUNTERS.items():
        delta[f] = {}
        for k in keys:
            before = a["counters"].get(f, {}).get(k)
            after = b["counters"].get(f, {}).get(k)
            if before is not None and after is not None and after < before:
                raise ValueError(f"counter reset: {f}/{k}")
            delta[f][k] = None if before is None or after is None else after - before
    return {"schema": 1, "delta": delta,
            "configuration_changed": [k for k in SCALARS
              if not k.endswith(".current") and a["scalars"].get(k) != b["scalars"].get(k)]}


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--diff", nargs=2, type=Path, metavar=("BEFORE", "AFTER"))
    args = parser.parse_args()
    try:
        result = compare(*(json.loads(path.read_text()) for path in args.diff)) if args.diff else snapshot()
    except (ValueError, KeyError, TypeError, OSError) as exc:
        parser.error(str(exc))
    print(json.dumps(result, indent=2, allow_nan=False))
    return 2 if result.get("status") == "unavailable" else 0


if __name__ == "__main__":
    raise SystemExit(main())

診斷對照：同一種症狀，可能是不同層的問題

p99 上升

先對照飽和度、節流與失敗比例。若 p99 上升但群組無節流，不能用未發生的葉層事件解釋；查上層配額、應用在途量、TCP backlog 與對端延遲。CPU 降速本身也可能拉長 p99 而不增加 quota 計數。

退出碼 137

對讀 Docker OOM 標記、主機紀錄與停止事件時間線。低記憶體 OOM 與 stop 超時會出現相同退出碼。遇到重啟後新容器，不可讓新的零值覆蓋舊事故證據。

第一次寫入特別慢

比較下層檔案首寫和後續寫、相同方式寫 volume 控制組。確認快取、fsync 次數和實際快照驅動。如果 volume 首寫也慢，先排除資料檔延遲配置、磁碟及快取，不歸咎 copy-up。

服務健康，遙測卻過時

同時讀程序存活、採集完整性與點位來源時間。若本地 PLC 持續自行控制但中控讀到舊值，先標記 stale，依工區設定的最大資料年齡告警。盲目重啟可能丟掉待傳事件，不能取代來源資料驗收。

部署決策：同組織、可信程式的唯讀採集優先以非 root、分區網路、最小裝置授權與有限資源起步。若要執行不受信任的跨租戶程式，另評估獨立 VM 或更強隔離；一般容器與宿主共用核心。Rootless 降低 daemon 層級的權限，仍要驗 cgroup 控制器委派、落盤權限與網路行為。把映像 digest、來源驗證、備份還原和實際量測分開做成可稽核紀錄。

資安分析：先辨識信任邊界，再決定怎麼驗

映像與依賴：內容正確嗎？

風險：可變 Tag、未授權映像、過時基底或把連線密碼做進 image layer。控制：可信 Registry、digest 固定、SBOM、弱點掃描與簽章驗證；建置用 secrets 機制，執行期用授權祕密來源，不寫在 Dockerfile 或日誌。

驗收：核對發行 digest、發行來源、掃描／簽章結果與更新期限；掃描無告警不代表安全。

Engine 管理面：誰能控制主機？

風險：服務或腳本持有 Docker socket、共享管理帳密。控制：不把 socket 掛進採集容器；限制 Docker 使用者與遠端管理，分離資料面和管理面。適用時用 rootless 或獨立 VM，仍要管好權限、憑證與主機更新。

驗收：以匯出的服務設定核對沒有 socket 掛載、沒有不必要管理埠，日誌可追溯管理變更。

執行隔離：最低權限與影響範圍

風險：root、過多 capabilities、任意主機掛載、資源競爭。控制：非 root、唯讀根檔案系統、cap_drop: [ALL]、禁止取得額外權限，保留適用的 seccomp／AppArmor／SELinux 防護。只開必要可寫目錄，設定合理 CPU／記憶體／程序限制。

驗收：查有效 UID、實際掛載、資源上限及設定是否生效；不因程式失敗就改成 privileged。

OT 資料面：隔離不等於安全控制

風險：採集容器能碰到無關的 PLC、寫入設備、送出錯誤或過時的點值。控制：依工區分區；出口依目的端、埠與協定需求審查，採集預設唯讀。維護點位／單位／品質／來源時間，限制重試與輪詢負載。

驗收：分開測本地程序、Gateway 至平台、點位對應、斷線／來源過期；PLC 安全連鎖仍由已驗證的本地控制邏輯負責。

最小權限設定範例：獨立覆寫檔

可儲存為 compose.hardening.yaml，和上一章的 compose.yaml 疊加。數值只供實驗；實際上限先量測尖峰、延遲和記憶體再定。覆寫不替代 OT 分區、防火牆或 Engine 管理權限控管。

services:
  telemetry:
    user: "10001:10001"
    read_only: true
    cap_drop: [ALL]
    security_opt:
      - "no-new-privileges:true"
    cpus: 0.50
    mem_limit: 128m
    pids_limit: 64
docker --context "$ctx" compose -p python-interop-lab \
  -f compose.yaml -f compose.hardening.yaml config

config 只解析合併的設定，不代表核心已套用限制。上線前再從容器組態、執行中的資源指標及應用程式延遲各自驗收。

邊界提醒：容器共享核心，rootless、唯讀、網路分段都是不同防線，不能互相替代。容器不應被描述為可安全承載任意不受信任程式的通用沙箱。

工控 Gateway 威脅模型與驗收

保護標的：採集服務的可用性、平台所見點位的完整性與來源時間、憑證與資產資訊的機密性，以及本地控制不受上位故障干擾。信任邊界依序為建置／Registry、Engine 主機、容器程序、OT 設備區與上位平台；網頁沙盒或本機合成資料不跨入後兩區。

T1｜製品被換版或來源不明

判斷：生產部署以核准 digest 與平台為準，核對 SBOM、簽章、建置來源、掃描時間與修補責任。拒絕未對應 release 的映像。SBOM 只是組成清單；弱點存在不等於可到達，掃描無告警也不等於安全。

證據：發行紀錄、政策檢查、重建和回滾的已知映像。

T2｜管理身分擴大成主機權限

判斷：採集程序與一般 Web API 不持有 Engine socket、遠端管理憑證或主機管理掛載。區分 non-root 程序、rootless Engine 和獨立 VM；根據需隔離的資產決定是哪一層，不把 socket 檔標成唯讀當成權限控制。

證據：靜態服務設定、實際掛載與執行 UID、Engine 帳號範圍和稽核紀錄。

T3｜點位錯配或來源資訊遺失

判斷：單一點位 ID 對一份版本化對應。協定、單位、有效範圍和來源時間各自保存；取不到來源時間標未知。HTTP 200、Docker healthy 和協定可達都不能證明對應正確。

證據：逐點核對從合成輸入到上位端的值、單位、品質、目的端；避免把「沒有讀值」填成合法數字零。預覽與實際上位接收分開記錄。

T4｜過載或上位故障影響本地控制

判斷：按工區做最小路由集合，記錄允許的目的地址、方向、協定、埠與批准的讀寫範圍。限制輪詢頻率、重試和緩衝；先試合成斷線與恢復，刻意不對現場設備試寫或施壓。

證據：應用延遲和錯誤率、cgroup 指標、切換／回復紀錄、品質旗標，以及 PLC 本地連鎖的獨立合格紀錄。

驗收矩陣：對每條失敗路徑記錄前置條件、輸入、預期、觀察位置與回復步驟。停服務至少關注「新連線不再收」「已接處理完成或明示超時」「上位站能辨識資料過期」「本地控制不變」。在合成案例通過，不得直接替現場驗收簽核。[S03、S08、S10]

架構實作：以唯讀合成遙測核對四個層級

沿用 Docker × Python 的 telemetry 實驗。先在已確認的本機測試情境啟動，不連真實設備。在上一章實驗的資料夾執行。以下只查該實驗的狀態，並在容器中短暫執行 Python 印出 UID；不變更設備或服務組態。若未啟動，先照原章建置。

ctx="$(docker context show)"     # 先確認指向隔離的本機測試 Engine
docker --context "$ctx" compose -p python-interop-lab ps
cid="$(docker --context "$ctx" compose -p python-interop-lab ps -q telemetry)"
test -n "$cid" || { echo "請先啟動 telemetry"; exit 1; }
docker --context "$ctx" inspect --format '{{.State.Status}} {{json .State.Health}}' "$cid"
docker --context "$ctx" inspect --format 'user={{.Config.User}} ro={{.HostConfig.ReadonlyRootfs}} mounts={{json .Mounts}}' "$cid"
docker --context "$ctx" compose -p python-interop-lab port telemetry 8080
docker --context "$ctx" compose -p python-interop-lab exec -T telemetry python -c 'import os; print(os.getuid())'
docker --context "$ctx" stats --no-stream "$cid"
python3 host.py sample
  1. 平台層：確認容器存在、健康檢查可回應。
  2. 隔離層：預期 UID 為 10001、根檔案系統唯讀。檢查沒有額外主機掛載；讀實際輸出，不把教材預期值當測量。
  3. 網路層：發布應為主機 loopback 的 18080 對容器 8080。主機從 HTTP 讀樣本，不經 Docker socket。
  4. 應用層：核對 schema=1、point=supply_temp、unit=degC、quality=synthetic。真實 Gateway 還要驗收逾時、過期、重複 ID 和目的端資料一致性。

取得服務設定、公開埠、容器狀態與實際 HTTP 結果後，才有完整的對照。這個小實驗不宣稱已通過 OT 網路驗收或實際 Docker Engine 壓測。

研究限制、判準與延伸題

  • 判準須先登記：先和場域定出可接受的讀點延遲、錯誤率、重啟恢復及收尾預算，再看數據。不要拿出現最好的一輪當驗收。p99 改善但失敗增加，不能單靠 p99 判定改善。
  • 內部效度：比較時固定 logger、worker、資源配置與請求模型。同機發流量與服務會爭 CPU；記錄客戶端條件。檔案快取及頻率調整會使試驗不獨立；資料可做分輪解讀，但不能補造校正後結果。
  • 外部效度：本例的 Python 標準庫 HTTP server、合成資料和 loopback 不是多設備真實拓樸。磁碟同步寫入、跨 VLAN、數百點輪詢、多租戶干擾都需要另作實驗。比較年代較早的 KVM／Docker 研究時，引用其工作負載方法，不沿用當年數字作為今天效能保證。
  • 可重現包：保留程式版本、映像識別、Compose 合併結果（先去除敏感資訊）、原始 CSV、摘要、失敗分類與試驗順序。保留失敗輪，不只留成功圖。

延伸練習：（1）設計只改倍率或讀點名稱的負面驗收，不觸碰現場；（2）為讀寫分離與日誌輪替的儲存配置建立成本模型；（3）比較冷啟動和預拉映像啟動的差異，把發現寫成可推翻的假設。
