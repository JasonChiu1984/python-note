01｜先問要防的是讀取、竄改，還是冒用

目標／工具機密性完整性／來源工程用法及限制
SHA-256 雜湊不提供僅在摘要另有可信來源時可核對內容hashlib.sha256。不加密，不能用單次雜湊存密碼。Base64 只是編碼。
HMAC-SHA-256不提供共用密鑰持有人可算與驗，無法區分是哪一位持有人hmac.digest、hmac.compare_digest。可保護訊息完整性；須另外約定時效與重放控制。
Argon2id 密碼 KDF不是資料加密以成本較高的推導檢查密碼每個密碼用獨立隨機 salt，保存參數及雜湊；按環境量測調整成本，不用硬編廣泛通用的數值。
AES-GCM（AEAD）保護明文密文與 AAD 驗證是針對密鑰持有人用 AESGCM；同一密鑰不可重複 nonce。AAD 不保密；重放要由應用處理。
Ed25519 數位簽章不提供私鑰簽署、可信公鑰驗證交付檔案與更新聲明；公鑰要獨立建立信任，另驗版本與部署時間窗。
TLS 1.3保護傳輸連線驗證憑證與主機名；必要時加雙向 TLS沿用平台 TLS，不自製握手。終止於代理後，仍須檢查後段信任邊界與應用授權。

要防竄改但不需要保密，例如公開 release：優先簽章。要把跨信任邊界的資料變成只有持鑰服務能讀的密文：用 AEAD。兩者都不能替代使用者、角色或設備授權。

02｜架構圖：將資料與金鑰的責任分開

資料金鑰 DEK

加密資料的金鑰。解包後僅在獲准的程序邊界短暫使用；不寫進 log、網址、程式碼或共用設定檔。

金鑰加密金鑰 KEK

由 KMS／HSM 保管，授權的服務用它包裝或解包 DEK。把誰可解包、記錄與配額一起設計。

輪替與復原

新寫用新版本；舊版本僅作限期讀取。依威脅、保存期限和復原計畫重包裝或重加密；若 DEK 疑似外洩，單換 KEK 不會使既有密文重新安全。

03｜流程圖：從封裝到拒絕

  • Nonce：不是祕密，但同一把金鑰不可重複。96 位元是 GCM 推薦長度。隨機有碰撞機率；正式大量、多程序寫入需依規範設計用量上界、輪替與唯一值分配，並涵蓋重啟、備份還原及多實例，不能照抄教具的低用量策略。
  • AAD：可綁定版本、金鑰識別與記錄上下文。要由接收端依請求的可信上下文重建，不能單靠收到的記錄 ID 判定歸屬；序列化須固定。AAD 不會因此變祕密。
  • 標籤與重放：PyCA AESGCM 使用 16 位元組標籤並附在密文尾端。有效封包本身仍可能被重送；若是事件或控制資料，另核對事件序號／允許時間窗及重複處理規則。

from secrets import token_bytes
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = AESGCM.generate_key(bit_length=256)
nonce = token_bytes(12)  # 低用量教具；正式系統須設計同鑰唯一。
aad = b'["record-v1","demo-kid","record-1"]'
sealed = AESGCM(key).encrypt(nonce, b"HVAC demo", aad)
assert AESGCM(key).decrypt(nonce, sealed, aad) == b"HVAC demo"
看「加密成功」與「拒絕」的差別

預設輸出 JSON 封包、明文 HVAC demo 以及錯誤 AAD 的拒絕訊息。每次執行都生成全新密鑰與 nonce，密文不固定。測試同時檢查合法明文、錯誤 AAD、竄改 tag、不支援版本／金鑰識別及大小限制；不對未驗證資料做解析或業務處理。

AES-GCM 不是密碼儲存方式，也不會讓執行程序看不到本身解出的明文。交付程式的簽發、封裝與信任鏈另見 Python 程式碼保護。

05｜上線驗收與常見失誤

輸入與失敗

測試破損、超大小、未知版本、換 record ID、缺金鑰、標籤一位元變動。對外用統一錯誤，不將底層例外、金鑰或明文寫進 log。

執行與重啟

測並行、重啟或備份回復時 nonce 不重用；驗證拒絕不導致明文下落、重送有自己的政策、權限撤銷後不可再解包。

輪替與災備

量測新舊金鑰的讀寫覆蓋，測新寫只走新版、舊讀限期且有稽核，確認備份和回復與金鑰保留期限一致。

觀測與責任

記版本、拒絕計數與輪替覆蓋；不得用單一密鑰橫跨租戶和用途。P99 量測包含 KMS 等待，分開評估吞吐與安全邊界。

延伸學習：實作、現場案例與自我檢查

前面示範 AES-GCM 加密（需要第三方套件 cryptography）。很多現場問題其實不是「保密」而是「確認沒被改過」：本節只用標準函式庫，示範設定檔的完整性簽章、金鑰輪替與密碼雜湊。

架構圖與流程圖

可實跑範例：HMAC 設定檔簽章、金鑰輪替與 scrypt 密碼雜湊

sign() 以 HMAC-SHA256 對正規化後的 JSON 簽章並附上金鑰版本 kid；verify() 只接受清單內的版本，並用 hmac.compare_digest 做常數時間比較。hash_password() 用 scrypt 產生可儲存的密碼雜湊字串。範例金鑰與 salt 是固定值，只為了讓輸出可重現。

下載範例 example.py

"""設定檔完整性簽章（HMAC-SHA256＋金鑰版本）與密碼雜湊（scrypt），只用標準函式庫。

情境：閘道器從維護主機下載 Modbus 點位設定檔。要確認檔案沒被竄改、來自持有金鑰的一方，
並能在金鑰輪替期間同時接受新舊金鑰。這只提供完整性與來源驗證，不提供機密性（不加密）。
"""
import base64
import hashlib
import hmac
import json

KEYS = {                                   # 實務上金鑰放在 KMS／HSM 或受保護的檔案，不寫進程式
    "k2025": bytes.fromhex("11" * 32),
    "k2026": bytes.fromhex("22" * 32),
}
ACTIVE_KID = "k2026"
ACCEPTED_KIDS = {"k2025", "k2026"}         # 輪替期間兩把都接受；過渡期結束後移除 k2025


def canonical(obj) -> bytes:
    """固定鍵順序與分隔字元，避免同內容不同排版導致簽章不同。"""
    return json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode()


def sign(config: dict, kid: str = ACTIVE_KID) -> dict:
    mac = hmac.new(KEYS[kid], kid.encode() + b"." + canonical(config), hashlib.sha256).digest()
    return {"kid": kid, "config": config, "mac": base64.urlsafe_b64encode(mac).decode()}


def verify(envelope: dict) -> dict:
    kid = envelope.get("kid")
    if kid not in ACCEPTED_KIDS:
        raise ValueError(f"不接受的金鑰版本：{kid}")
    expected = hmac.new(KEYS[kid], kid.encode() + b"." + canonical(envelope["config"]),
                        hashlib.sha256).digest()
    given = base64.urlsafe_b64decode(envelope["mac"])
    if not hmac.compare_digest(expected, given):       # 常數時間比較，避免時序側通道
        raise ValueError("簽章不符：檔案可能被修改")
    return envelope["config"]


def hash_password(password: str, salt: bytes) -> str:
    dk = hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1, dklen=32)
    return f"scrypt$16384$8$1${salt.hex()}${dk.hex()}"


def check_password(password: str, stored: str) -> bool:
    _, n, r, p, salt_hex, dk_hex = stored.split("$")
    dk = hashlib.scrypt(password.encode(), salt=bytes.fromhex(salt_hex),
                        n=int(n), r=int(r), p=int(p), dklen=len(dk_hex) // 2)
    return hmac.compare_digest(dk.hex(), dk_hex)


if __name__ == "__main__":
    config = {"device": "AHU-01", "unit_id": 3,
              "points": [{"name": "SAT", "fc": 3, "addr": 0, "scale": 0.1}]}
    env = sign(config)
    print("簽章：", env["kid"], env["mac"][:16] + "…")
    print("驗證原檔：", verify(env)["device"])

    tampered = json.loads(json.dumps(env))
    tampered["config"]["points"][0]["scale"] = 1.0       # 有人把倍率改成 1.0
    try:
        verify(tampered)
    except ValueError as e:
        print("驗證竄改檔：", e)

    old = sign(config, "k2025")
    print("舊金鑰簽的檔案（輪替期內）：", verify(old)["unit_id"])
    ACCEPTED_KIDS.discard("k2025")
    try:
        verify(old)
    except ValueError as e:
        print("過渡期結束後：", e)

    salt = bytes.fromhex("a1" * 16)                       # 示範固定 salt；實務用 os.urandom(16)
    stored = hash_password("Bms#2026!", salt)
    print("密碼雜湊：", stored[:40] + "…")
    print("正確密碼：", check_password("Bms#2026!", stored), "／錯誤密碼：", check_password("bms#2026!", stored))

工程現場案例：點位設定檔的倍率被改成 1.0

某閘道器每天從維護主機下載 Modbus 點位設定檔。一次維修後，送風溫度倍率從 0.1 被誤改成 1.0，BAS 顯示 225 °C，聯動邏輯誤判高溫而關閉空調箱。檔案以 HTTPS 傳輸，但 HTTPS 只保護傳輸途中，無法證明檔案在維護主機上沒被改過。

加上 HMAC 簽章後，閘道器只載入簽章正確的檔案；未經發布流程修改的檔案會被拒絕並保留現行設定。簽章不提供保密，若設定檔含帳密，仍要另外加密或改用祕密管理服務。

  1. 把設定檔發布做成固定流程：審核 → 以發布金鑰簽章 → 上傳。閘道器只持有驗證用金鑰（HMAC 是同一把，因此要限制可讀取的帳號）。
  2. 簽章內容先正規化（排序鍵、固定分隔字元），避免縮排或鍵順序不同造成誤判。
  3. 金鑰輪替時先讓閘道器同時接受新舊 kid，所有檔案改用新金鑰重簽後，再移除舊 kid。
  4. 驗證失敗要告警並保留現行設定，不要退回「不驗證直接載入」。

版本與法規更新（核對日期 2026-11-28）

  • NIST 於 2026 年 10 月 27 日發布 IR 8547 定稿：所有易受量子攻擊的公開金鑰演算法（RSA、ECDSA、EdDSA、DH 等），不論金鑰長度都在 2030 年後列為 deprecated、2035 年後 disallowed。草案原本只把 112-bit 參數（如 RSA-2048）提前淘汰，定稿連 RSA-3072、P-256、Ed25519 也一併納入。替代方案為 ML-KEM（FIPS 203）與 ML-DSA、SLH-DSA（FIPS 204／205）。 來源：Cloud Security Alliance：NIST IR 8547 定稿摘要
  • HMAC-SHA256 與 AES-256 這類對稱式演算法不在上述淘汰範圍內，本節範例的做法仍適用。本頁核對時 cryptography 套件最新版為 50.0.2。 來源：PyPI：cryptography

練習題與自我檢查

  1. 為什麼 verify() 要用 hmac.compare_digest()，而不是 expected == given？

    看解答

    一般的 == 在第一個不同的位元組就會回傳，比較時間會洩漏「前面有幾個位元組正確」。攻擊者可以逐位元組猜出正確的 MAC。compare_digest() 的執行時間與內容無關。

  2. 如果簽章時沒有把 kid 一起放進 HMAC 的輸入，會有什麼風險？

    看解答

    攻擊者可以把 kid 換成另一個仍被接受的版本，讓驗證端用不同金鑰驗證。雖然 MAC 仍需正確，但把 kid 納入簽章能確保「用哪把鑰匙」本身也受保護，避免版本混淆。

  3. 把設定檔的 "unit_id": 3 改成 "unit_id": 3.0，簽章會通過嗎？為什麼？

    看解答

    不會。json.dumps 會把 3.0 輸出成 "3.0"，正規化後的位元組不同，HMAC 也就不同。這是好事：型別改變可能影響閘道器行為，應該視為修改。

  4. scrypt 的 n=2**14 代表什麼？什麼情況需要調高？

    看解答

    n 是 CPU／記憶體成本參數，記憶體用量約為 128 × n × r 位元組（此例約 16 MB）。硬體變快或安全需求提高時要調高，但要確認登入伺服器在尖峰時的記憶體足夠。雜湊字串中保存了參數，舊密碼仍可驗證，可在使用者下次登入時重新雜湊。

  5. 輪替時若先讓維護主機改用 k2026 簽章，閘道器的 ACCEPTED_KIDS 還只有 {"k2025"}，下載到新檔會發生什麼事？正確的順序是什麼？

    看解答

    實際執行：把 ACCEPTED_KIDS 設成只含 k2025 後驗證新檔，verify() 拋出「不接受的金鑰版本：k2026」。依案例的處理原則，閘道器告警並保留現行設定，所以設備不會壞，但所有新設定都下不去。

    正確順序是先把新驗證金鑰佈到每一台閘道器並確認（過渡期接受新舊兩把），再讓發布端改用新金鑰簽章；所有舊檔重簽、清點為 0 之後才移除舊 kid。這和憑證輪替「先信任、再切換、最後撤銷」是同一個道理。

  6. 把 hash_password() 的 n 從 2**14 調高到 2**15（r=8 不變），在本機 Python 3.13.18／OpenSSL 3.5.9 執行會怎樣？要怎麼改？

    看解答

    實際執行會拋出 ValueError: [digital envelope routines] memory limit exceeded。記憶體需求約 128 × n × r = 32 MiB，已碰到 OpenSSL 預設的 32 MiB 上限（hashlib.scrypt 的 maxmem 為 0 時採用預設值）。

    做法是明確傳入 maxmem，例如 maxmem=64 * 1024 * 1024，並確認登入尖峰時的並行數 × 每次記憶體不會壓垮伺服器。調高成本後，舊雜湊字串裡保存的是舊參數，check_password() 仍能驗證；check_password() 本身也要能帶入足夠的 maxmem，否則高成本的雜湊會驗不過。
