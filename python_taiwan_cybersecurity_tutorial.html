讀法規時先看「沿革」和生效狀態，再讀條文。下文的「資安法」指《資通安全管理法》，不是把刑法、產業監理或個資法合併為一個通用法。

02｜適用判斷流程圖

  1. 1｜先核對身分 →是否為法定公務機關？若否，查是否為特定非公務機關，不以產業名稱直接下結論。
  2. 2｜看納管文件 →具備哪些指定、核定或公告？查責任等級、主管機關與資安維護計畫。
  3. 3｜查服務與契約 →僅受託的廠商仍有受託範圍的安全管理、書面契約及通知安排，不能代替甲方法定申報。
  4. 4｜平行檢核 →資安期間、個資、行業與契約，多條義務可能同時適用。

公務機關依第 3 條包括依法行使公權力的中央、地方機關（構）或公法人，不含軍事及情報機關。特定非公務機關包括關鍵基礎設施提供者、公營事業、特定財團法人，及符合定義的受政府控制事業、團體或機構。關鍵基礎設施所在領域與「某一法人已被指定並核定為提供者」是兩回事；後者須依第 3、20 條查實。[1]

第 7、8 條牽涉資通安全責任等級及稽核。公務機關依第 12、13 條置資安長並落實維護計畫；特定非公務機關依第 20、21 條落實相應維護計畫，並依第 23 條置資安長，不能拿別家的責任等級套用。機關責任等級也不是第 1–4 級的事件等級。[1]

第 10 條要求受規範機關委外時考量受託者、監督管理機制並以書面約定；施行細則第 7 條細列應注意事項，包括在執行受託業務時知悉資安事件的通知與補救。供應商不因承攬就自動成為第 24 條法定申報主體，但不能因此忽略受託義務。[1][5]

03｜事件通報時鐘：起點、收件人、完成條件

先記錄機關何時知悉、系統受影響範圍與初步分級。依辦法第 2 條，評估核心／非核心業務資訊或系統及機密性、完整性、可用性等條件；第 3、4 級為重大事件（施行細則第 13 條）。沒有外部駭客不表示一定排除；也不是每個感測器告警都構成事件。[2][5][6]

通報辦法一般機制（第 6–8、11–13 條）
里程碑公務機關路線特定非公務機關路線
知悉起 1 小時至數位發展部指定的系統平台通報。第 6 條。按中央目的事業主管機關指定方式通報。第 11 條。
接獲起 8 或 2 小時由受通報機關審核：第 1、2 級 8 小時內；重大 2 小時內。審核完成再於 1 小時內通知主管機關。第 7 條。由中央目的事業主管機關依相同分級時限審核，完成後 1 小時內送主管機關。第 12 條。
知悉起 72 或 36 小時第 1、2 級 72 小時內；重大 36 小時內。完成損害控制或復原，並依指定方式通知。第 8 條。同一組時限，按中央目的事業主管機關指定方式通知。第 13 條。
控制或復原後 1 個月繼續調查處理，送交調查、處理及改善報告；延長須取得受通報機關同意。第 8 條。依指定方式送交報告；延長須中央目的事業主管機關同意。第 13 條。

通報和損害控制是不同工作，時鐘不可串成「先報完再開始算」。等級變更依規續報；指定方式暫不能用也須在原時限內用適當替代方式、註記原因並於障礙解除後補報。辦法第 18 條另有經核定沿用既有機制的例外；一個月不是固定 30 天。[2][6]

04｜個資事故要另走一條路

資安法第 33 條規定受規範機關的事件如涉及個資外洩，另依個資法與相關法令辦理。事件紀錄可共用，但資安通報、通知受影響當事人、依行業規範向主管機關通報不是同一件事。[1]

現行第 12 條
公務機關或非公務機關違反個資法，導致個資遭竊取、洩漏、竄改或其他侵害，應查明後以適當方式通知當事人。施行細則第 22 條說明通知方式與內容。不是普遍適用 72 小時向政府通報。
已公布、尚未施行的第 12 條
新版另設一定範圍的主管機關通報、即時有效應變及保存紀錄等安排；不能提前視為已生效。官方提供舊文、新文與狀態，應在事發時再次核查。
主管機關及行業規範
官方頁面為個人資料保護委員會籌備處；不把籌備處等同已正式承接所有監管職權。先依當時的中央目的事業、地方或特別行業規則辨識收件主體與時限。

行業規則例：金管會指定的非公務機關發生該辦法定義的重大個資事故時，有第 10 條 72 小時通報規定。不要推廣到所有公司，也不是資安辦法的 72 小時損害控制時限。[4][7][8]

05｜機房與工控案例：同樣是冰水站異常，不同身分不同義務

  • 案例 A｜一般 HVAC 供應商承攬一般商辦，設備失聯不使其自動變成關鍵基礎設施提供者。依契約回報業主，確認是否影響服務或涉及個資；若受納管甲方委託，依約及受託安排即時通知、保全、補救。
  • 案例 B｜已核定的關鍵基礎設施提供者機房冷卻監控／控制異常且核心服務疑受影響，先與資安及設施團隊依現行規定鑑別和分級，符合事件定義時啟動法定程序；不要等復原或根因報告才通報。
  • 共同工程措施記錄告警、知悉、隔離、局部復原與正式通知時間；保留現場交班、BMS 事件、遠端維護紀錄及校時狀態。先確保人員與設備安全，採用核准的安全操作程序。

例如 10:20 已知悉且屬第 1、2 級的適用事件，一般機制下是當日 11:20 前初報、知悉 72 小時內完成損害控制或復原；若認定重大則後者為 36 小時。接報審核及後續報告另起時鐘。案例不判定任何實際機關、案場或事件已納管。

延伸學習：實作、現場案例與自我檢查

法規頁最容易在實際事件中出錯的，是時間：誰在什麼時候「知悉」、時限從哪一刻起算、各里程碑何時到期。本節提供一個只算時間的小工具，並示範告警時間、知悉時間與 UTC 紀錄的差異。

架構圖與流程圖

可實跑範例：資安事件通報時鐘

依本頁整理的辦法時限：知悉起 1 小時通報；第 1、2 級 72 小時、第 3、4 級 36 小時內完成損害控制或復原。程式使用 zoneinfo 固定台北時區，避免伺服器時區設定不同造成誤差。是否構成事件、等級與適用身分仍要依法規與納管文件判斷。 逾時分鐘數無條件進位，晚 1 秒也顯示逾時 1 分鐘。

下載範例 example.py

"""資安事件通報時鐘：依《資通安全事件通報應變及演練辦法》的時限，從知悉時間算出各里程碑（教學工具）。

時限依本頁整理：知悉起 1 小時通報；第 1、2 級知悉起 72 小時、第 3、4 級（重大）36 小時內完成損害控制或復原。
本工具只算時間，不判斷是否構成事件、事件等級或適用身分；那些要依實際納管文件與法規判斷。
"""
from datetime import datetime, timedelta
from zoneinfo import ZoneInfo

TPE = ZoneInfo("Asia/Taipei")


def milestones(aware: datetime, level: int):
    if level not in (1, 2, 3, 4):
        raise ValueError("事件等級須為 1–4")
    control_h = 36 if level >= 3 else 72
    return [
        ("通報（知悉起 1 小時）", aware + timedelta(hours=1)),
        (f"完成損害控制或復原（知悉起 {control_h} 小時）", aware + timedelta(hours=control_h)),
    ]


def report_status(aware, reported, level):
    deadline = aware + timedelta(hours=1)
    late = reported - deadline
    if late <= timedelta(0):
        return "如期"
    minutes = -(-late // timedelta(minutes=1))    # 無條件進位：晚 59 秒也算逾時 1 分鐘
    return f"逾時 {minutes} 分鐘"


if __name__ == "__main__":
    # 冰水站監控異常：02:40 告警，03:15 資安人員確認為可疑遠端登入並「知悉」事件
    alarm = datetime(2026, 11, 28, 2, 40, tzinfo=TPE)
    aware = datetime(2026, 11, 28, 3, 15, tzinfo=TPE)
    print(f"第一筆告警：{alarm:%Y-%m-%d %H:%M %Z}（告警時間不等於知悉時間，兩者都要記錄）")
    print(f"知悉時間：  {aware:%Y-%m-%d %H:%M %Z}")
    for level in (2, 3):
        print(f"-- 若判定為第 {level} 級")
        for name, t in milestones(aware, level):
            print(f"   {name}：{t:%m-%d %H:%M}")
    reported = datetime(2026, 11, 28, 4, 5, tzinfo=TPE)
    print(f"實際通報 {reported:%H:%M}：{report_status(aware, reported, 3)}")
    utc = aware.astimezone(ZoneInfo("UTC"))
    print(f"跨國母公司若用 UTC 記錄，知悉時間是 {utc:%Y-%m-%d %H:%M %Z}，日期不同要特別注意")

執行方式：python example.py，只需 Python 3.10 以上；Windows 若缺時區資料，先 pip install tzdata

工程現場案例：夜間冰水站遠端登入異常，通報時間差點逾時

某已核定的關鍵基礎設施提供者，機房冰水站監控系統在 02:40 出現異常告警。值班人員先當成設備故障處理，03:15 資安人員看到可疑的遠端登入紀錄才確認為資安事件。若把 02:40 當成知悉時間，通報期限是 03:40；以 03:15 起算則是 04:15。兩個時間都要記錄，並寫明判定知悉的依據。

另一個常見問題是時區：集團 SOC 若以 UTC 記錄，同一事件的知悉日期是 11 月 27 日，台灣端是 11 月 28 日，報告上的日期不一致會引來追問。範例最後一行就是提醒這一點。

  1. 事件紀錄表固定欄位：第一筆告警時間、確認為資安事件的時間（知悉）、判定人、判定依據，全部以台北時間並附 UTC。
  2. 值班手冊寫明誰有權判定「知悉」，避免設施與資安團隊互相等待。
  3. 通報後依等級設定損害控制倒數，並在 BAS／SOC 儀表板顯示剩餘時間。
  4. 事後檢討時比較告警與知悉的時間差，作為改善監控與交接流程的指標。

練習題與自我檢查

  1. 若事件在 23:30 知悉並判定為第 4 級，損害控制或復原的期限是哪一天幾點？

    看解答

    知悉起 36 小時，也就是後天的 11:30。可把範例的 aware 改成 23:30、level 改成 4 驗證。

  2. 為什麼範例要把告警時間與知悉時間分開記錄？

    看解答

    時限從「知悉」起算，而告警可能只是設備故障或誤報。分開記錄才能說明判定過程；若事後發現告警當時就足以判斷是資安事件，兩者差距也會成為檢討重點。

  3. report_status() 用 timedelta 比較而不是比較字串時間，原因是什麼？

    看解答

    字串比較在跨日、跨時區時會出錯（例如 23:50 與 00:10）。帶時區的 datetime 相減能得到正確的時間差，也能正確處理 UTC 與台北時間混用的紀錄。

  4. 一般 HVAC 維護廠商承攬關鍵基礎設施的業務，自己需要直接向主管機關通報嗎？

    看解答

    依本頁整理，受託者不因承攬就自動成為法定通報主體，但必須依契約與受託安排，即時通知委託機關並協助處理。工具裡的時限是委託機關的義務，廠商要做的是確保自己的通知時間能讓委託機關趕上。

  5. 值班若把 02:40 的告警當成知悉時間、04:05 才通報，report_status() 會回傳什麼？若知悉是 03:15、實際通報在 04:15:59 呢？為什麼範例改成無條件進位？

    看解答

    以 02:40 起算，期限是 03:40，04:05 通報回傳「逾時 25 分鐘」；以 03:15 起算則是「如期」。知悉 03:15、04:15:59 通報時晚了 59 秒，回傳「逾時 1 分鐘」。已用範例函式實際執行驗證。

    舊寫法用 // 60 無條件捨去，晚 59 秒會顯示「逾時 0 分鐘」，讀起來像沒有逾時。期限判斷要保守：只要超過期限就至少算 1 分鐘，紀錄上同時保留精確到秒的通報時間。
