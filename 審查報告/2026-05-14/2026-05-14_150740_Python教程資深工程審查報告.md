## 1. Overview

本次以「教程是否已能支撐現代 Python 專案的事件驅動架構、重試重放、故障隔離與營運驗收」重新檢查教材。既有教材已涵蓋語法、資料庫、測試、可觀測性、安全、非同步、工業資料閘道、部署、CI/CD、整合韌性與效能記憶體工程。

結論：教程廣度與大部分專案交付深度已足夠，但在「事件驅動可靠性」仍缺一條獨立路線。高階案例雖已提及 transactional outbox、poison message、exactly-once illusion 與 search index sync，但尚未把 outbox、idempotent consumer、DLQ、replay、ordering 與 evidence report 組成可驗收教學。

## 2. Architecture

現有教程架構審查：

| 層級 | 既有內容 | 審查結果 |
|---|---|---|
| 語法與基礎 | 初級、互動式基礎、物件、函式、模組 | 符合入門需求 |
| 專案開發 | 中級、FastAPI、資料庫、非同步、測試 | 符合一般專案深度 |
| 工程交付 | 可觀測性、安全、發布、部署、CI/CD、型別契約、整合韌性、效能記憶體 | 已形成交付閉環 |
| 工業場域 | Modbus、OPC UA、BACnet、MQTT、alarm、fail-safe | 符合本專案工業自動化方向 |
| 事件驅動可靠性 | outbox、DLQ、replay、ordering、idempotent consumer | 仍需獨立補強 |

建議新增路線：

```text
domain change
  -> transactional outbox
  -> dispatcher publish
  -> idempotent consumer
  -> dead-letter queue
  -> replay after fix
  -> reliability evidence
```

## 3. Setup

本輪審查聚焦的原因：

| 缺口 | 已有教材 | 仍不足之處 |
|---|---|---|
| outbox | 高階案例有概念 | 沒有完整 sample、測試與 smoke |
| idempotent consumer | 資料庫與整合韌性有局部提及 | 未形成事件 side effect 安全閉環 |
| DLQ / replay | 高階案例有概念 | 缺 operator runbook 與 evidence report |
| ordering | 非同步教材提到 queue | 未明確解釋 stream ordering 邊界 |
| release evidence | 可觀測性與發布工程有框架 | 尚未納入事件 delivery 數據 |

## 4. Configuration

仍需補強的設定與驗收面向：

| 設定缺口 | 風險 | 建議補強 |
|---|---|---|
| max delivery attempts | 無上限重試導致 queue 堵塞 | 教材明確定義重試上限與 DLQ |
| replay reason | 事件重放不可審計 | 記錄操作原因、時間與結果 |
| stream ordering | 同一訂單或設備命令亂序 | 補 stream key 與 ordering boundary |
| duplicate handling | 重複事件造成副作用 | 補 processed event id 與 dedup policy |
| reliability evidence | 發版缺少 delivery 統計 | 輸出 reliability report JSON |

## 7. Troubleshooting

| 問題 | 可能原因 | 處理方式 |
|---|---|---|
| pending event 不下降 | broker 或 dispatcher 有問題 | 檢查 publish 失敗與批次設定 |
| 事件重複處理 | dedup key 不穩定 | 固定 event_id 並持久化 processed set |
| DLQ 堆積 | schema drift 或 handler bug | 先修正根因，再帶 replay reason 重放 |
| 同 stream 順序錯亂 | 沒有定義 ordering 邊界 | 補 stream key 與單流驗證 |
| replay 後又失敗 | 未完成修補就重放 | 把 replay 視為操作流程，不是盲目重試 |

## 8. Best Practices

- 先接受 at-least-once，再用 idempotency 達成業務安全。
- outbox、consumer、DLQ、replay 必須分層，不要互相耦合。
- 事件版本、replay 原因、delivery 統計都應進更新紀錄與 release note。
- 工業自動化命令事件要明確處理重送風險與 fail-safe。

## 9. 審查結論

本輪建議執行 v3.1.0 更新：新增 `Python Event-Driven Reliability` 教材與標準庫範例專案。這是目前最高價值、可本機驗證、且不與既有非同步、資料庫、整合韌性或可觀測性教材重疊的補強點，可讓教程更完整地支撐真實專案中的事件派送、重複處理、故障隔離與營運修復流程。
