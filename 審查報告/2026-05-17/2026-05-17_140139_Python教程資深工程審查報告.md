## 1. Overview

本輪在 `v3.8.0` 已補齊批次與排程工程後，重新從專案開發深度與廣度檢視整體教程。結論是：目前教程已涵蓋語法、服務、資料、交付、治理、可靠性、排程與工業整合，但仍缺少一條把「多步驟業務流程」做成正式工程能力的獨立教材。

現有內容雖然零散提過：

- 高階案例中的 `State Machine`、`Saga Compensation`、`GDPR Delete Workflow`
- 事件驅動可靠性的 replay、DLQ、ordering
- 批次與排程工程的 checkpoint、rerun、operator handoff
- 架構治理中的邊界、淘汰與決策紀錄

但缺少一條把下列工作流工程核心集中講清楚的專題：

- state transition contract
- transition guard / invariant
- timeout / expiry
- compensation / rollback path
- manual review handoff
- audit trail / workflow evidence

這是 Python 專案中非常常見的真實場景，例如訂單流程、工單審批、資料刪除、設備啟停審核、人工覆核與跨步驟補償。從資深工程師角度看，這是目前最值得補的高價值缺口。建議本輪更新為 `v3.9.0`。

## 5. Example

建議用零外部套件範例專案 `範例程式碼/workflow_state_machine_engineering/`，聚焦在流程治理本身，而不是引入外部 BPM / orchestrator 框架：

範例要能驗證：

- transition table 是否阻擋非法狀態轉移

- 是否輸出可交付的 audit evidence

## 7. Troubleshooting

| 問題 | 可能原因 | 處理方式 |
|---|---|---|
| 流程狀態被直接改壞 | 缺 transition contract | 補 transition table 與事件驅動轉移 |
| 逾時流程卡死 | 缺 timeout / expiry path | 補 deadline 檢查與 manual review |
| 失敗步驟無法回復 | 缺 compensation path | 補 rollback / compensate 事件與證據 |
| 人工接手時看不懂現況 | 缺 audit trail / handoff | 補 transition log、operator、reason |

## 8. Best Practices

- 工作流邏輯要集中在狀態機，不要散落在 controller、service 與 script 的 if/else。
- transition guard、timeout、compensation 與 manual review 要一起設計，不要只做 happy path。
- audit trail 要能直接被更新紀錄與 release note 引用。
- 工業場景中的工單、告警確認、設備啟停核准也適用同一套原則。
