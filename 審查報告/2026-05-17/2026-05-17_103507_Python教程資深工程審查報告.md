## 1. Overview

本輪從已發布的 `v3.4.0` 重新審視整體教程，確認主題廣度已涵蓋語法、服務、資料、部署、工業協定、可靠性與治理層；目前最大的缺口不再是新增另一條協定或框架路線，而是缺少一條把 Python 專案最常見的交付失敗來源獨立講清楚的主題：

- `venv` 是否固定
- `requirements.txt / requirements-dev.txt / constraints.txt` 是否有治理規則
- 啟動命令、Python 版本基準、依賴升級窗口是否能被驗收
- 開發、CI、部署三個環境是否能從同一份依賴契約收斂

結論：現有教程已能教「怎麼寫」，也逐步補上「怎麼測、怎麼發、怎麼部署」，但對「怎麼讓環境與依賴不漂移」仍缺獨立工程路線。這個缺口直接影響專案交付穩定性，應優先補成 `v3.5.0`。

另，本輪同步以 Python 官方網站於 2026-05-17 可查到的資訊重新確認版本事實：`Python 3.14.5` 為穩定版（發布於 2026-05-10），`Python 3.15.0b1` 為最新 beta 預覽版（發布於 2026-05-07）。這代表既有版本現代化路線的時間基準仍成立，但缺的是依賴與環境治理這一層。

建議新增一條獨立路線：

```text
Dependency Environment Governance
  -> Python runtime baseline
  -> virtual environment contract
  -> requirements / requirements-dev / constraints governance
  -> startup command / verification command
  -> dependency update window / release evidence
```

## 5. Example

本輪範例專案應以零外部套件方式，專注於依賴與環境治理本身，而不是重新做一個新服務：

- `requirements.txt`
- `requirements-dev.txt`
- `constraints.txt`
- `src/dependency_environment_governance/*.py`
- `tests/test_dependency_environment_governance.py`
- `scripts/run_dependency_environment_governance_smoke.py`

範例要能驗證：

- production requirements 是否全部 pin 版本
- dev requirements 是否正確引用 production requirements
- constraints 是否覆蓋所有依賴
- Python 版本基線是否符合專案政策
- 是否輸出可交付的 governance report

## 7. Troubleshooting

| 問題 | 可能原因 | 處理方式 |
|---|---|---|
| 本機可跑、CI 失敗 | venv 與 requirements 契約不一致 | 補明確啟動與驗收命令 |
| dev 套件污染 production | requirements 分層不清楚 | 拆 `requirements.txt` 與 `requirements-dev.txt` |
| 不同機器安裝到不同次版本 | 缺 constraints 或 pin 不完整 | 加 constraints 與 pin 檢查 |
| 升級 Python 後套件行為漂移 | 只有版本現代化，沒有依賴治理層 | 補 runtime baseline + dependency policy |

## 8. Best Practices

- `venv`、requirements、constraints、CI 與 release note 應視為同一條交付鏈。
- 若沒有明確 `requirements-dev.txt -> requirements.txt` 關係，就不要宣稱環境可重現。
- 若 production 依賴沒有 pin 版本，就不要把測試結果視為可持續證據。
- Python 版本升級與套件升級應分開治理，避免把 runtime 漂移與 dependency 漂移混在同一次故障排查。
