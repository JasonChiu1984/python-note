## 1. Overview

本次以「能否支撐真實專案開發、效能診斷、容量規劃與 release gate」重新檢查教材。既有教材已涵蓋語法、專案架構、Cython、NumPy、Pandas、FastAPI、版本現代化、資料庫、測試、可觀測性、安全、非同步、發布、工業資料閘道、部署、CI/CD、型別契約與 API 整合韌性。

結論：教程廣度已足以支撐 Python 專案從開發到交付，但在「效能分析與記憶體工程」仍缺一條獨立路線。高階案例與 Cython 有提到 performance，但尚未把 profiler selection、benchmark baseline、latency budget、memory leak detection、allocation hotspot、regression threshold、CI artifact 與容量風險串成可驗收流程。

## 7. Troubleshooting

| 問題 | 可能原因 | 處理方式 |
|---|---|---|
| benchmark 每次結果浮動 | 資料量太小或只跑一次 | 增加資料量、重複測量、用 median |
| profiler 指向錯誤熱點 | 測試資料不代表 production workload | 先定義 workload 與資料分布 |
| memory snapshot 看不出差異 | 沒有固定測量區間或基準 | 使用 before/after snapshot 與 top diff |
| 優化後正確性壞掉 | 只看速度沒有 regression test | 先用同一資料集比較輸出 |
| CI performance gate 偶發失敗 | threshold 太貼近本機數值 | 使用寬鬆 budget，CI 只擋明顯回退 |

## 8. Best Practices

- 先定義 performance question，再選 benchmark、profile 或 memory snapshot。
- 效能優化必須先保留正確性 regression test。
- `cProfile` 找 CPU hotspot，`tracemalloc` 找 Python allocation hotspot；兩者用途不同。
- CI 中的效能閘門應使用寬鬆 threshold，正式容量結論需用固定環境與多次測量。
- 工業資料閘道、輪詢與批次 ETL 應把 latency、throughput、memory、timeout 與 fail-safe 一起評估。
