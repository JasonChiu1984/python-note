## 1. Overview

目前教材已形成十條主線：初級、中級、高階 100 案例、Cython、NumPy、Pandas、FastAPI、版本現代化、資料庫工程、測試工程。v2.0.0 已把 testing pyramid、fixtures、test double、quality gate 與 release evidence 補成獨立路線，教材的「開發前、中、交付前」能力已相當完整。

下一個專案開發深度缺口是「可觀測性與維運工程」。現有高階案例與 FastAPI 教材有提到 OpenTelemetry、部署 smoke、runbook 與 error budget，但尚未形成一條從 structured logging、metrics、tracing、health check、SLO、incident record 到 rollback evidence 的獨立可驗證路線。對 production Python 專案而言，程式通過測試只是交付前提；上線後能否被觀測、診斷、降級與回復，才是維運成熟度的核心。

## 7. Troubleshooting

| 風險 | 處理方式 |
|---|---|
| 教材只講工具名 | 本輪用標準庫示範資料結構與診斷流程，避免依賴外部 SaaS |
| logging 只剩 print | 必須保留 trace id、event、level、duration 與 error context |
| metrics 不可驗收 | 範例需輸出 request count、error count、latency average 與 timeout count |
| health check 混淆 | liveness 與 readiness 分開，dependency failure 不應等同 process dead |
| GitHub push 受 DNS 影響 | 先完成 commit/tag；若 push 失敗，重試並記錄實際結果 |

## 8. Best Practices

- 可觀測性教材應教「如何讓系統可診斷」，不是只列 logging 套件名稱。
- 每個 request 應有 correlation id / trace id，否則 incident triage 會缺少串聯線索。
- metrics 要能支持 SLO 與 alert 判斷，不能只輸出漂亮 dashboard。
- health check 要區分 liveness、readiness 與 dependency degradation。
- 更新紀錄與 release note 應列出實際 smoke、test、quality gate 與已知維運限制。

## 9. Risk Notes

- 本輪新增的是可觀測性與維運 baseline，不宣稱已完成 OpenTelemetry exporter、Prometheus scraping 或雲端監控整合。
- 後續若要接近 production，可再新增 FastAPI middleware、OpenTelemetry SDK、Prometheus client、Grafana dashboard 與 alert rule 專題。
