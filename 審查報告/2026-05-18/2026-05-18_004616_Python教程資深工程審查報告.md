## 1. Overview

本輪從專案開發深度與廣度重新檢查目前教程。結論是：目前 API、治理、可靠性、資料、部署、工業整合與本地知識庫主題都已具備相當深度，但仍缺一條把「Python 自動化命令列工具」獨立講清楚的正式工程路線。

目前 workspace 已大量使用：

- `scripts/*.py` smoke / export / verification 工具
- `knowledge_base` 與 `mcp_server` 這類本地自動化支援元件
- 多個 sample project 的 runner 與驗收腳本

但教程尚未獨立說明：

- subcommand contract
- dry-run 安全邊界
- exit code policy
- JSON report 與 operator handoff
- plan / apply / report 的責任分離

這代表使用者能學到很多 Python 專題，但對最常見的「把腳本升級成可交付 CLI 工具」仍缺一條正式教材。這是目前最小、最安全、又最高價值的新增層。

## 6. Troubleshooting

| 問題 | 可能原因 | 處理方式 |
|---|---|---|
| CLI 參數愈改愈亂 | 沒有 subcommand contract | 先固定命令與參數責任 |
| dry-run 仍改到資料 | 預檢與執行邏輯混在一起 | 分離 `plan` 與 `apply` |
| 更新紀錄難引用輸出 | 只有散亂 stdout | 補 JSON report 與固定摘要行 |
| 值班同仁無法接手 | 沒有 exit code / report policy | 補錯誤碼與 handoff summary |

## 7. Best Practices

- 任何會進 CI、排程或現場操作的 Python CLI，都應先定義 subcommand contract。
- dry-run 不只是方便，而是變更安全邊界。
- JSON report 與終端摘要應同時存在，分別服務工具與人。
