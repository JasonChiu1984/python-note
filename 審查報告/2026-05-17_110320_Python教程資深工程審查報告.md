## 1. Overview

本輪從 `v3.5.0` 之後的整體教材版圖重新審視，確認目前已經補齊測試、部署、可觀測性、安全、資料演進、事件可靠性、設定治理與依賴治理等專題。現階段最大的缺口，不再是單一框架或單一技術機制，而是缺少一條把大型 Python 專案如何持續演進、拆模組、管理邊界與安全重構講清楚的獨立主題。

目前教材雖然在初級/中級/高階案例中零散提到 `ADR`、package boundary、plugin boundary、deprecation、rollback 與 refactor，但仍缺一條可直接驗收的 `Architecture Governance` 路線，把：

- ADR 與 decision log
- package / module ownership
- import rule 與 boundary guard
- deprecation policy
- refactor gate 與 release evidence

串成可交付的工程流程。

結論：教程的深度與廣度已足以支撐中小型 Python 專案實作，但對「專案規模變大後如何持續維護結構」這一層，仍缺正式獨立教材。建議本輪補成 `v3.6.0`。

## 2. Architecture

現有教程架構審查：

| 層級 | 既有內容 | 審查結果 |
|---|---|---|
| 語法與案例 | 初級 / 中級 / 高階 100 案例 | 已完整 |

| 治理與可靠性 | Configuration / Data Evolution / Event Reliability / Dependency | 已形成閉環 |

建議新增一條獨立路線：

```text
Architecture Governance
  -> ADR / decision record
  -> package ownership
  -> import boundary rule
  -> deprecation policy
  -> refactor gate
  -> release evidence
```

## 7. Troubleshooting

| 問題 | 可能原因 | 處理方式 |
|---|---|---|
| 重構後功能沒壞但結構更亂 | 缺 module ownership 與 import rule | 先補邊界規則再做重構 |
| 舊 API 一直刪不掉 | 缺 deprecation policy 與 sunset date | 補 deprecate/replace/remove 時間線 |
| 不同開發者各自拆模組 | ADR 與 ownership 未集中 | 補 decision record 與 owner map |
| CI 過了仍發生循環依賴 | 測試只驗功能沒驗邊界 | 補 import boundary guard |

## 8. Best Practices

- 架構治理不是文件美化，而是降低重構風險的可驗收機制。
- ADR 要短，但要能明確說明選擇、代價、替代方案與轉換點。
- 沒有 module ownership 與 import 邊界，不要把重構稱為可維護。
- deprecation policy 要和 release note 一起交付，避免使用者只看到功能新增，看不到舊路徑淘汰時間。
