Industrial Protocol Engineering Report

把四種工業協定放在同一張工程地圖

這份網頁版報告的目的，不是拆成四篇獨立 API 教學，而是把 `Modbus`、`OPC UA`、`BACnet`、`MQTT` 放回同一個工業/樓控專案內，清楚說明各自的網路位置、責任邊界、部署風險、速度感知與 Python 的合理角色。

Overview

這四種協定在真實專案中通常是共存關係，而不是互斥關係。正確做法是先定義誰負責設備採集、誰負責語意建模、誰負責樓控整合、誰負責平台發布，再決定程式實作與通訊治理方式。

Modbus

設備採集層

最常落在設備採集邊界，重點是 `FC`、`register/coil`、`datatype`、`word order`。

OPC UA

語意整合層

重點是 `NodeId`、`namespace`、`subscription`，負責穩定的語意節點整合。

BACnet

樓控網路層

重點不只在 `object/property`，也在 `BBMD`、`foreign device`、`routing`、`BACnet SC`。

MQTT

上行分發層

重點在 `topic`、`payload schema`、`QoS` 與 broker 行為，常作為 uplink 與分發通道。

Architecture

比較四種協定時，先看它解決哪一層問題，再看 library、port 與 API。真正的差異在責任邊界，不在命名表面。

協定主要工程位置主要責任
ModbusField device / PLC / RTU / meter 採集邊界讀寫 bit / register，取得現場原始資料
OPC UASCADA / historian / MES / edge semantic integration提供語意節點模型、訂閱更新、跨系統一致命名
BACnetDDC / BMS / building automation subnet提供樓控 object/property 模型與跨子網路整合
MQTTEdge uplink / broker / platform integration提供發布/訂閱式資料分發與事件上送

Engineering Map

同一個專案裡，資料採集、樓控整合、語意整合與平台發布經常同時存在。Python 最有價值的位置通常是邊界層：adapter、normalizer、poller、publisher，而不是盲目替代所有控制器。

控制與觀測邊界

工業專案不應把 command path 與 telemetry path 混為一談。即使協定提供寫入能力，也不代表可直接放進和觀測相同的預設流程。
Telemetry

觀測路徑

重點是資料完整性、時間戳、品質碼與可追蹤性。

Command

控制路徑

重點是 interlock、權限、寫入安全、timeout、retry 上限與 fail-safe。

Workflow

現場資料流不應從 library 呼叫開始思考，而應從設備所在網段、資料來源協定、資料表示方式與安全邊界開始判斷。

Modbus FC Implementation

`Modbus` 在設備採集層最容易「通訊成功但資料錯」。真正決定正確性的不是 socket 是否連通，而是 `FC`、資料區、位址、資料型別與字序是否全部定義清楚。

工程實作必記欄位

  • function code
  • register type
  • register address
  • quantity
  • datatype
  • endian
  • word order

  • engineering unit
若缺少上述任一欄位，現場就很容易出現「通訊成功但值錯」的假成功狀態。

FC03、FC04、FC06、FC16 的實務差異

項目實務重點
FC03最常用來讀 holding register，常見於可配置或可映射的工程值讀取。
FC04讀 input register，不應假設與 FC03 可互換，必須依設備文件定義。
FC06單一 register 寫入，適合單點設定，但不適合需要成組一致性的多寄存器更新。
FC16多寄存器成組寫入，較適合需要整體一致性的參數更新與 32-bit / 多欄位寫入。

Python/Gateway 實作流程

選定 FC
  -> 確認 register/coil 類型
  -> 確認 address / quantity
  -> 確認 datatype / endian / word order
  -> decode / scaling
  -> 補 timestamp / quality / source
  -> 判斷 alarm / fail-safe
  -> 轉成 OPC UA node / BACnet object / MQTT payload

OPC UA Role

OPC UA 回答的不是「某個 bit 在哪裡」，而是「這筆資料在系統內是什麼節點、什麼語意、如何穩定被訂閱」。它更靠近語意資料層，而不是設備寄存器層。

定位

語意一致整合

適合 SCADA、historian、MES 與跨 vendor 語意整合。

欄位

NodeId 必須可追蹤

必須記錄 endpoint、namespace、NodeId，而不是只記 display name。

行為

Subscription 優先

常用 subscription + publish，不應只用高頻 polling 硬模擬更新。

Python

Client / Bridge

常扮演 client、bridge、integration agent、payload normalizer。

BACnet Network and SC Role

BACnet 在工業/樓控專案中的難點，往往不只在 object/property，而是在跨子網路、broadcast、router、BBMD、foreign device 與 BACnet SC 的整體拓樸。

資料模型與網路部署

項目工程重點
object type / instance / property只記點位名稱不足以支撐可維護整合。
local subnet discovery同網段能看到設備，不代表跨網段也會成功。
BBMD用來在跨 subnet 的 BACnet/IP 網路中處理 broadcast distribution。
foreign device非本地 subnet 的 client/gateway 需要透過 FD registration 參與 BACnet/IP 網路。
routing跨 network number / router 邊界時，必須把 BACnet routing 視為部署一級議題。
BACnet SC屬於安全通道架構的一部分，適合遠端安全整合與受控接入。

Python 在這一層最適合扮演 gateway、integration adapter、report/export bridge，不應假設自己直接取代全部 DDC / BMS 控制核心。

MQTT Role

MQTT 最常作為 uplink 與訊息分發層，不負責原始設備位址模型，也不天然提供 PLC/DDC/BMS 的本體語意。它承載的通常是已正規化後的消息。

識別

topic + payload

核心不是寄存器或 object，而是 topic 命名與 payload 契約。

行為

Publish / Subscribe

天然適合 broker-based 分發，但 QoS、retain、buffer 都要治理。

Python

Publisher / Buffer

常扮演 publisher、subscriber、buffer manager。

誤判

快不代表源頭快

Broker 很靈活，不代表原始設備採集速度也同樣高。

Protocol Speed Comparison

這裡比較的是工程感知速度與即時性特徵，不是脫離場景的實驗室跑分。速度評估必須綁定點數規模、輪詢週期、server/broker/device 負載與網路拓樸。

通訊速度與即時性比較表

協定典型更新模式工程感知速度延遲主要來源高頻更新適配性吞吐擴展特性速度比較注意事項
Modbuspolling低到中，取決於 polling interval、device response、segment loading輪詢週期、serial/TCP timeout、逐站掃描有限，點數增多時惡化明顯受單站回應與輪詢模型限制不能只看單點速度，要看整段輪詢週期
OPC UAsubscription + publish中到高，適合事件化與連續更新sampling interval、publish interval、queue、server load通常優於純 polling取決於 server、subscription 設計與 session 管理不是所有 OPC UA server 都能高頻穩定運行
BACnetrequest/response 為主，部分場景可 COV低到中，依 object access、network topology、router/BBMD 狀態而變broadcast/discovery、routing、device processing、network design樓控監控可用，但不應假設等同高速 stream bus受樓控拓樸與設備能力影響較大若含跨 subnet、BBMD、FD、SC，速度評估必須放回拓樸中看
MQTTpublish/subscribe中到高，適合 uplink 分發與事件傳播broker load、QoS、network path、payload size通常適合，但取決於 broker 與 schema 設計通常優於輪詢式協定MQTT 快不代表資料源快，它常只是上行承載層
不做實驗室基準跑分，不宣稱四協定有單一絕對快慢排名。少量點位下 `Modbus` 可很直接，但大規模輪詢會快速累積延遲；`BACnet` 速度也不能脫離 `routing / BBMD / FD / BACnet SC` 拓樸來看。

Troubleshooting

很多整合失敗不是 library 問題，而是拿錯協定心智模型，或忽略資料表示與網路邊界。

問題先查什麼不要先做什麼
Modbus 看起來很慢輪詢點數、scan cycle、timeout、站點數量不要先怪 socket library
FC03 有值但結果怪word order、datatype、scaling、signedness不要先改上層業務邏輯
OPC UA 更新延遲高subscription、publish interval、queue、server load不要只靠高頻 polling 補救
BACnet 看不到設備subnet、BBMD、foreign device、routing不要先假設 object name 填錯
BACnet 遠端整合不穩BACnet SC、gateway 拓樸、router不要直接暴露傳統 BACnet/IP
MQTT 看起來很快但資料很舊上游資料更新週期、payload timestamp、broker backlog不要只看 broker 是否在線

Best Practices

先定義工程角色，再定義協定；先定義契約與治理，再寫程式；先區分控制與觀測，再談效能與速度。

交付前最低要求

  • 沒有 FC + register type + address + datatype + word order，不要宣稱 Modbus 點位已交付。
  • 沒有 NodeId，不要宣稱 OPC UA 契約可維護。
  • 沒有 object type / object instance / property + BBMD / FD / routing / SC，不要宣稱 BACnet 整合已可跨網段部署。
  • 沒有 topic + payload schema + quality + timestamp，不要宣稱 MQTT 整合已可維運。

工程原則

  • command path 與 telemetry path 必須分離。
  • `速度` 不能脫離 `alarm`、`fail-safe`、資料品質與安全策略單獨討論。
  • 比較協定時，先看責任邊界與拓樸，再看 library。
  • Python 最有價值的位置通常是 adapter、normalizer、poller、publisher。

Risk Notes

錯把協定當成單純不同 port，會直接導致錯誤選型、錯誤測試方法與錯誤交付結論。

Risk

把四協定當成不同 port

會導致錯誤選型與錯誤實作邊界。

Risk

把 Modbus 當語意模型

會忽略上層標準化與品質治理。

Risk

把 BACnet 當純點位讀寫

會低估 BBMD、FD、routing、SC 的部署複雜度。

Risk

把 MQTT 速度當源頭速度

會做出錯誤的效能比較結論。

Summary

四種工業協定放在同一張工程地圖時，重要的不是背名詞，而是看清它們各自解的是哪一層問題，以及資料、控制、安全與維運應如何被分層治理。

  1. Modbus 解設備寄存器與線圈採集/寫入。
  2. OPC UA 解語意節點與連續訂閱整合。
  3. BACnet 解樓控物件模型與跨網段 building automation 拓樸。
  4. MQTT 解上行發布與訊息分發。
  5. 專案落地前，至少要明確定義協定責任矩陣、位址/節點/物件/topic 契約、timeout、alarm、fail-safe，以及 command / telemetry 分離。
