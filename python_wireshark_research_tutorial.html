2｜Wireshark GUI：三個窗格交叉核對

  1. 用 File → Open 開啟合成 PCAP。不選擷取介面，不需要管理員或即時抓包權限。
  2. 在封包清單選 No.1。它應是一筆 60-byte 紀錄；若 Info 欄的文字受設定檔影響，以下方正確的欄位和值核對，不依摘要字串判斷。
  3. 在封包詳細資料逐層展開 Frame → Ethernet II → IPv4 → UDP：查 Frame Length／Capture Length、IPv4 Total Length、UDP Length、兩端埠。可將關鍵欄位佈置為自訂欄位，並記下欄位名稱。
  4. 在封包位元組選 EtherType 或 UDP Length，看高亮的實際 bytes。比較 No.1 的 IPv4 位移 14 與 No.2 的 18；再查 No.3 值從哪層開始無法成立。
  5. 從 Statistics 檢查 Protocol Hierarchy、Conversations／Endpoints 與 I/O Graphs。自行記錄是否只計顯示篩選後的樣本；同一圖表需有視窗寬度及選到的顯示篩選式。

3｜顯示篩選與 TShark：把同一個觀測做成可重跑指令

擷取篩選在擷取時決定保留哪些封包；丟掉的資料事後不能復原。顯示篩選只選擇已錄下的封包來閱讀。本例只用 Offline File 與顯示篩選，原始 PCAP 不會被修改。

顯示篩選回答什麼合成檔的預期
frame.number == 3以原始筆號定位一筆，不因篩選後列表而重編。No.3。
frame.cap_len < frame.len找只錄到前綴的紀錄，不是計算重傳或網路丟包率。No.3。
vlan.id == 100找具有這個 802.1Q VLAN ID 的觀測資料。No.2、No.3。
udp.dstport == 8080 && udp.length == 12縮到可辨識的 UDP 欄位，不把埠號當成應用協定證明。No.1、No.2。
tshark -n -r wireshark_research_sample.pcap -Y 'frame.cap_len < frame.len'
tshark -n -r wireshark_research_sample.pcap -Y 'udp.dstport == 8080 && udp.length == 12'
tshark -n -r wireshark_research_sample.pcap -T fields -E header=y -E separator=, -e frame.number -e frame.cap_len -e frame.len -e vlan.id -e ip.len -e udp.length
tshark -n -r wireshark_research_sample.pcap -q -z conv,udp

實測差異：No.3 的 TShark 仍列 ip.len=32，因該欄位所在的 bytes 已落在捕獲前綴；udp.length 則留空。Python 實作在完整 IPv4 標頭未驗證前提早停止，沒有回傳 IP 長度。兩種行為可以並存，「讀到欄位」不等於「整層資料完整」。

-n 不查名稱；-r 指定檔；-Y 套顯示篩選；-T fields 加 -e 選輸出欄；-z conv,udp 以 UDP 交談彙整。先保存全檔欄位，再算條件分組；若欄位空白，保存空白與解析狀態，不替換成 0。

4｜研究生等級的判讀：現象、推論、排除

  • 先建立可重現紀錄：檔案 SHA-256、Wireshark/TShark 版本、解析設定檔、時間格式、篩選原文、匯出欄、測點位置和樣本數。比較 Python 與 Wireshark 時，分開報告兩者的支持範圍與截斷策略。
  • 封包可解碼不等於通訊完成：同一合成檔可見兩筆 UDP，無法從來源埠/目的埠推斷應用身分、對端是否收到，或回覆是否正常。TLS 的可見資料不包含未被解密的應用內容。
  • Wireshark 的分析標記是提示：例如 TCP 重傳解讀依賴視角、順序及捕獲是否完整；一個封包的 TCP payload 不一定是一條完整應用層訊息。這份 UDP 檔沒有 TCP，不能用它驗證 TCP 重組。
  • 校驗和不等於資料來源可靠：主機端擷取的 checksum 可能受卸載影響；IPv4 UDP 的 0 欄位表示未提供 UDP checksum，不能以 0 直接推為損壞或實測遺失。
  • 一般化必須新增證據：時戳對時、交換器鏡像掉包、捕獲機使用率、取樣偏差都會改變統計。若需分析真實資料，先確認授權、去識別、保存原因與留存週期，再設計可對照的觀測。
