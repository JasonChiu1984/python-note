2｜Wireshark GUI：三個窗格交叉核對

  1. 用 File → Open 開啟合成 PCAP。不選擷取介面，不需要管理員或即時抓包權限。
  2. 在封包清單選 No.1。它應是一筆 60-byte 紀錄；若 Info 欄的文字受設定檔影響，以下方正確的欄位和值核對，不依摘要字串判斷。

3｜顯示篩選與 TShark：把同一個觀測做成可重跑指令

擷取篩選在擷取時決定保留哪些封包；丟掉的資料事後不能復原。顯示篩選只選擇已錄下的封包來閱讀。本例只用 Offline File 與顯示篩選，原始 PCAP 不會被修改。

顯示篩選回答什麼合成檔的預期
frame.number == 3以原始筆號定位一筆，不因篩選後列表而重編。No.3。
frame.cap_len < frame.len找只錄到前綴的紀錄，不是計算重傳或網路丟包率。No.3。
vlan.id == 100找具有這個 802.1Q VLAN ID 的觀測資料。No.2、No.3。
udp.dstport == 8080 && udp.length == 12縮到可辨識的 UDP 欄位，不把埠號當成應用協定證明。No.1、No.2。
tshark -n -r wireshark_research_sample.pcap -Y 'frame.cap_len < frame.len'
tshark -n -r wireshark_research_sample.pcap -Y 'udp.dstport == 8080 && udp.length == 12'
tshark -n -r wireshark_research_sample.pcap -T fields -E header=y -E separator=, -e frame.number -e frame.cap_len -e frame.len -e vlan.id -e ip.len -e udp.length
tshark -n -r wireshark_research_sample.pcap -q -z conv,udp

實測差異：No.3 的 TShark 仍列 ip.len=32，因該欄位所在的 bytes 已落在捕獲前綴；udp.length 則留空。Python 實作在完整 IPv4 標頭未驗證前提早停止，沒有回傳 IP 長度。兩種行為可以並存，「讀到欄位」不等於「整層資料完整」。

-n 不查名稱；-r 指定檔；-Y 套顯示篩選；-T fields 加 -e 選輸出欄；-z conv,udp 以 UDP 交談彙整。先保存全檔欄位，再算條件分組；若欄位空白，保存空白與解析狀態，不替換成 0。

4｜研究生等級的判讀：現象、推論、排除

  • 先建立可重現紀錄：檔案 SHA-256、Wireshark/TShark 版本、解析設定檔、時間格式、篩選原文、匯出欄、測點位置和樣本數。比較 Python 與 Wireshark 時，分開報告兩者的支持範圍與截斷策略。
  • 封包可解碼不等於通訊完成：同一合成檔可見兩筆 UDP，無法從來源埠/目的埠推斷應用身分、對端是否收到，或回覆是否正常。TLS 的可見資料不包含未被解密的應用內容。
  • Wireshark 的分析標記是提示：例如 TCP 重傳解讀依賴視角、順序及捕獲是否完整；一個封包的 TCP payload 不一定是一條完整應用層訊息。這份 UDP 檔沒有 TCP，不能用它驗證 TCP 重組。
  • 校驗和不等於資料來源可靠：主機端擷取的 checksum 可能受卸載影響；IPv4 UDP 的 0 欄位表示未提供 UDP checksum，不能以 0 直接推為損壞或實測遺失。
  • 一般化必須新增證據：時戳對時、交換器鏡像掉包、捕獲機使用率、取樣偏差都會改變統計。若需分析真實資料，先確認授權、去識別、保存原因與留存週期，再設計可對照的觀測。

官方參考：Wireshark 使用手冊、顯示篩選語法、TShark 參數、Frame 欄位、校驗和行為。

5｜TCP 串流重組實驗：同一筆 HTTP 跨兩個區段

下載 第二份合成 PCAP與 TShark 實測 CSV。樣本使用文件示例 IP 和 example.invalid，內容只有合成 HTTP，沒有真實憑據、裝置或網路互動。

連線建立

第 1–3 筆為 SYN、SYN+ACK、ACK。SYN 佔一個序號，沒有應用 payload。

請求跨兩段

第 4 筆 22 bytes、第 5 筆 23 bytes。兩段拼回完整的 GET /demo 與標頭。

回覆與關閉

第 6 筆 85 bytes，HTTP 200 與合成內文 OK；第 7 筆 ACK，第 8–10 筆為關閉交換。

  1. File → Open 讀第二份檔，先輸入 tcp.stream == 0。tcp.stream 由分析器分配，只對目前檔案與解析條件有意義，不是網路應用提供的 ID。
  2. 選第 4、5 筆，在 TCP 明細對照資料長度、相對序號與 ACK。第 5 筆的相對序號 23＝第 4 筆的 1＋22；伺服器在第 6 筆 ACK 46＝1＋22＋23。序號不是第幾筆封包。
  3. 在支援的預設重組設定下輸入 http.request || http.response，本機 TShark 4.4.19 取得第 5、6 筆。第 4 筆包含應用資料，但單獨不足以完成請求解碼。查看 TCP 詳細的重組參照，把兩段 frame number 寫進證據。
  4. 選其中一筆，右鍵 Follow → TCP Stream。比對雙方向顯示的請求與回覆。Follow 視窗是便利的串流檢視，不保留每個位元組去哪筆 frame 的完整脈絡；回到封包明細確認序號、捕獲長度與時間。
tshark -n -r wireshark_http_reassembly_sample.pcap -Y 'http.request || http.response' -T fields -e frame.number -e http.request.method -e http.response.code
tshark -n -r wireshark_http_reassembly_sample.pcap -q -z follow,tcp,ascii,0

雙向可見度、解析設定或快照長度不同，結果就可能不同。若只有 TLS 加密紀錄，不應期待直接看到 HTTP 明文。本教程不使用任何真實流量或解密資料。

6｜統計圖與時間：每張圖先寫分母

要問什麼Wireshark 操作不能直接下的結論
哪些通訊端點與交談可見？Statistics → Endpoints／Conversations。選對 Ethernet、IPv4、TCP 或 UDP 分頁，保存篩選與視窗。端點數不是設備總數；NAT、負載平衡與觀測範圍會影響統計。
流量是平穩還是尖峰？Statistics → I/O Graphs；分別設定 1 秒與較小的時間桶、相同的顯示篩選，再切換 packets/bytes。比較前保留單位。粗時間桶會抹平短尖峰；位元組數不必然包含前導碼、IFG、FCS 或未擷取流量，不能直接等同線路使用率。
請求與回覆隔多久？先定義事件起點：本例第 4 筆首段或第 5 筆請求完成，與第 6 筆回覆相比分別為 40 ms／20 ms，皆是合成時間戳實測欄位。不是單程網路延遲，也不是伺服器處理時間；兩個標記選擇不同會產生不同結果。
哪筆疑似重傳或不連續？TCP 分析欄位與 Expert Information 是定位提示。用相對序號、ACK、長度、觀測方向與對照點複核；本樣本沒有刻意重傳。單一測點缺一筆不等於發送端沒送；不能把 Wireshark 分析提示全部計為故障。

匯出報告時一併記下時間區間、時間桶、是否只統計已顯示的資料及記錄數。比較不同收集機的單程延遲前，另驗證時鐘來源、同步偏差和校時證據。

7｜完整研究交付：隔離來源、保存原始檔、重做指標

  1. 保全輸入：原始檔只讀保留；另用分析副本或只匯出必要無敏感欄位。classic PCAP 多半只有單一鏈路設定；PCAPNG 可包含多介面與個別時間設定，分析前記錄格式，不直接套用本頁的單時鐘推論。
  2. 固定方法：記錄軟體版本、解析偏好（名稱解析、TCP 重組、Decode As 若有）、顯示篩選、時間單位、擷取長度與原始長度。若讀不到預期欄位，先回全部封包，確認其鏈路型別與是否捕獲全層資料。
  3. 保存可重做輸出：CSV 以 frame number 為引用鍵，搭配快照的雜湊、篩選原文和實驗假設。截圖可說明操作，不足以代替原始欄位或條件。
  4. 區分三個層級：欄位事實（例：第 5 筆 tcp.len=23）、解析器推論（例：第 5 筆完成 HTTP request）、因果或效能結論（需其他測點或系統資料）。不要用封包數估裝置數，不要用 capture timestamp 當絕對真值。
  5. 反證練習：開兩份合成檔，確認同一 UDP 埠號並不能證明該流量屬於 HTTP；對比 TCP 檔中完整重組後明文才出現 GET。任何外部樣本須事先確認授權、避免匯出驗證資訊或其他敏感內容。

詳細解析與驗收

封包截短
caplen 小於原長，代表該封包剩餘部分未被保存在此檔案。
驗證：此檔 snaplen 64、3 筆，1 筆截短；檔案內可知缺 34 bytes。不代表線路掉了 34 bytes。
看不到的封包
classic pcap 本身的封包紀錄不等於介面統計；本程式無法從不存在的資料推回遺失數。
驗證：有原始擷取統計、雙端觀測、交換器計數器時再做交叉比對；不要將 wire_drops 缺值寫成零。
Checksum offload
本機擷取的資料可能在 NIC 完成 checksum 前就被複製。
驗證：單端的 checksum indicator 先核對擷取位置與 offload，再和另一端合法取樣比較。
框架限制
此程式只讀 classic pcap metadata；不解碼應用 payload，不支援 pcapng 或舊式特殊連結層格式。
驗證：若樣本格式不支援或檔案不完整，即拒絕解析；不得自動填補。

延伸學習：實作、現場案例與自我檢查

本頁介紹以 Wireshark 與 TShark 觀察封包。本節反過來，用 Python 手動組出一個含 Modbus TCP 請求的 pcap 檔，再逐層解析，練習把 Wireshark 畫面上每一層欄位對應回原始位元組。

可實跑範例：手動組出並解析 pcap 中的 Modbus TCP 封包

pcap 全域標頭與記錄標頭是 little-endian，乙太網路以上的協定欄位是 big-endian（網路位元組順序）。程式依序解析 Ethernet、IPv4、TCP 與 MBAP，輸出可與 Wireshark 的封包詳細窗格對照。

下載範例 example.py

"""不用 Wireshark 也能讀 pcap：產生一個含 Modbus TCP 請求的 pcap，再逐層解析（標準函式庫 struct）。"""
import struct


def build_pcap():
    mbap_pdu = struct.pack(">HHHB", 0x002A, 0, 6, 1) + struct.pack(">BHH", 3, 0, 10)   # FC03 讀 10 個暫存器
    tcp = struct.pack(">HHIIBBHHH", 50123, 502, 1000, 2000, 5 << 4, 0x18, 8192, 0, 0)
    ip_total = 20 + len(tcp) + len(mbap_pdu)
    ip = struct.pack(">BBHHHBBH4s4s", 0x45, 0, ip_total, 1, 0x4000, 64, 6, 0,
                     bytes([192, 168, 10, 5]), bytes([192, 168, 10, 20]))
    eth = bytes.fromhex("001122334455") + bytes.fromhex("66778899aabb") + struct.pack(">H", 0x0800)
    frame = eth + ip + tcp + mbap_pdu
    global_hdr = struct.pack("<IHHiIII", 0xA1B2C3D4, 2, 4, 0, 0, 65535, 1)          # LINKTYPE_ETHERNET
    rec = struct.pack("<IIII", 1_795_800_000, 123_456, len(frame), len(frame))
    return global_hdr + rec + frame


def parse(data):
    magic, vmaj, vmin, _, _, snaplen, linktype = struct.unpack_from("<IHHiIII", data, 0)
    assert magic == 0xA1B2C3D4, "非 little-endian 微秒格式 pcap"
    print(f"pcap v{vmaj}.{vmin}，snaplen {snaplen}，linktype {linktype}（1 = Ethernet）")
    off = 24
    while off < len(data):
        sec, usec, incl, orig = struct.unpack_from("<IIII", data, off)
        frame = data[off + 16: off + 16 + incl]
        off += 16 + incl
        dst, src, etype = frame[:6], frame[6:12], struct.unpack_from(">H", frame, 12)[0]
        print(f"時間 {sec}.{usec:06d}，長度 {incl}/{orig}，EtherType 0x{etype:04X}")
        ihl = (frame[14] & 0x0F) * 4
        proto = frame[14 + 9]
        sip, dip = frame[14 + 12:14 + 16], frame[14 + 16:14 + 20]
        print(f"IPv4 {'.'.join(map(str, sip))} → {'.'.join(map(str, dip))}，協定 {proto}（6 = TCP），IHL {ihl}")
        t = 14 + ihl
        sport, dport, seq, ack, doff = struct.unpack_from(">HHIIB", frame, t)
        hlen = (doff >> 4) * 4
        print(f"TCP {sport} → {dport}，seq {seq}，標頭 {hlen} bytes")
        m = t + hlen
        tid, pid, length, uid, fc, start, qty = struct.unpack_from(">HHHBBHH", frame, m)
        print(f"Modbus TCP：交易 {tid}，協定 {pid}，長度 {length}，Unit {uid}，FC{fc:02d} 起始 {start} 數量 {qty}")


if __name__ == "__main__":
    data = build_pcap()
    print(f"pcap 共 {len(data)} bytes")
    parse(data)
    print("等效 Wireshark 顯示篩選：", "modbus.func_code == 3 && ip.dst == 192.168.10.20")

執行方式：python example.py，只需 Python 3.10 以上，無第三方套件；不會擷取網路流量

工程現場案例：BAS 說讀不到電表，電表廠商說沒收到請求

整合時常見雙方各執一詞。在閘道器與電表之間的交換器設定鏡像埠擷取封包，用顯示篩選 modbus 過濾，就能確認請求是否真的送出、Unit ID 與起始位址是否正確、電表有沒有回應或回了例外碼。

擷取檔要能重跑分析：保存原始 pcap、擷取點、時間與篩選條件。範例示範的逐層解析，也可以寫成腳本批次檢查大量擷取檔，例如統計每台電表的平均回應時間與例外碼次數。

  1. 確認擷取點：交換器鏡像埠或閘道器本機，記錄位置與時間同步方式。
  2. 先用 tcp.port == 502 篩選，再用 modbus.func_code、modbus.exception_code 細分。
  3. 把同一個觀測寫成 tshark 指令，結果輸出成 CSV 方便比對。

練習題與自我檢查

  1. MBAP 的長度欄位是 6，代表哪幾個位元組？

    看解答

    長度欄位計算的是其後的位元組數：Unit ID 1 + 功能碼 1 + 起始位址 2 + 數量 2 = 6。不含交易識別碼、協定識別碼與長度欄位本身。

  2. 為什麼 pcap 全域標頭用 "<"，而 IP 與 TCP 欄位用 ">"？

    看解答

    pcap 標頭以寫檔主機的位元組順序儲存，魔術數字 0xA1B2C3D4 讀出來的順序可判斷 endian；本例為 little-endian。乙太網路以上的協定欄位依標準一律採網路位元組順序（big-endian）。

  3. 如果要讓 parse() 也能讀 big-endian 的 pcap，怎麼改？

    看解答

    先讀前 4 bytes：若 "<I" 解出 0xA1B2C3D4 為 little-endian；若 ">I" 解出才是 big-endian。依此決定後續標頭的 endian 前綴。另有 0xA1B23C4D 表示奈秒精度的時間戳。

  4. 範例的 IHL 為 20、TCP 標頭為 20 bytes。若 TCP 帶了選項（例如時間戳記），解析程式哪裡會出錯？

    看解答

    不會出錯，因為程式依 data offset 欄位計算 TCP 標頭長度（(doff >> 4) × 4），帶選項時會自動往後跳。若寫死 20 bytes，MBAP 就會從錯誤位置開始解析。
