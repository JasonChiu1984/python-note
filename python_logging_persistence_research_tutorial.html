Python 寫 Log、記憶體緩衝與狀態持久化

以工程研究方法回答三個問題：日誌事件到哪裡才可被觀察？佇列塞滿時會丟多少？重啟後應以日誌、快照還是資料庫找回狀態？

架構日誌模組狀態持久化實驗研究設計深度研究與實作

1｜三種成功條件不能混在一起

日誌為可追加的事件紀錄，主要回答發生什麼、何時發生。程式狀態回答什麼已完成，以及重啟時從哪裡繼續。記憶體緩衝只調節尖峰或傳輸批次；程序崩潰時，未落地資料可能全部消失。Log 出現「完成」不代表業務交易已 commit，反過來也可能 commit 已成功但 log 遺失。

2｜logging：階層、欄位、佇列與輪替

  • logging.getLogger(__name__) 形成有點號命名的階層。Logger 的有效 level 決定事件是否建立；propagate=True 讓事件交給祖先 handlers，祖先 logger 的 level／filter 不會再過濾傳上去的 record，祖先 handler 仍按自己的 level／filter 處理。子與父同時接同一目的地，容易重覆。應用在入口一次設定，函式庫通常只建立 logger，必要時加 NullHandler。
  • NDJSON 用 json.dumps() 每筆一行，利於串流分析。欄位至少包含 UTC 事件時間、固定事件名、severity、logger、run/request ID、結果與版本。業務值及時間單位需定義。不要把 Token、headers、個資、原始例外全文寫到 log；白名單控制來源，運營上再加 ACL、輪替、備份、刪除與異常告警。
  • 使用 datetime.fromtimestamp(record.created, timezone.utc) 記錄可對時事件；同一程序量延遲用 time.monotonic_ns() 或 perf_counter_ns() 的差值，不用兩個牆鐘時間相減。跨程序／主機的順序需來源 ID、序號與時鐘校對，不保證全域嚴格順序。
  • RotatingFileHandler 依大小加 backupCount 管理副本；TimedRotatingFileHandler 依排程計算觸發，在有事件寫入時執行 rollover，不是背景排程。兩者都不補上異地備份、壓縮、合規保留或斷電保證；需找磁碟水位、權限與輪替失敗的觀測點。
  • QueueHandler 讓慢 I/O 離開業務執行緒。預設以非阻塞方式入列，滿了走 handleError()，視設定輸出診斷或丟棄；正式服務應明訂超時、丟棄級別、告警和丟失計數。prepare() 可能先格式化並移除 args／exc_info 等欄位；需要下游格式化例外時，用白名單 schema 安全序列化，不能假設原 traceback 還在。
  • QueueListener 消費事件，respect_handler_level=True 才按各 handler 的 level 是否送出。停機先阻止 producer，再限時排空並處理 sentinel、flush、close；監控 writer 存活。Python 3.14+ 支援 listener 上下文管理，實驗用顯式 start/stop 兼顧舊版。
  • 多程序不要各自以 handler 對同一路徑寫檔或輪替。標準庫 logging 不支援多程序安全寫往同一檔；把 record 送至單 writer 或程序外採集器。使用 multiprocessing.Queue 時，不將該 queue 自身 DEBUG 日誌送回同一 QueueHandler，避免遞迴或死鎖。

3｜記憶檔、快照與交易：如何選

模組／格式合適用途失敗與取捨
io.StringIO／BytesIO、queue.Queue測試輸出、記憶體暫存、有界執行緒傳輸。程序停止不保留；設定容量／丟失政策。Queue 不是 durable log。
logging／NDJSON按事件追加、機器可讀、分頁與輪替。最後一行可能截斷；並行 writer、磁碟滿與輪替要監控。追加與資料庫交易之間沒有共同提交。
pathlib＋json＋tempfile／os.replace小容量、單 writer 整份設定或 checkpoint 快照，易人工閱讀。先寫同目錄暫存，flush、fsync 檔案再 replace。發布對讀者的原子替換不等於斷電耐久；如需更強承諾，核實檔案系統、目錄同步與平台。多 writer 另需版號或鎖。
sqlite3本機狀態、產品計數、運行記錄、用唯一鍵去重與交易。同時只能有一個 writer；排程同步，設逾時，測鎖競爭、回滾、磁碟滿與備份。多主機通常評估服務型 DB 或事件平台。
pickle／shelve受信任程式之間的 Python 特定物件快照。不可反序列化不受信任資料，可能執行程式；另有版本、類別匯入及可攜性風險。資料交換優先用 schema 驗證的 JSON 或其他明確格式。

不要把 file.flush()、os.fsync() 或完成 conn.commit() 說成相同承諾。flush 將 Python 緩衝往下送；fsync 與資料庫提交的耐久性取決於同步設定、檔案系統、硬體及實際故障情境。測試前明確定義程序終止、主機失電、磁碟損壞各要求保留什麼。

查看可重用的 API 與保障
  • QueueHandler.enqueue() 可替換飽和政策，本例固定 put_nowait()／except Full。正式服務視事件重要性決定能否丟棄，不能把審計及安全事件直接套用相同策略。
  • json.dump(..., allow_nan=False) 拒絕非有限數；同目錄 NamedTemporaryFile(delete=False) 關檔後 os.replace()，若出錯移除暫存。
  • CREATE TABLE ... PRIMARY KEY 加上 ON CONFLICT ... DO NOTHING 避免同一鍵重存；若同鍵內容不同，正式服務需另驗不可變欄位、記錄衝突，不能默默丟棄。

5｜研究設計：如何比較，而不只列模組

  1. 控制變因：固定 Python 版、檔案系統、記錄長度、佇列大小、producer 數、測試時長、同步與輪替設定。設定暖機，使用不同重複批次，標示測試環境。
  2. 候選組：同步檔案 vs. 有界 queue＋單 writer；狀態比較整份快照 vs. 交易增量。不要將 log 平均延遲當資料庫提交延遲。比較時功能前提需相同。
  3. 指標：量 producer latency（p50/p95/p99）、事件輸入率、sink 吞吐、丟失／重覆率、佇列與磁碟上界、停機排空時間及重啟後缺失。分母需含未落地及 dropped，不只用成品 log 算成功率。
  4. 故障注入：用本地暫存設計 queue 滿、寫入失敗、輪替、程序中斷與重播測試；報告是否可復原、重送是否重複。正式 RPO/RTO 不能由此單例推出。

深入解析與評估邊界

不要用看到 log 當作成功依據：python logging 收到一筆、listener 寫入檔案與應用交易 commit 是不同狀態。外部來源 ack 應等應用交易成功；若 commit 後 ack 之前中斷，來源仍會重送。

單交易修補確認空窗：若先提交 checkpoint 再寫事件，重啟可能跳過未入庫資料；若先提交事件、游標獨立寫入，重啟會重送並可能重複計數。把資料與游標放到同一交易，使用 ID 唯一約束做去重；同 ID 異內容只能告警或人工釐清。

這不是 distributed exactly-once：實驗是單 writer、連續整數 ID、SQLite 單 DB。多分區需每個來源游標與唯一鍵，跨 DB、PLC 命令或外部通知不能被這個本地交易回滾；可考慮 outbox 加冪等消費，另測服務崩潰後是否補送。

區分測到什麼：此處是程式內例外後重新開啟 DB，不是斷電、檔案系統或損壞測試。正式選 journal/synchronous 之前先定 RPO、允許重送量、儲存媒介，以及正常關機與故障復原的對照。

延伸學習：實作、現場案例與自我檢查

事件與應用程式游標必須一起提交。這個本機 SQLite 範例驗證明確回滾後重新開啟資料庫，事件與游標仍一致；不等同實體斷電驗證。

架構圖與流程圖

可實跑範例：事件與應用程式游標：回滾與重新開啟示範

每 3 筆為一批；正常路徑在同一交易寫入事件並更新 last_seq。模擬分支插入第二批後，未執行該批的游標 UPDATE 就回滾。重新開啟後讀到 last_seq=3，靠這個游標過濾已提交的有序輸入；主鍵只防止重複列，plain INSERT 遇到重複鍵仍會報錯。

下載範例 example.py

"""SQLite 交易內同時寫入事件與 checkpoint，模擬中途崩潰後重啟不重複、不跳筆（標準函式庫）。"""
import sqlite3
import tempfile
from pathlib import Path

READINGS = [(i, 20.0 + i * 0.1) for i in range(1, 11)]     # (序號, 讀值)


def open_db(path):
    con = sqlite3.connect(path, isolation_level=None)       # 手動控制交易
    con.execute("PRAGMA journal_mode=WAL")
    con.execute("CREATE TABLE IF NOT EXISTS reading(seq INTEGER PRIMARY KEY, value REAL)")
    con.execute("CREATE TABLE IF NOT EXISTS checkpoint(id INTEGER PRIMARY KEY CHECK(id=1), last_seq INTEGER)")
    con.execute("INSERT OR IGNORE INTO checkpoint VALUES (1, 0)")
    return con


def process(con, crash_after=None, batch=3):
    last = con.execute("SELECT last_seq FROM checkpoint").fetchone()[0]
    pending = [r for r in READINGS if r[0] > last]
    done = 0
    for i in range(0, len(pending), batch):
        chunk = pending[i:i + batch]
        con.execute("BEGIN")
        con.executemany("INSERT INTO reading VALUES (?, ?)", chunk)
        if crash_after is not None and done + len(chunk) > crash_after:
            con.execute("ROLLBACK")                          # 模擬交易提交前程序崩潰
            raise RuntimeError(f"在處理序號 {chunk[0][0]}–{chunk[-1][0]} 時崩潰")
        con.execute("UPDATE checkpoint SET last_seq=?", (chunk[-1][0],))
        con.execute("COMMIT")
        done += len(chunk)
    return last


if __name__ == "__main__":
    with tempfile.TemporaryDirectory() as tmp:
        db = Path(tmp) / "state.db"
        con = open_db(db)
        try:
            process(con, crash_after=5)
        except RuntimeError as e:
            print("第一次執行：", e)
        con.close()
        con = open_db(db)                                   # 重啟
        n, last = con.execute("SELECT COUNT(*), (SELECT last_seq FROM checkpoint) FROM reading").fetchone()
        print(f"重啟時：已寫入 {n} 筆，checkpoint = {last}")
        resumed_from = process(con)
        rows = con.execute("SELECT seq FROM reading ORDER BY seq").fetchall()
        seqs = [r[0] for r in rows]
        print(f"從序號 {resumed_from + 1} 繼續；最後共 {len(seqs)} 筆，重複 {len(seqs) - len(set(seqs))} 筆，"
              f"缺漏 {[s for s in range(1, 11) if s not in seqs] or '無'}")
        con.close()

執行方式：python example.py，只需 Python 3.10 以上，無第三方套件；資料庫建立在暫存目錄

工程現場案例：閘道器斷電重開後，趨勢資料重複一段

某閘道器把讀值寫入本機資料庫，另外在一個文字檔記錄「上次處理到第幾筆」。斷電發生在寫完資料、尚未更新文字檔之間，重開機後從舊位置重新處理，趨勢圖出現一段重複資料；反過來的順序則會跳筆。兩者都源於資料和進度不在同一個原子操作裡。

同交易提交可避免資料和游標一邊提交、另一邊沒有提交。範例在本機測得重新開啟後兩者都停在序號 3，回補後完整保有 1–10；不證明主機斷電時所有已確認的交易都會保留。

  1. 同一交易提交處理結果與應用程式游標；last_seq 是讀取進度，不是 SQLite 把已提交頁面寫回主資料庫的 WAL checkpoint。
  2. 重跑時讀取游標並過濾有序、可重播的輸入。跨來源或亂序資料要另定游標與重複、內容衝突的處理規則。
  3. SQLite 的一般 WAL 只用本機檔案；不要把資料庫放在網路檔案系統上。部署時讀回 journal_mode 與 synchronous 設定，不以範例預設值推論現場能力。
  4. 把程式層回滾、程序終止與主機斷電分開驗收。需要保留已確認交易時，再以目標儲存媒介、同步設定與容許的資料損失量試驗。

練習題與自我檢查

  1. 把 batch 改成 1，crash_after 仍是 5，第一次執行會成功提交幾筆？

    看解答

    每筆一個交易，處理第 6 筆時 done + 1 = 6 > 5 觸發崩潰，前 5 筆已提交，重啟後從序號 6 繼續。批次越小，崩潰時重做的量越少，但交易次數越多。

  2. 如果 reading 表沒有主鍵，而程式在 COMMIT 之後、更新 checkpoint 之前崩潰（兩者分開提交），會發生什麼？

    看解答

    獨立提交時，事件已落庫但游標未前進，重開後就會再次嘗試寫入。沒有唯一鍵會出現重複列；有主鍵且使用一般 INSERT 時會報錯，不會自動變成成功的冪等重送。

  3. 為什麼 open_db() 用 CHECK(id=1) 限制 checkpoint 表？

    看解答

    確保 checkpoint 表永遠只有一列，避免程式錯誤插入多列後不知道該讀哪一列。

  4. 範例證明的是交易一致性，還是斷電後保留每一筆已確認交易？

    看解答

    範例只驗證明確回滾後重新開啟的資料與游標一致。SQLite 文件指出，本機 WAL + NORMAL 即使一致，主機當機或斷電仍可能遺失已提交的整筆交易；FULL 則在每次提交後多做一次 WAL 同步。不要用程序終止結果替代斷電測試。

  5. crash_after 改成 7，batch 分別用 3 與 4，第一次執行各在哪一批崩潰？重啟時游標 last_seq 各是多少？

    看解答

    實際執行：batch=3 時第一、二批（序號 1–6）已提交，第三批 done 6 + 3 = 9 > 7 觸發模擬崩潰，訊息為「在處理序號 7–9 時崩潰」，重新開啟時 6 筆、last_seq = 6。batch=4 時第一批（1–4）提交後，第二批 4 + 4 = 8 > 7 就回滾，訊息為「在處理序號 5–8 時崩潰」，重新開啟時只有 4 筆、last_seq = 4。

    同一個崩潰點，批次越大，回滾後要重做的量可能越多；但兩種設定重新開啟後都從游標的下一筆繼續，最後一樣是 10 筆、不重複不缺漏。批次大小影響效能與重做量，一致性靠的是「資料與游標同交易」。這仍是程式層回滾的結果，不能代替程序終止或主機斷電的驗收。
