先選對 API 型態，再設計保護策略

型態常用方式實務邊界
HTTP RESTGET /devices/42 讀取狀態；POST /orders 送出業務指令。關注 HTTP 狀態、資源識別、驗證及快取。不要因斷線重送未知是否已完成的寫入。
Webhook供應端推送事件；接收端驗證簽章、落地後應答，再交給工作者。依供應商契約處理重送、重複與亂序；以交付 ID 去重，必要時輪詢補漏。
分頁輪詢游標取得下一頁，設定整輪期限、最大頁數及重複游標防護。游標是服務端給的不透明值。資料成功落地後才推進 checkpoint；排序、更新與漏資料依契約核對。
gRPC以服務與訊息契約提供 unary 或串流 RPC。傳遞 deadline；串流需要個別設計斷線續傳或重新同步，不能直接套 HTTP 的狀態重試表。
GraphQL透過型別 schema 查詢指定欄位；mutation 表示修改意圖。HTTP 200 仍可能帶有 errors 或部分資料；同時檢查 HTTP 及操作層結果。

單筆讀取適合即時查詢，Webhook 適合新事件通知，輪詢可做補漏與對帳。三者可以一起使用，但不可重複觸發同一個業務寫入。

把時間、容量與寫入風險拆成三組政策

政策設計與驗收
總等待預算記錄單調時鐘 deadline；每次呼叫最多取「單次 timeout、剩餘預算」兩者較小值。排隊、嘗試與退避都要納入，HTTP 函式庫單一 timeout 未必等於端到端期限。
重試／限流對可安全重試的讀取允許少量嘗試，以指數退避加 jitter 防止同步尖峰；429 依服務契約讀取 Retry-After，超過預算則退回上層。用 token bucket 限制速率與突發量，另以佇列和併發上限控制積壓與連線；每次重試也消耗配額。
斷路器Closed 正常呼叫；跨過可用性錯誤門檻進 Open 快速拒絕；冷卻後 Half-open 僅允許限量試探。成功回 Closed，失敗重回 Open。按依賴與操作分開計數，並明訂統計以單次嘗試或整筆操作為單位。
可持久的冪等服務端明確支援才使用冪等鍵，以租戶／操作／鍵及內容指紋定位，原子記錄處理中與完成結果；同鍵同內容回原結果，不同內容拒絕。設定有效期限、衝突及請求超時後的查詢／對帳行為。

外部副作用跨系統時，單靠資料庫鍵值不能保證恰好一次。應使用支援的服務端冪等契約，或 outbox、狀態查詢與對帳；關鍵寫命令不做盲目重試。

RESEARCH / DESIGN CONTRACT

把「呼叫成功」拆成可驗證的責任邊界

整合層不替外部系統保證成功；它保證在有限時間內回傳可辨認的結果，且能重建一筆操作從接收、發送到對帳的證據。

1. 先定義業務成功，再選 API

介面／情境成功的定義預設韌性設計
REST 讀取回應可解析、符合 schema，且資料年齡未超過用途允許值。在期限內有限重試；若允許用快取，回傳來源時間和 stale。設備控制不得拿舊快照冒充即時值。
REST 寫入／非同步工作以業務 ID 識別唯一效果；HTTP 202 只是已接受，不是已完成。同一次操作固定 ID；有服務端冪等契約才考慮自動重送。202 保存作業 ID，再按獨立的查詢期限追蹤狀態。
Webhook／事件依供應商規格驗證來源，訊息或等效交付紀錄耐久保存後才回傳已接收。入口 inbox 去重；處理失敗用本地工作重試；亂序按版本或事件時間規則處理，缺少資料用官方查詢介面對帳。
游標分頁／批次同步每頁資料先提交；checkpoint 只跨過已持久化的資料。不自行解讀不透明游標；限制頁數、整輪時間，偵測游標循環，必要時以重疊視窗和業務鍵補漏。
gRPC／GraphQLgRPC 看 RPC 狀態和應用內容；GraphQL 另判斷 errors、必要欄位及是否接受部分資料。gRPC 向下傳遞剩餘 deadline；串流斷線後需 resume token 或重新同步。GraphQL mutation 不能只因 HTTP 200 就判成成功或可重送。
設備閘道／PLC 讀取取得設備端資料品質及來源時間；資料過期或讀不到都不是有效零值。資料採集與安全連鎖分離。設備寫入或安全動作由授權的原有控制路徑處理，不由網站重試邏輯自行送出。

每個依賴至少登錄：用途、端點契約版本、資料 owner、可用性與新鮮度目標、操作最大等待、配額、誰能寫、外部失敗時的降級行為、診斷與對帳窗口。選擇同步、非同步或混合是業務決策，不是只看平均延遲。

RESEARCH / FAILURE POLICY

等待、重試與斷路：不同保護不能共用一個數字

2. 用單調時鐘管總預算

deadline = monotonic_now + total_budget。先把排隊與連線池等待算進去；建立連線再分 DNS、TCP、TLS（函式庫不一定分別限制）；發送與接收各有 timeout。讀取 timeout 通常是等待下一段資料的上限，不等於完整回應的總時間。呼叫後的驗證、持久化及回傳也要預留時間；取消本地等待也不代表對方停止處理。

例：總預算 300 ms，排隊 35 ms，保留 25 ms 給驗證與回傳，首個下游嘗試上限 120 ms。若首輪耗 75 ms、退避 40 ms，第二輪只剩 125 ms 可用，仍受單次 120 ms 拘束。若 Retry-After 要等 200 ms，程式應結束同步等待或轉已明訂的非同步路徑，不是提早打下一次。跨程序傳相對期限或採用協定定義的期限；不要把本機單調時鐘值送到另一台。

remaining = deadline - monotonic()
attempt_budget = min(per_attempt, remaining - finish_reserve)
if attempt_budget <= 0:
    stop("deadline")
# 僅在能控制真正 transport 等待期的介面使用此預算；
# 不把每個 I/O phase timeout 相加後宣稱端到端受限。

3. 只重試可安全重試且仍有預算的操作

觀察結果決策要留下的證據
暫時連線失敗／503只有業務效果可重送、服務契約允許且還有預算才重試；DNS 設定錯誤、TLS 憑證失敗不是等待就能修好的錯誤。錯誤發生階段、是否已送出、政策及嘗試次數。
429／帶 Retry-After先減速；以 delta seconds 或 HTTP-date 解析，不早於服務要求。等待超期限就回報或按契約排程，不當成一般服務不可用一起熔斷。租戶與配額範圍、等待理由、是否已超過同步期限。
401／403、格式或 schema 不符停止一般重試；按契約修憑證、權限或格式。若有更新憑證的契約，把有限的一次更新流程單獨建模。不含憑證原文的分類、Trace ID、schema 版本。
寫出後 timeout／回應遺失效果標為 UNKNOWN，先以原操作 ID 查詢／對帳。無確實的冪等與狀態契約時，不自動重送。操作 ID、送達證據層級、查詢結果及人工升級時限。

全抖動退避的示例：第 k 次重試等待 Uniform(0, min(cap, base × 2^k))，k 從 0 起算；若服務要求 Retry-After，不得用抖動縮短它。總嘗試數要包含首次呼叫。假如閘道與 SDK 各允許 3 次總嘗試，同一業務呼叫可能打 9 次；一般選定一層負責重試並紀錄放大倍數 = 下游嘗試數 ÷ 邏輯操作數。

4. 速率、併發、容量與斷路分開

  • 配額：按依賴、租戶或憑證定義範圍；令牌桶限制平均速率及短期突發。併發是同一時間的請求數，另設上限；排隊要有限長度和等待時間。例：50 次/s、平均耗時 0.2 s，穩態平均約 10 筆在途（Little 定律），不是安全併發規格，仍需測試長尾、尖峰與失敗。
  • Closed：正常放行並用滑動窗及最小樣本數觀察下游可用性錯誤；不能把無效業務輸入或本地限流混作下游故障。以依賴／操作分桶，說明是按單次嘗試還是按完整業務操作統計。
  • Open：暫時不打下游，快速回傳不可用、標示舊讀值，或把可延後的作業耐久排隊。不是耗完所有重試才套用，也不能用舊值掩蓋未知寫入。
  • Half-open：冷卻後只允許少量試探，其餘維持拒絕或降階；按明訂門檻恢復 Closed，或試探失敗回 Open。共享配置需考慮多副本同時試探，不讓恢復瞬間的流量淹沒外部服務。
RESEARCH / WRITE CONTRACT

寫入狀態不明時，對帳優先

冪等鍵是同一個業務意圖的識別，不是每次重試重新產生的 request ID。資料設計可採 (tenant, operation, key) 唯一索引，加上請求指紋、狀態、首次受理時間、外部業務 ID 和可安全回傳的結果摘要。組合欄位、正規化規則、保留期及隱私範圍須明訂。相同鍵且指紋不同，應回衝突而不是覆寫；相同鍵且處理中，依契約顯示等待中，不再執行第二份。

完全在同一資料庫內的副作用可與去重紀錄放同一交易。若需跨系統，採用交易式 outbox 保存意圖，透過供應端明列支援的冪等鍵降低重複，再用外部狀態查詢及定期對帳修復不確定狀態。outbox 只保證本地意圖不遺失；常見仍是至少一次交付，不能單靠它保證外部副作用恰好一次。不得將未確認、超過保留期或需人工查證的操作自動判成失敗後重送。

狀態建議：RECEIVED → SENT → SUCCEEDED / REJECTED / UNKNOWN；UNKNOWN 經查詢取得可信證據後才轉已完成或已拒絕。狀態查詢使用獨立限流、退避和最長對帳時限；狀態 API 未同步或只回「查無」時，先按供應商一致性契約處理，不自行推論從未執行。

RESEARCH / ACCEPTANCE

上線前的故障矩陣：每個測試都有可查證的證據

注入場景可驗收條件保留證據
連線池滿、建立連線慢、慢速回應總期限包含排隊與接收；客戶端取消後停止追加嘗試，不假定遠端操作被撤銷。單調時間軸、各 phase、最大嘗試數和終結理由。
429 比剩餘預算更久／持續 503429 不提前重送；支援 503 的有限重試和抖動，故障持續時按政策斷路。配額範圍、退避分布、下游實際嘗試數及轉態。
提交後斷線、同鍵同時送入對方已提交時能查回原結果，無重複效果；同鍵不同內容被拒，跨租戶不共用結果。測試用操作 ID、外部紀錄數、對帳狀態及查詢結果。
斷路冷卻、同時試探只有指定數量探測；依探測結果回 Closed 或再 Open。恢復不得造成突發。允許／拒絕探測數、冷卻期間、轉態事件。
Schema 漂移、事件重複／亂序不合格資料不覆寫有效快照；落地去重、checkpoint 及回放可驗證無漏樣。契約版、拒收理由、最後可信來源時間與對帳計數。

發行紀錄：固定提交、政策與 schema 版本，保存測試種子、階段事件和不含機密的證據。用不同的量測口徑分別觀察邏輯成功率、每次嘗試延遲、p95／p99、資料年齡、429、斷路轉態、池飽和、重試放大、對帳積壓；不要以全部結果平均值掩蓋依賴或租戶分布。Trace 使用低基數路由與 http.request.resend_count，操作識別放追蹤／結構化日誌，不做高基數指標標籤；不記錄 token、完整查詢或個資。

"""整合韌性教材：確定性模擬，沒有網路 I/O。"""
from dataclasses import dataclass
import json
from urllib.parse import urlencode
import unittest


class ApiFailure(Exception):
    """所有策略失敗，都有明確原因。"""


class Breaker:
    """同步單用戶範例：連續兩次可用性失敗開路；冷卻後試探。"""
    def __init__(self, threshold=2, cool_ms=100):
        self.threshold = threshold
        self.cool_ms = cool_ms
        self.failures = 0
        self.until = None
        self.state = "closed"

    def permit(self, now):
        if self.state == "half_open":
            raise ApiFailure("probe_in_progress")
        if self.until is not None:
            if now < self.until:
                raise ApiFailure("circuit_open")
            self.state = "half_open"

    def success(self):
        self.failures = 0
        self.until = None
        self.state = "closed"

    def failure(self, now):
        self.failures += 1
        if self.state == "half_open" or self.failures >= self.threshold:
            self.until = now + self.cool_ms
            self.state = "open"


@dataclass(frozen=True)
class Reply:
    status: int
    elapsed_ms: int
    body: object = None
    retry_after: str | None = None  # 教學僅接受 HTTP delay-seconds。


class FakeTransport:
    """虛擬時鐘：模型會遵守本次 timeout 上限。"""
    def __init__(self, replies):
        self.replies = iter(replies)
        self.now = 0
        self.calls = []

    def sleep_ms(self, delay):
        self.now += delay

    def request(self, method, path, timeout_ms):
        self.calls.append((method, path, timeout_ms))
        reply = next(self.replies)
        self.sleep_ms(min(reply.elapsed_ms, timeout_ms))
        if reply.elapsed_ms > timeout_ms:
            raise TimeoutError()
        return reply


def request(transport, breaker, method, path, total_ms=240, attempts=3):
    if total_ms <= 0 or attempts <= 0:
        raise ValueError("預算和嘗試次數必須為正")
    deadline = transport.now + total_ms
    reason = "unknown"
    for attempt in range(attempts):
        remaining = deadline - transport.now
        if remaining <= 0:
            raise ApiFailure("deadline")
        breaker.permit(transport.now)
        retry_after = None
        try:
            reply = transport.request(method, path, min(80, remaining))
        except TimeoutError:
            reason = "timeout"
            breaker.failure(transport.now)
        else:
            status = reply.status
            if status == 200:
                breaker.success()
                return reply.body
            reason = f"http_{status}"
            if status in (502, 503, 504):
                breaker.failure(transport.now)
                if status == 503:
                    retry_after = reply.retry_after
            elif status == 429:
                if breaker.state == "half_open":
                    breaker.failure(transport.now)
                retry_after = reply.retry_after
            else:
                # 可連線但非預期業務回應，不列為此 demo 的可用性故障。
                breaker.success()
                raise ApiFailure(reason)

        if transport.now >= deadline:
            raise ApiFailure("deadline")
        # 本例僅自動重試 GET；寫入要另有服務端契約。
        if method != "GET" or attempt + 1 == attempts:
            raise ApiFailure(reason)
        if breaker.state == "open":
            raise ApiFailure("circuit_open")
        # 確定性測試固定退避；正式版加入 jitter。服務端等待是下限而非取代退避。
        delay = min(200, 25 * 2 ** min(attempt, 4))
        if retry_after is not None:
            # 只接受最多 9 位 ASCII 數字；日期格式保守交回上層。
            if not (
                1 <= len(retry_after) <= 9
                and retry_after.isascii()
                and retry_after.isdecimal()
            ):
                raise ApiFailure("retry_after_unsupported")
            delay = max(delay, int(retry_after) * 1000)
        if delay >= deadline - transport.now:
            raise ApiFailure("deadline")
        transport.sleep_ms(delay)
    raise AssertionError("unreachable")


def parse_page(body):
    if type(body) is not dict or type(body.get("items")) is not list:
        raise ApiFailure("schema")
    ids = []
    for row in body["items"]:
        if type(row) is not dict or type(row.get("id")) is not int:
            raise ApiFailure("schema")
        ids.append(row["id"])
    cursor = body.get("next")
    if cursor is not None and (not isinstance(cursor, str) or not cursor):
        raise ApiFailure("schema")
    return ids, cursor


def poll_pages(transport, breaker, max_pages=4, total_ms=400):
    seen = set()
    ids = []
    cursor = None
    deadline = transport.now + total_ms
    for _ in range(max_pages):
        path = "/items" + (("?" + urlencode({"cursor": cursor})) if cursor else "")
        left = deadline - transport.now
        if left <= 0:
            raise ApiFailure("poll_deadline")
        items, cursor = parse_page(
            request(transport, breaker, "GET", path, total_ms=min(left, 240))
        )
        ids.extend(items)
        if cursor is None:
            return ids
        if cursor in seen:
            raise ApiFailure("cursor_loop")
        seen.add(cursor)
    raise ApiFailure("page_cap")

from dataclasses import dataclass
from typing import Callable

from .models import (
    CircuitOpenError,
    HttpTransport,
    IntegrationRequest,
    IntegrationResponse,
    RateLimitExceededError,
    ResponseValidationError,
    RetryNotAllowedError,
)
from .policies import CircuitBreaker, FixedWindowRateLimiter, IntegrationMetrics, RetryPolicy, validate_response


def no_sleep(seconds: float) -> None:
    """Default sleep hook for examples; tests keep it as a no-op."""


@dataclass
class ResilientIntegrationClient:
    transport: HttpTransport
    retry_policy: RetryPolicy
    circuit_breaker: CircuitBreaker
    rate_limiter: FixedWindowRateLimiter
    timeout_seconds: float = 2.0
    metrics: IntegrationMetrics | None = None
    sleep: Callable[[float], None] = no_sleep

    def __post_init__(self) -> None:
        if self.metrics is None:
            self.metrics = IntegrationMetrics()

    def call(self, request: IntegrationRequest, now_epoch: int) -> IntegrationResponse:
        assert self.metrics is not None
        try:
            self.rate_limiter.allow(now_epoch)
            self.circuit_breaker.before_call()
        except (CircuitOpenError, RateLimitExceededError) as exc:
            self.metrics.blocked += 1
            self.metrics.events.append(type(exc).__name__)
            raise

        last_response: IntegrationResponse | None = None
        for attempt in range(1, self.retry_policy.max_attempts + 1):
            self.metrics.attempts += 1
            response = self.transport.send(request, timeout_seconds=self.timeout_seconds)
            last_response = IntegrationResponse(status_code=response.status_code, data=response.data, attempt_count=attempt)
            if last_response.ok:
                try:
                    validate_response(last_response)
                except ResponseValidationError:
                    self.metrics.schema_errors += 1
                    self.circuit_breaker.record_failure()
                    self.metrics.events.append("schema_error")
                    raise
                self.metrics.successes += 1
                self.circuit_breaker.record_success()
                self.metrics.events.append("success")
                return last_response

            self.circuit_breaker.record_failure()
            self.metrics.failures += 1
            if not self.retry_policy.should_retry(last_response, attempt):
                self.metrics.events.append(f"failed_status_{last_response.status_code}")
                return last_response
            if not request.can_retry():
                self.metrics.events.append("retry_not_allowed")
                raise RetryNotAllowedError("request cannot be retried without idempotency")
            self.metrics.retries += 1
            self.metrics.events.append(f"retry_{attempt}")
            self.sleep(self.retry_policy.backoff_seconds * attempt)

        assert last_response is not None
        return last_response

    """Raised when the external service response does not match the contract."""


class Method(str, Enum):
    GET = "GET"
    POST = "POST"
    PUT = "PUT"
    DELETE = "DELETE"

    payload: dict[str, Any]

    data: ResponsePayload
    attempt_count: int

    def ok(self) -> bool:

from __future__ import annotations

from dataclasses import dataclass, field

from .models import CircuitOpenError, IntegrationResponse, RateLimitExceededError, ResponseValidationError


@dataclass(frozen=True)
class RetryPolicy:
    max_attempts: int = 3
    backoff_seconds: float = 0.2
    retry_statuses: tuple[int, ...] = (408, 429, 500, 502, 503, 504)

    def should_retry(self, response: IntegrationResponse, attempt: int) -> bool:
        return attempt < self.max_attempts and response.status_code in self.retry_statuses


@dataclass
class CircuitBreaker:
    failure_threshold: int = 2
    failure_count: int = 0
    opened: bool = False

    def before_call(self) -> None:
        if self.opened:
            raise CircuitOpenError("external dependency circuit is open")

    def record_success(self) -> None:
        self.failure_count = 0
        self.opened = False

    def record_failure(self) -> None:
        self.failure_count += 1
        if self.failure_count >= self.failure_threshold:
            self.opened = True


@dataclass
class FixedWindowRateLimiter:
    limit: int
    window_seconds: int = 60
    _window_start: int | None = None
    _count: int = 0

    def allow(self, now_epoch: int) -> None:
        if self._window_start is None or now_epoch - self._window_start >= self.window_seconds:
            self._window_start = now_epoch
            self._count = 0
        if self._count >= self.limit:
            raise RateLimitExceededError("external dependency rate limit exceeded")
        self._count += 1


@dataclass
class IntegrationMetrics:
    attempts: int = 0
    retries: int = 0
    successes: int = 0
    failures: int = 0
    blocked: int = 0
    schema_errors: int = 0
    events: list[str] = field(default_factory=list)


def validate_response(response: IntegrationResponse) -> None:
    data = response.data
    if not isinstance(data, dict):
        raise ResponseValidationError("response data must be a dict")
    if data.get("status") not in {"ok", "accepted", "degraded"}:
        raise ResponseValidationError("response status must be ok, accepted, or degraded")
    if not isinstance(data.get("payload"), dict):
        raise ResponseValidationError("response payload must be a dict")

Verification

驗收要覆蓋成功與失敗控制面

只測 happy path 無法證明外部整合能上線。

證據圖：240 ms 虛擬預算如何用掉？

  • 503：40 ms
  • 退避：25 ms
  • 成功：55 ms
  • 餘額：120 ms

辨識口徑：240 ms 是設定值，120 ms 是虛擬時鐘中的確定性結果，不是網路實測。整合驗收另記錄延遲分位數、429／逾時比率、嘗試放大倍數、排隊量、資料年齡與斷路轉態。

程式測試包含 503 回復、429 超預算、整輪 timeout、POST 不盲重送、斷路與試探、schema 拒絕、分頁與循環游標、401 不重試。

Troubleshooting

整合問題要先分類再修

timeout、429、5xx、schema drift、非冪等寫入與 circuit open 的處理不同。

從現象找可觀測的原因

429 增加：檢查租戶用量、並行佇列及重試放大；若持續逾額，降低節奏而非加長重試。重複事件：核對交付 ID、去重記錄期間與提交順序。舊資料：量測產生到進站的資料年齡及可靠落地延遲，別只看 HTTP 耗時。

研究實作｜伺服器退避提示遇到客戶端截止時間

遇到 429 或 503 時，不要把外部伺服器的等待提示縮短成自己的剩餘預算，也不要每一層都重試。教材新增可算出確切答案的政策測試，協助分辨「不該重試」和「雖可重試但時間不足」。

項目驗證重點
政策計算503、有冪等保證且剩 180 ms，抖動 30 ms、HTTP-date 換算後剩餘 100 ms：取 100 ms，再加 50 ms 保留量，允許。若改為 429 且剩 120 ms，剩餘預算不足，不能將等待縮為 70 ms。
輸入處理服務端提示缺失或無效時採自己的抖動政策；若合法提示極長且超預算，回報已節流而不是違反提示。429 不必然帶 Retry-After。使用單調時鐘控制總預算，日曆時鐘只用來解讀 HTTP-date。
驗收證據本測試只驗證純政策函式，不是網路整合測試。另用 fake transport 驗證取消能停止等待、pool 等候包含在 deadline、以及上游併發／半開探測沒有突破限制。

def retry_delay(*, status, idempotent, remaining_ms, jitter_ms, retry_after_ms=None):
    """已正規化成毫秒的政策輸入；不是 HTTP client。"""
    if min(remaining_ms, jitter_ms) < 0 or (retry_after_ms is not None and retry_after_ms < 0):
        raise ValueError("negative time")
    if not idempotent or status not in (429, 502, 503, 504):
        return None
    # 預留下一次嘗試至少 50ms；不把伺服器指定等待縮短到預算內。
    delay = max(jitter_ms, retry_after_ms or 0)
    return delay if delay + 50 <= remaining_ms else None

延伸學習：實作、現場案例與自我檢查

本頁說明整合韌性。本節實作斷路器：外部系統連續失敗時暫停呼叫，冷卻時間過後只試探一次，成功才恢復。這能避免外部系統故障時，自己的程式被大量逾時拖垮。

可實跑範例：斷路器狀態變化

連續 3 次失敗後由 closed 轉為 open；open 期間直接略過，不發出請求；冷卻 30 秒後進入 half_open 試探一次，失敗則重新開路，成功則關閉並清除失敗計數。時鐘以參數注入，輸出可重現。 冷卻從實際進入 open 時計算，而不是從失敗請求的送出時刻開始。

下載範例 example.py

"""斷路器：連續失敗後暫停呼叫外部系統，冷卻後試探一次，成功才恢復（標準函式庫，使用模擬時鐘）。"""


class CircuitBreaker:
    def __init__(self, threshold=3, cooldown=30.0, clock=None):
        self.threshold, self.cooldown, self.clock = threshold, cooldown, clock
        self.state, self.failures, self.opened_at = "closed", 0, None

    def call(self, fn):
        now = self.clock()
        if self.state == "open":
            if now - self.opened_at < self.cooldown:
                return "略過（斷路中）"
            self.state = "half_open"
        try:
            result = fn()
        except Exception as e:
            self.failures += 1
            if self.state == "half_open" or self.failures >= self.threshold:
                self.state, self.opened_at = "open", self.clock()  # 冷卻從失敗結束、開路時開始
            return f"失敗：{e}"
        self.state, self.failures = "closed", 0
        return f"成功：{result}"


if __name__ == "__main__":
    t = [0.0]
    up = {"ok": False}

    def energy_api():
        if not up["ok"]:
            raise ConnectionError("能源平台無回應")
        return "上傳 120 筆"

    cb = CircuitBreaker(clock=lambda: t[0])
    timeline = [(0, False), (5, False), (10, False), (15, False), (25, False),
                (41, False), (75, True), (80, True)]
    for at, ok in timeline:
        t[0], up["ok"] = at, ok
        before = cb.state
        print(f"t={at:>3}s 狀態 {before:<9} → {cb.call(energy_api):<16} 之後 {cb.state}")

工程現場案例：能源平台當機，閘道器的本地輪詢也跟著變慢

某閘道器每 5 秒把資料上傳到雲端能源平台，平台當機時每次上傳都要等 10 秒逾時。上傳與本地輪詢在同一個執行緒，結果 Modbus 輪詢週期從 5 秒拉長到 15 秒，本地的需量控制也受到影響。

加上斷路器後，連續 3 次失敗就停止上傳嘗試，資料暫存在本地佇列；每 30 秒試探一次，平台恢復後再補傳。範例的時間軸顯示 15 秒與 25 秒時直接略過、41 秒試探失敗重新開路、75 秒試探成功恢復。

  1. 找出所有呼叫外部系統的地方，為每個外部系統各自建立斷路器。
  2. 開路期間把資料寫入本地持久化佇列，恢復後依序補送。
  3. 斷路器狀態變化寫入日誌並告警。
  4. 本地控制與外部上傳分開執行緒或程序，確保外部故障不影響本地控制。

練習題與自我檢查

  1. 為什麼 half_open 試探失敗時，不需要等失敗次數達到門檻就重新開路？

    看解答

    試探失敗代表外部系統仍未恢復，再多試幾次只會增加負擔。half_open 只允許一次試探，失敗立刻回到 open 並重新計算冷卻時間。

  2. 若把 cooldown 改成 60 秒，75 秒時會發生什麼？

    看解答

    t=10 累積第三次失敗並開路。改成 60 秒後，t=41 還在冷卻期，並未試探或重新開路。t=70 起可試探，但不會自動發出呼叫。本例下一次在 t=75，平台已恢復，試探成功並回到 closed。

  3. 開路期間略過的資料要怎麼處理？

    看解答

    不能丟棄。應寫入本地持久化佇列（例如 SQLite），恢復後依序補送，並以序號或時間戳讓接收端去重。佇列也要有上限與告警。

  4. 多個執行緒共用同一個斷路器時，範例的寫法安全嗎？

    看解答

    不安全。state 與 failures 的讀寫不是原子操作，可能有多個執行緒同時進入 half_open 並發出多次試探。多執行緒環境要加鎖。
