MQTT 深度研究

從採集閘道到歷史資料庫，把 QoS、狀態、重播、權限和驗收分開設計。

01｜工控資料流

  1. 現場控制器本地閉迴路／保護
  2. 採集閘道時間、品質、序號、離線緩衝
  3. MQTT Broker身份、主題授權、轉送
  4. 歷史服務交易寫入、去重、監測

閘道把設備的來源值、量測 UTC 時間、資料品質、單位與來源識別形成事件。監控端優先讀快照和歷史，不以 Broker 可用作為安全聯鎖或控制迴路的前提。事件到達延遲要分為採集週期、閘道排隊、轉送與持久化四段，不用 TCP 往返時間冒充畫面新鮮度。

02｜QoS 不是資料庫交易

級別協定語意（每一段）選用條件
0至多一次；PUBLISH 無該級別的協定回應高頻快照，少量丟失可接受
1至少一次；PUBLISH → PUBACK；可能重複事件需可重送，消費端以穩定事件鍵去重
2恰一次的協定傳遞；PUBLISH → PUBREC → PUBREL → PUBCOMP協定端點確需此語意，且可承受多階段往返與狀態成本

Publisher→Broker 與 Broker→Subscriber 各自交付；訂閱的核准 QoS 是接收上限，不能把原始 QoS 0 提升成交付保證。DUP 描述此連線傳送端是否在重送 PUBLISH，不是業務事件重複判定；Packet Identifier 是協定交換識別，可在交換完成後重用，不是長期全域事件 ID。

需要業務恰一次效果時，讓事件鍵與業務寫入在同一交易提交，並確認客戶端是否能延後確認至提交後。若還要呼叫外部服務，另設發件箱（outbox）及下游冪等鍵，不把 PUBACK 當資料庫提交。

03｜主題、保留訊息與連線狀態

plant/a/gw01/telemetry 承載事件；plant/a/gw01/status 放保留狀態。發布使用具體主題；訂閱篩選器的 + 只匹配一層，末尾 # 匹配多層。

  • Retain：Broker 可保存每主題末筆保留訊息，供後續訂閱取得目前快照，不是事件歷史。保留旗標搭配零位元組載荷可清除該主題的保留訊息。
  • Session：以 Client ID 識別，Session Expiry 決定中斷後保留狀態多久，Clean Start 決定本次是否捨棄舊狀態；查 CONNACK 的 Session Present，不假定續接成功。
  • Birth / LWT：連線成功後由應用發布 retained online；CONNECT 先設定 Will（遺囑）作為異常離線訊號。正常停機若想留下 offline，應主動發布再正常斷線。Will Delay 可減少短斷抖動；失聯警示仍應加心跳／超時與資料年齡，不以 retained online 推定仍在線。
  • Expiry：Message Expiry 限制 Broker 儲存及轉送的時效，與 Session Expiry 分開。閘道重播仍要用量測時間重算剩餘 TTL，消費端也要拒絕過期或不合理的未來時間。

04｜離線重播與冪等落地

  1. 產生事件鍵source + epoch + seq
  2. 記錄送出前資料有限磁碟、剩餘時效
  3. 復線分批補送保留原鍵與量測時間
  4. 交易式寫入重複略過、衝突告警

epoch 在每次真正重建序號域時更換，傳輸重連不重建；若暫存跨重開機，重播原 epoch/seq、不重新編號。序號可偵測同一 epoch 的缺口，不可把不同 epoch 的序號直接比較。晚到的舊 epoch 歷史事件不能直接覆寫目前快照，需另有快照新鮮度規則與時間同步。重播保持限速、磁碟上限、可觀察的丟棄與缺口告警。

本例由消費端用「現在時間減量測時間」判定樣本時效，接受 −5 至 30 秒（含端點）。量測時間快超過 5 秒回報 future-clock-skew；量測已超過 30 秒回報 expired。時效先於入庫與查重，所以同一事件超出時效時，不會再判斷是重複或衝突。這不是 MQTT 5 的 Message Expiry Interval：後者是 MQTT 訊息的存活期限，不依應用資料內的量測時間計算。

完整 Python 離線練習：寫入、重送、衝突、時間偏移、重開機
from dataclasses import dataclass
import sqlite3


@dataclass(frozen=True)
class Sample:
    source: str
    epoch: str
    seq: int
    measured_at: int
    milli_c: int


def store(db, msg: Sample, now: int) -> str:
    # 教學只接受單一已知來源；正式環境須把身份對應到 topic 與 source。
    if msg.source != "gw01" or msg.seq < 0 or not msg.epoch:
        return "invalid"
    age_s = now - msg.measured_at
    if age_s < -5:
        return "future-clock-skew"
    if age_s > 30:
        return "expired"
    key = (msg.source, msg.epoch, msg.seq)
    data = (msg.measured_at, msg.milli_c)
    with db:
        inserted = db.execute(
            "INSERT INTO samples VALUES (?, ?, ?, ?, ?) "
            "ON CONFLICT(source, epoch, seq) DO NOTHING", key + data
        ).rowcount
        if inserted:
            return "inserted"
        saved = db.execute(
            "SELECT ts, value FROM samples WHERE source=? AND epoch=? AND seq=?",
            key
        ).fetchone()
        return "duplicate" if saved == data else "identity-conflict"


def main():
    db = sqlite3.connect(":memory:")
    try:
        db.execute("""CREATE TABLE samples (
          source TEXT, epoch TEXT, seq INTEGER, ts INTEGER, value INTEGER,
          PRIMARY KEY (source, epoch, seq))""")
        now = 1000  # 固定秒數，讓邊界情境可重現
        a = Sample("gw01", "boot-A", 3, now, 22_500)
        bad = Sample("gw01", "boot-A", 3, now, 99_000)
        late = Sample("gw01", "boot-A", 2, now - 31, 22_300)
        future = Sample("gw01", "boot-A", 4, now + 6, 22_400)
        oldest_ok = Sample("gw01", "boot-A", 5, now - 30, 22_400)
        fastest_ok = Sample("gw01", "boot-A", 6, now + 5, 22_400)
        next_boot = Sample("gw01", "boot-B", 3, now, 22_600)
        cases = (a, a, bad, late, future, oldest_ok, fastest_ok, next_boot)
        results = [store(db, x, now) for x in cases]
        assert results == [
            "inserted", "duplicate", "identity-conflict", "expired",
            "future-clock-skew", "inserted", "inserted", "inserted"
        ]
        assert store(db, a, now + 31) == "expired"
        assert store(db, bad, now - 6) == "future-clock-skew"
        assert db.execute(
            "SELECT epoch, seq FROM samples ORDER BY epoch, seq"
        ).fetchall() == [("boot-A", 3), ("boot-A", 5), ("boot-A", 6), ("boot-B", 3)]
        print(" / ".join(results))
    finally:
        db.close()


if __name__ == "__main__":
    main()

範例僅走記憶體 SQLite，沒有連線、密碼或現場資料。它證明事件鍵與保存行為，沒有模擬 MQTT 握手、Broker 訊息過期、客戶端確認時機或程序崩潰後持久性。正式環境另驗證 SQLite／資料庫持久化、交易隔離、次序與訊息 ACK 邊界。

05｜TLS、ACL 與容量

  • 驗證伺服器憑證和名稱；裝置具有獨立可輪替身份，依需要使用 mTLS。TLS 是每段連線的防護，Broker 及可讀資料方仍需納入信任邊界。
  • 以主題 ACL 分離發布與訂閱：閘道僅寫自己資料與狀態，監看器僅讀必要範圍；不共用帳號，不給監看端控制寫入或全域萬用字元。
  • 依實際負載設定封包、QoS 1/2 同時在途數、訂閱及離線佇列的上限；收集佇列水位、重送、拒絕、磁碟及新鮮度。安全與控制流各自測試。

延伸學習：實作、現場案例與自我檢查

可實跑範例：主題比對、Remaining Length 與冪等落地

不需要 broker，直接執行即可看到結果。topic_matches() 依 MQTT 規格處理 +、# 與 $ 開頭的系統主題；encode_remaining_length() 可對照規格的編碼表；IdempotentSink 以（裝置, 序號）去重，並檢查序號缺口。

下載範例 example.py

"""MQTT 主題過濾、Remaining Length 編碼與 QoS 1 重複投遞的冪等落地（標準函式庫模擬）。"""


def topic_matches(topic_filter: str, topic: str) -> bool:
    """依 MQTT 規則比對：+ 比對單一層級，# 只能在最後、比對其後所有層級。"""
    f_parts, t_parts = topic_filter.split("/"), topic.split("/")
    if topic.startswith("$") and topic_filter[:1] in ("+", "#"):
        return False                      # $SYS 等系統主題不被開頭的萬用字元匹配
    for i, part in enumerate(f_parts):
        if part == "#":
            if i != len(f_parts) - 1:
                raise ValueError("# 只能出現在過濾字串最後一層")
            return True
        if i >= len(t_parts):
            return False
        if part != "+" and part != t_parts[i]:
            return False
    return len(f_parts) == len(t_parts)


def encode_remaining_length(n: int) -> bytes:
    """MQTT 可變長度整數：每位元組 7 bits，最高位表示後面還有位元組，最多 4 位元組。"""
    if not 0 <= n <= 268_435_455:
        raise ValueError("超出 MQTT 允許範圍")
    out = bytearray()
    while True:
        byte, n = n % 128, n // 128
        out.append(byte | (0x80 if n else 0))
        if not n:
            return bytes(out)


class IdempotentSink:
    """QoS 1 是「至少一次」：同一則訊息可能重送，落地端以 (裝置, 序號) 去重。"""

    def __init__(self):
        self.seen: set[tuple[str, int]] = set()
        self.rows: list[tuple[str, int, float]] = []

    def handle(self, device: str, seq: int, value: float) -> str:
        key = (device, seq)
        if key in self.seen:
            return "重複，略過"
        self.seen.add(key)
        self.rows.append((device, seq, value))
        return "寫入"


if __name__ == "__main__":
    cases = [
        ("site/+/ahu/+/sat", "site/b1/ahu/01/sat"),
        ("site/+/ahu/+/sat", "site/b1/ahu/01/rat"),
        ("site/b1/#", "site/b1/chiller/02/kw"),
        ("site/b1/#", "site/b1"),
        ("+/b1/ahu/01/sat", "site/b1/ahu/01/sat"),
        ("#", "$SYS/broker/uptime"),
    ]
    for f, t in cases:
        print(f"{f:<18} vs {t:<24} -> {topic_matches(f, t)}")

    for n in (0, 127, 128, 16_383, 16_384, 2_097_152):
        print(f"Remaining Length {n:>9,} -> {encode_remaining_length(n).hex(' ')}")

    sink = IdempotentSink()
    # 斷線重連後 broker 重送了序號 1002（DUP 旗標），且到達順序與送出順序不同
    deliveries = [("AHU-01", 1001, 13.2), ("AHU-01", 1002, 13.4), ("AHU-01", 1002, 13.4),
                  ("AHU-01", 1004, 13.9), ("AHU-01", 1003, 13.6)]
    for d in deliveries:
        print(f"收到 {d} -> {sink.handle(*d)}")
    seqs = sorted(r[1] for r in sink.rows)
    gaps = [s for s in range(seqs[0], seqs[-1] + 1) if s not in seqs]
    print(f"落地 {len(sink.rows)} 筆，序號缺口：{gaps or '無'}")

工程現場案例：閘道器重連後，趨勢圖出現重複點與跳點

某棟大樓的 Modbus 轉 MQTT 閘道器以 QoS 1 上傳空調箱送風溫度。4G 線路斷線重連後，broker 重送了未確認的訊息，歷史資料庫因此多出重複點；另一方面，閘道器本機緩衝在重連時又以不同順序補送，趨勢圖出現時間倒退。

根本原因是落地端把「收到一則訊息」當成「新增一筆資料」。QoS 1 只保證至少送達一次，不保證只送一次，也不保證跨連線的順序。解法是在 payload 帶裝置序號與量測時間戳，落地端以（裝置, 序號）做唯一鍵，排序依量測時間而不是到達時間。

  1. 在閘道器的 payload 加入單調遞增序號與量測時間（UTC），不要用 broker 收到的時間當資料時間。
  2. 資料庫以（device_id, seq）建立唯一索引，寫入採 INSERT … ON CONFLICT DO NOTHING 或等效語法。
  3. 定期檢查序號缺口，缺口代表遺失而不是延遲，要觸發補抓或告警。
  4. 主題設計保留層級語意（site/棟/設備類型/編號/點位），訂閱端用 + 過濾，避免用 # 訂閱整棵樹。

練習題與自我檢查

  1. site/b1/# 會不會匹配 site/b1？site/+/# 會不會匹配 site？請先判斷再用 topic_matches() 驗證。

    看解答

    site/b1/# 會匹配 site/b1，因為 # 也代表父層本身。site/+/# 不匹配 site，因為 + 必須對應一個實際存在的層級。

  2. 一則 payload 為 200 bytes 的 PUBLISH 封包，Remaining Length 需要幾個位元組？

    看解答

    Remaining Length 包含可變標頭與 payload，總長度介於 128 到 16,383 之間，需要 2 個位元組。可以用 encode_remaining_length() 代入實際長度確認。

  3. IdempotentSink 把已見過的鍵全部放在記憶體的 set 裡。長時間運作會有什麼問題？怎麼改？

    看解答

    set 會無限成長。實務上應由資料庫唯一索引負責去重；若要在記憶體快取，只保留每台裝置最近 N 個序號或最近一段時間的鍵，並在程序重啟後以資料庫為準。

  4. 序列圖中，若歷史服務改成「先回 PUBACK、再 INSERT」，程序剛好在兩步之間當機，會發生什麼事？為什麼本頁堅持在提交後才確認？

    看解答

    Broker 收到 PUBACK 就認定這則訊息已交付，從 Session 狀態刪除，不會再重送；資料庫卻沒有這筆，結果等同「至多一次」，而且沒有任何協定訊號提醒遺失，只能靠序號缺口檢查發現。先提交、後確認時，最壞情況是提交後尚未送出 PUBACK 就斷線，Broker 重送一次，由唯一鍵擋成 duplicate，可被安全吸收。

  5. 為什麼 # 開頭的訂閱不應該收到 $SYS/broker/uptime？

    看解答

    MQTT 規格規定以 $ 開頭的主題保留給 broker 內部使用，開頭為萬用字元的過濾不可匹配它們。要訂閱系統主題必須明確寫出 $SYS/…。
