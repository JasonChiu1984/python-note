設備稼動率怎麼算？

先選定分母，再把運轉、停止與資料未知拆開，最後才比較設備或班別。以合成冰機運轉回授與重疊排程做完整練習。

指標口徑時間切片算例與圖表Python 實作

01｜指標口徑不能混用

指標定義不要混成
日曆運轉占比整個觀測窗的運轉分鐘 ÷ 觀測窗分鐘。不代表設備都需要開機；備援或負載不足時停機可以正常。
排程內運轉占比回授運轉與排程交集的分鐘 ÷ 排程聯集分鐘。不要用整天運轉分鐘除排程分鐘；排程外運轉另列。
服務可用率依事先約定的應服務時段、就緒條件及可服務時間計算；以心跳、測試或故障紀錄佐證。可用的備機不必正在運轉。BMS 連線正常也不能證明有能力供冷。
製造 OEE常用模型為可用率 × 效率 × 良率。效率需理想節拍與實際產出；良率需合格品和總產量。不能把冰機運轉回授當作製造產量，也不應憑空填入兩項為 100%。
部分負載比（PLR）明示能力基準後，以同時段實際冷量 ÷ 基準冷量。PLR 是負載程度，不是時間占比；能力若會隨條件變化，也要標註基準。

本課把「稼動率」拆成日曆及排程兩個口徑。兩者都以實際運轉回授判斷，而非啟動命令。命令 ON、回授 OFF 是待診斷狀態，不能算運轉；命令不變且回授失聯也不能算停機。

02｜時間切片：回授失效即改列未知

  1. 統一時間基準UTC 事件、明示廠區時區與班表
  2. 整理變更事件重複同值去重、同戳異值交給來源裁決
  3. 切成半開區間狀態、時效及排程邊界都可切片
  4. 分三類加總運轉／停止／未知，排程先取聯集

以 [start,end) 計算，左閉右開使接續的報表不重複計入邊界事件。先找左端點前最後一次回授；仍在有效期限內才承接。範例的每次回授有效 15 分鐘，過期、壞品質或沒有回授都記為未知。正式系統應由來源更新機制決定 TTL：若系統只上報狀態變更，需另有心跳或品質來源以續證新鮮度。

覆蓋率＝（運轉＋停止）÷ 目標時窗。只在已知資料中的運轉占比＝運轉÷已知時間，不能代替全時窗。全時窗運轉占比的下／上界＝運轉÷總時間，與（運轉＋未知）÷總時間；不是統計信賴區間。無排程、分母為零時回傳無資料。

03｜合成算例：未知 10 分鐘不能當成停機

觀測 [0,60)；排程 [5,25) 與 [20,50) 取聯集是 [5,50)。窗前 −5 分鐘已啟動，10 分鐘續證運轉，20 分鐘停止，35 分鐘過期，37 分鐘報品質不良，45 分鐘恢復運轉。60 分鐘停止事件放到下一窗，不影響本窗。

範圍運轉／停止／未知覆蓋率已知運轉占比全窗可能範圍
日曆 60 分鐘35／15／10 分83.3%70.0%58.3–75.0%
排程 45 分鐘20／15／10 分77.8%57.1%44.4–66.7%

跨設備總覽應視場景決定是加總設備分鐘，還是只算「至少一台可服務」的系統時間聯集；兩者分母不同。

"""合成運轉回授範例。時間以同一時間基準的整數分鐘表示，不連設備。"""
from dataclasses import dataclass
from fractions import Fraction
import json
import unittest
from bisect import bisect_right


@dataclass(frozen=True)
class Event:
    minute: int
    running: bool | None


def merge_schedule(spans, start, end):
    """先裁切再取聯集，避免重疊排程重複計時。"""
    selected = []
    for left, right in spans:
        if left >= right:
            raise ValueError("排程區間須有正長度")
        lo, hi = max(left, start), min(right, end)
        if lo < hi:
            selected.append((lo, hi))
    out = []
    for lo, hi in sorted(selected):
        if out and lo <= out[-1][1]:
            out[-1] = (out[-1][0], max(hi, out[-1][1]))
        else:
            out.append((lo, hi))
    return out


def utilization(events, schedule, start, end, ttl):
    """回授適用 [event, event+ttl)；None 是立即失效，不是停機。"""
    if not start < end or ttl <= 0:
        raise ValueError("須有正長度觀測窗與正數時效")
    samples = {}
    for event in events:
        if event.minute >= end:
            continue  # 位於右端點的事件屬於下一窗
        if event.minute in samples and samples[event.minute] is not event.running:
            raise ValueError("同時戳回授衝突，須先由來源裁決")
        samples[event.minute] = event.running
    times = sorted(samples)
    spans = merge_schedule(schedule, start, end)
    cuts = {start, end}
    cuts.update(t for lo, hi in spans for t in (lo, hi))
    cuts.update(t for event_t in times for t in (event_t, event_t + ttl)
                if start < t < end)
    timeslices = sorted(cuts)
    sums = {scope: {"run": 0, "stop": 0, "unknown": 0}
            for scope in ("calendar", "schedule")}
    trace = []
    for left, right in zip(timeslices, timeslices[1:]):
        idx = bisect_right(times, left) - 1
        state = (samples[times[idx]]
                 if idx >= 0 and left < times[idx] + ttl else None)
        status = "run" if state is True else "stop" if state is False else "unknown"
        planned = any(lo <= left < hi for lo, hi in spans)
        sums["calendar"][status] += right - left
        if planned:
            sums["schedule"][status] += right - left
        trace.append({"start": left, "end": right, "status": status, "planned": planned})
    return sums, trace


def fractions(time):
    run, stop, unknown = (time[key] for key in ("run", "stop", "unknown"))
    total, known = run + stop + unknown, run + stop
    return {
        "coverage": Fraction(known, total) if total else None,
        "known_only": Fraction(run, known) if known else None,
        "lower": Fraction(run, total) if total else None,
        "upper": Fraction(run + unknown, total) if total else None,
    }


FIXTURE = (
    Event(-5, True), Event(10, True), Event(10, True), Event(20, False),
    Event(37, None), Event(45, True), Event(60, False)
)
SCHEDULE = [(5, 25), (20, 50)]


class LabTests(unittest.TestCase):
    def test_aggregate_and_half_open(self):
        sums, trace = utilization(FIXTURE, SCHEDULE, 0, 60, 15)
        self.assertEqual(sums["calendar"], {"run": 35, "stop": 15, "unknown": 10})
        self.assertEqual(sums["schedule"], {"run": 20, "stop": 15, "unknown": 10})
        self.assertEqual(fractions(sums["schedule"])["upper"], Fraction(2, 3))
        self.assertEqual(trace[-1]["status"], "run")

    def test_stale_and_quality_edge(self):
        sums, trace = utilization([Event(-10, True), Event(2, True), Event(3, None),
                                   Event(5, False)], [], 0, 10, 3)
        self.assertEqual(sums["calendar"], {"run": 1, "stop": 3, "unknown": 6})
        self.assertIsNone(fractions(sums["schedule"])["coverage"])

    def test_conflicting_duplicates(self):
        with self.assertRaises(ValueError):
            utilization([Event(1, True), Event(1, False)], [], 0, 4, 3)


if __name__ == "__main__":
    import sys
    if "--test" in sys.argv:
        unittest.main(argv=["lab"])
    else:
        counts, trace = utilization(FIXTURE, SCHEDULE, 0, 60, 15)
        result = {scope: dict(minutes=value, fractions=fractions(value))
                  for scope, value in counts.items()}
        print(json.dumps(dict(result=result, trace=trace), default=str,
                         ensure_ascii=False, indent=2))

延伸學習：實作、現場案例與自我檢查

前面說明「未知不能當停機」。本節把它延伸到完整的 OEE：可用率、效能、品質三項分別怎麼算，以及未知時段對結果的影響。

可實跑範例：從狀態事件計算 OEE

輸入是一串（開始時間, 狀態）事件，程式算出各狀態的累計時間，再依可用率 × 效能 × 品質計算 OEE。閘道器斷線的 20 分鐘列為 unknown，不放進分母。

下載範例 example.py

"""由狀態事件紀錄計算稼動率與 OEE，並把「未知」時段獨立列出（標準函式庫）。"""
from datetime import datetime, timedelta

PLANNED = (datetime(2026, 11, 20, 8, 0), datetime(2026, 11, 20, 16, 0))   # 計畫生產 8 小時
EVENTS = [                     # (開始時間, 狀態)；狀態持續到下一筆事件
    ("08:00", "run"), ("09:40", "stop_changeover"), ("10:10", "run"),
    ("12:00", "unknown"),      # 閘道器斷線，無回授
    ("12:20", "run"), ("14:05", "stop_fault"), ("14:50", "run"),
]
IDEAL_CYCLE_S = 30            # 理想節拍：每件 30 秒
GOOD, TOTAL = 690, 720        # 良品數、總產出


def durations():
    day = PLANNED[0].date()
    times = [datetime.combine(day, datetime.strptime(t, "%H:%M").time()) for t, _ in EVENTS]
    times.append(PLANNED[1])
    acc: dict[str, timedelta] = {}
    for (start, end), (_, state) in zip(zip(times, times[1:]), EVENTS):
        acc[state] = acc.get(state, timedelta()) + (end - start)
    return acc


if __name__ == "__main__":
    acc = durations()
    planned = PLANNED[1] - PLANNED[0]
    for state, d in sorted(acc.items()):
        print(f"{state:<17} {d}")
    unknown = acc.get("unknown", timedelta())
    run = acc.get("run", timedelta())
    known = planned - unknown
    availability = run / known
    performance = TOTAL * IDEAL_CYCLE_S / run.total_seconds()
    quality = GOOD / TOTAL
    print(f"未知時段 {unknown}（占計畫 {unknown / planned:.1%}），不列入分母也不算停機")
    print(f"可用率 A = {run} ÷ {known} = {availability:.1%}")
    print(f"效能 P = {TOTAL} × {IDEAL_CYCLE_S}s ÷ {run} = {performance:.1%}")
    print(f"品質 Q = {GOOD} ÷ {TOTAL} = {quality:.1%}")
    print(f"OEE = {availability * performance * quality:.1%}")
    print(f"若把未知當停機：A = {run / planned:.1%}，OEE = {run / planned * performance * quality:.1%}")

工程現場案例：OEE 因通訊中斷被低估 3 個百分點

範例中閘道器在 12:00–12:20 斷線。若把這 20 分鐘當成停機，可用率從 83.7% 降到 80.2%，OEE 從 75.0% 降到 71.9%。這 3 個百分點會讓產線看起來比實際差，也可能讓維修團隊去追一個不存在的故障。

反過來，若把斷線期間當成運轉，同樣會高估。正確做法是單獨列出 unknown，並在報表上寫明涵蓋率；unknown 比例過高時，先處理資料收集問題，再談改善稼動率。

  1. 確認狀態訊號來源：PLC 的運轉位元、電流門檻，或 MES 的工單狀態，各自的延遲與可靠度不同。
  2. 停機原因代碼要在現場輸入或由 PLC 給出，不要事後在報表上補。
  3. 理想節拍以設備規格或最佳實績為準，並在報表上註明，避免各班別用不同標準。
  4. unknown 比例超過 2% 時，先檢查閘道器、網路與緩衝設定。

  • OEE 與可用率、效能、品質的定義可參考 ISO 22400-2（製造營運管理 KPI）。各公司常有自己的口徑，例如計畫停機是否列入分母，報表必須寫明採用哪一種。 來源：ISO 22400-2

練習題與自我檢查

  1. 若理想節拍改成 28 秒，效能與 OEE 會變成多少？

    看解答

    P = 720 × 28 ÷ 23,100 = 87.3%；OEE = 83.7% × 87.3% × 95.8% ≈ 70.0%。理想節拍越嚴格，效能越低，所以跨產線比較時必須用相同的節拍定義。

  2. 效能 P 有可能超過 100% 嗎？如果出現，代表什麼？

    看解答

    計算上可能，但通常代表理想節拍設得太寬鬆、產出計數重複，或運轉時間少算（例如 unknown 期間其實在生產）。應檢查資料而不是接受超過 100% 的結果。

  3. 修改 EVENTS，讓 14:05 的故障停機改為 14:05–14:20 故障、14:20–14:50 待料，結果哪些數字會變？

    看解答

    只有狀態分類變了（stop_fault 15 分鐘、新增 30 分鐘待料），運轉時間不變，所以 A、P、Q 與 OEE 都不變。差別在停機原因分析：故障與待料的改善對象完全不同。

  4. 為什麼 durations() 要把 PLANNED 的結束時間加到時間清單最後？

    看解答

    最後一筆事件（14:50 run）沒有下一筆事件可以當結束時間，必須用計畫結束時間 16:00 截斷，否則最後一段運轉時間會漏算。
