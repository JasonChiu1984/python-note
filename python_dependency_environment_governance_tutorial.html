把環境與依賴做成可交付的專案契約

交付時不只要交程式碼，也要回答「用哪個 Python、依賴版本由誰審查、裝的是哪個成品、如何證明目標端真的能啟動」。以下從宣告、鎖定、離線成品到驗收證據拆成可重做步驟。原有 34 張互動複習卡與進度保留在下方。

可交付契約的四個階段

  1. 輸入宣告專案直接依賴、Python 範圍、build backend 與環境 marker。
  2. 解析與固定在明確目標環境求解 transitive closure，審查版本、來源與雜湊。
  3. 受控成品只保留目標 ABI／平台可用 wheels、清單與可信摘要。
  4. 驗收與保存乾淨 venv 離線安裝、pip check、入口測試與報告；保留回退包。

定義的是交付契約，不是「我的電腦可以啟動」。venv 隔離 Python 套件目錄，不固定 OS、底層系統函式庫、CPU、憑證或其他執行參數。以明確的 Python 執行檔建立虛擬環境，避免複製 .venv 到另一台機器；切換 shell 不是隔離的必要條件。

物件責任重跑與維護成本不足之處
宣告pyproject.toml 標明直接依賴與支援範圍。需求改動時更新；可套多環境。不固定解出的完整版本或成品。
constraints在同一解析中限制被要求套件的版本。適合跨服務統一相容範圍，需定期更新。只限制版本，不會要求安裝該套件。
lock／核准清單每個目標對應已求解版本、來源候選與預期雜湊；內容依鎖格式。依平台與相依更新重解析並看差異。不等於已準備離線成品，也不保證 OS／外部動態庫。
wheelhouse本地預備可安裝的 wheel 目錄。占儲存成本，讓部署無需重新下載；按 ABI 管理。沒有核准版本／雜湊檢查時仍可能選到錯誤內容。
驗收證據pip inspect、pip check、真實匯入／CLI smoke、建置資訊、測試結果。每次部署重新保存，利於追蹤。報告不是來源認證，不應包含私有 index URL、認證資料或機密。

雜湊驗證比較的是檔案位元組；當雜湊清單與套件可一併被改寫時，無法證明來源，也不是簽章。由受信管道驗證核准清單或政策要求的 attestation，並將候選成品與那份清單綁定。pip freeze 是當下已裝環境的快照，不是解析器輸出的多目標 lock，也可能包含開發套件與本機路徑。

工具定位

  • venv 建執行環境；pip 解析、下載、安裝檔案及讀取安裝證據，pip lock 在查核所見文件仍標示實驗性，產出的 lock 只保證當前 Python 版本及平台。
  • pip-tools 的 pip-compile 依輸入產生 pinned requirements，可加入 hashes；在目標一致的環境解析並審查。uv 的 uv.lock 是 uv 專案流程產品，Poetry 使用 poetry.lock；不要假設 pip 可直接讀它們。需要互通時核對工具、版本與支援格式，pylock.toml 有 PyPA 規格但不代表每種工具已支援相同功能。目前 pip 文件把 pip install -r pylock.toml 的支援也標為實驗性；使用前核對目標端工具版本並實測。uv sync --locked 不允許更新鎖檔，鎖檔過期會失敗；--frozen 使用既有鎖檔，但不檢查它與專案宣告是否一致。CI 要偵測依賴宣告與鎖檔漂移時，用 --locked。pip install 文件 · uv 鎖定與同步文件。
  • build 驅動 PEP 517 後端出成品，不替應用程式決定依賴鎖；pip check 驗已裝依賴的中繼資料是否相容，不掃漏洞也不驗雜湊。

平台契約｜marker、Python 門檻與 ABI 分開

  • requires-python 聲明發行包可搭配哪些 Python 版本，不能固定執行端一定使用哪個 Python。
  • 環境 marker 以 PEP 508 條件決定本次依賴是否適用，例如 Python 版本或 OS；marker 不是 wheel tag。python_version 是 major.minor，需比較修補版時另使用合適欄位。
  • wheel tag 是 Python tag、ABI tag、平台 tag 的組合。py3-none-any 可表示無特定 ABI 與平台的 Python 3 wheel，但仍要看 Requires-Python 和依賴。cp313-cp313-… 不等於 free-threaded cp313-cp313t-…。不要直接把 macOS arm64 產物搬到 Linux x86_64，也要看 manylinux/musllinux 等平台基線。
  • sysconfig.get_platform() 是執行環境識別的一個訊號，不是完整的 wheel 相容 tag 集合；需要判斷候選時以對應的安裝器或 packaging.tags.sys_tags() 為準，並在目標 Python 實際安裝／匯入。

範例專案｜鎖定、準備成品與驗收

以下是 Linux／CPython 3.11 目標的工作範例。先準備兩個檔案和已核准的建置工具（pip-tools、build 與明確版本的 build backend）；建置與取依賴可使用經核准的內部來源，目標安裝不現場重新解析來源版本。實際門檻以自己專案的支援矩陣為準。不是本文的離線實驗實測結果。

範例的 [build-system] 表達最低可用後端，並不鎖定建置輸入。正式釋出要在受控工具環境固定建置工具及間接依賴；本例用 python -m build --no-isolation，需先在該環境依鎖檔安裝好後端及必要建置依賴。範例用 typing-extensions 只用來示範 marker，不是套件的必要功能。

2. 生成核准候選、目標驗收

set -eu
# 受控建置端；TOOLS 指向已由工具鎖檔建立的虛擬環境
"$TOOLS/bin/python" -m piptools compile --generate-hashes   --output-file requirements.lock pyproject.toml
"$TOOLS/bin/python" -m pip download --require-hashes   --only-binary=:all: -r requirements.lock -d wheelhouse
"$TOOLS/bin/python" -m build --no-isolation --wheel --outdir wheelhouse

# 目標端；先核驗鎖檔及 app wheel SHA-256 的已核准來源
printf '%s  %s\n' "$APP_SHA256" wheelhouse/env_contract_demo-0.1.0-py3-none-any.whl   | sha256sum --check -
python3.11 -m venv .venv
PY="$PWD/.venv/bin/python"
"$PY" -m pip install --no-index --find-links wheelhouse --only-binary=:all:   --require-hashes -r requirements.lock
"$PY" -m pip install --no-index --no-deps wheelhouse/env_contract_demo-0.1.0-py3-none-any.whl
"$PY" -m pip check
"$PY" -I -c 'from env_contract_demo import smoke; assert smoke()'
"$PY" -m pip inspect > installed-evidence.json

範例 APP_SHA256 需先由可信發布紀錄取得；不能從同一不可信 wheel 現算再當核准值。使用 --require-hashes 時，所有依賴（含間接相依）都須釘選並附預期檔案雜湊。部署輸入的鎖檔應經審查、不得含網路 direct URL、VCS 或他人可改寫的本地路徑；若需保證真正離線，另以隔離網路作防護，--no-index 只關索引，不阻擋所有可能的直接 URL。每個目標平台應生成對應 wheelhouse；建置端缺 wheel 時停止，改在批准的建置管線出成品，不偷偷允許目標端從來源建置。Windows 採 .venv\Scripts\python.exe，雜湊驗證命令也須換成受控等效方案。

3. CI 配置（驗收 job；不發布）

先將已審核的鎖檔、wheelhouse 與 app SHA-256 準備妥當，本範例假設由受控 checkout／流程輸入取得；不應將大型 wheel 任意提交。正式版釘選 Action commit；依目標分 job、保留受控證據。setup-python 與 checkout 可以用網路，承諾離線的是最後的成品安裝階段。

name: Verify approved offline contract
on: [workflow_dispatch]
permissions:
  contents: read
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - name: Verify pre-staged artifacts and smoke
        env:
          APP_SHA256: ${{ vars.APP_SHA256 }}
        shell: bash
        run: |
          set -euo pipefail
          test -n "$APP_SHA256"
          wheel="wheelhouse/env_contract_demo-0.1.0-py3-none-any.whl"
          printf '%s  %s\n' "$APP_SHA256" "$wheel" | sha256sum --check -
          python -m venv .venv
          py="$PWD/.venv/bin/python"
          "$py" -m pip install --no-index --find-links wheelhouse --only-binary=:all: --require-hashes -r requirements.lock
          "$py" -m pip install --no-index --no-deps "$wheel"
          "$py" -m pip check
          "$py" -I -c 'from env_contract_demo import smoke; assert smoke()'
          "$py" -m pip inspect > installed-evidence.json

流程圖｜正常、失敗到回退

  1. 設定目標Python 小版本、實作、OS、架構與 runtime image。
  2. 更新鎖定在受控建置端解析；以目標矩陣分別核准差異。
  3. 準備成品下載或建置選定 wheels；留鎖檔和摘要。
  4. 隔離驗收離線驗雜湊並安裝，測 API／CLI、必要的 ABI 匯入。
  5. 核准或回退證據不符停止；改用已核准舊成品組合，不現場重解。
驗收停點
症狀原因範圍安全處置
No matching distributionABI、Requires-Python、架構、OS／libc 或 wheelhouse 缺件。核對目標 tag 與鎖定版本；在正確 runner 補建，不切換到未核准來源。
SHA-256 不符檔案損壞、候選錯誤或來源不可信。停止安裝，查可信清單及儲存紀錄；不隨意更新雜湊來過關。
安裝過了、啟動失敗缺外部 DLL／共享函式庫、原生 ABI 或應用環境錯誤。在乾淨目標環境做實際入口與原生匯入，不能用 pip check 取代。
升級後不相容需求變更、新的可見 API 或部署環境與驗收不一致。隔離候選，回退到先前核准的 runtime＋lock＋wheelhouse；設定／資料遷移另驗相容性。

逐環境留：Python/實作/版本、OS 架構與映像 ID、工具與鎖檔版本、核准成品摘要、測試日期／結果、事故與回退證據。不把開發環境 pip freeze 當正式回退檔。

from __future__ import annotations

from dataclasses import dataclass
import json
from pathlib import Path
import re
import sys
from typing import Iterable


PINNED_RE = re.compile(r"^[A-Za-z0-9_.-]+==[A-Za-z0-9_.!+-]+$")


class GovernanceError(ValueError):
    """Raised when dependency governance rules are violated."""


@dataclass(frozen=True)
class RuntimePolicy:
    minimum_python: tuple[int, int]
    recommended_python: tuple[int, int]
    preview_python: str
    requires_venv: bool


DEFAULT_RUNTIME_POLICY = RuntimePolicy(
    minimum_python=(3, 11),
    recommended_python=(3, 14),
    preview_python="3.15.0b1",
    requires_venv=False,
)


def _read_lines(path: Path) -> list[str]:
    return [
        line.strip()
        for line in path.read_text(encoding="utf-8").splitlines()
        if line.strip() and not line.strip().startswith("#")
    ]


def _parse_requirement_names(lines: Iterable[str]) -> list[str]:
    names: list[str] = []
    for line in lines:
        if line.startswith("-r "):
            continue
        name = re.split(r"[<>=!~]", line, maxsplit=1)[0].strip()
        if not name:
            raise GovernanceError(f"Invalid requirement line: {line}")
        names.append(name)
    return names


def _ensure_pinned(lines: Iterable[str]) -> None:
    for line in lines:
        if line.startswith("-r "):
            continue
        if not PINNED_RE.match(line):
            raise GovernanceError(f"Dependency is not pinned: {line}")


def evaluate_governance(base_dir: Path, runtime_policy: RuntimePolicy = DEFAULT_RUNTIME_POLICY) -> dict:
    requirements = _read_lines(base_dir / "requirements.txt")
    requirements_dev = _read_lines(base_dir / "requirements-dev.txt")
    constraints = _read_lines(base_dir / "constraints.txt")

    _ensure_pinned(requirements)
    _ensure_pinned(requirements_dev)
    _ensure_pinned(constraints)

    if not requirements_dev or requirements_dev[0] != "-r requirements.txt":
        raise GovernanceError("requirements-dev.txt must start with '-r requirements.txt'")

    prod_names = _parse_requirement_names(requirements)
    dev_names = _parse_requirement_names(requirements_dev)
    constraint_names = set(_parse_requirement_names(constraints))

    missing_constraints = sorted((set(prod_names) | set(dev_names)) - constraint_names)
    if missing_constraints:
        raise GovernanceError(
            f"constraints.txt is missing pinned packages: {', '.join(missing_constraints)}"
        )

    python_runtime = f"{sys.version_info.major}.{sys.version_info.minor}.{sys.version_info.micro}"
    runtime_ok = (sys.version_info.major, sys.version_info.minor) >= runtime_policy.minimum_python
    if not runtime_ok:
        raise GovernanceError(
            f"Python {python_runtime} is below minimum {runtime_policy.minimum_python[0]}.{runtime_policy.minimum_python[1]}"
        )

    return {
        "runtime": {
            "current": python_runtime,
            "minimum": ".".join(map(str, runtime_policy.minimum_python)),
            "recommended": ".".join(map(str, runtime_policy.recommended_python)),
            "preview": runtime_policy.preview_python,
            "venv_active": sys.prefix != getattr(sys, "base_prefix", sys.prefix),
            "runtime_ok": runtime_ok,
        },
        "dependency_policy": {
            "requirements_count": len(requirements),
            "requirements_dev_count": len(requirements_dev),
            "constraints_count": len(constraints),
            "prod_dependencies": prod_names,
            "dev_dependencies": dev_names,
        },
        "evidence": {
            "startup_command": "PYTHONPATH=src python3 -m unittest discover -s tests -v",
            "smoke_command": "PYTHONPATH=src python3 scripts/run_dependency_environment_governance_smoke.py",
            "governance_passed": True,
        },
    }


def render_report(base_dir: Path, output_path: Path) -> Path:
    report = evaluate_governance(base_dir)
    output_path.write_text(json.dumps(report, indent=2, ensure_ascii=False) + "\n", encoding="utf-8")
    return output_path

        self.assertIn("fastapi", report["dependency_policy"]["prod_dependencies"])

深入解析與評估邊界

基準要用同一份契約：先針對目標環境解析適用的 marker 與 extras；不直接把跨平台鎖檔的全套候選拿來跟單一 venv 比較。以同一個可執行直譯器查 installed metadata，避免把系統 Python 或 PYTHONPATH 上的額外 distribution 混進報告。

分清四道驗證：名稱正規化、版本與依賴一致性、檔案 digest、可信來源各驗不同問題。此實驗只對預先解析好的名單做字串等值；不是 PEP 440 版本等價演算、resolver、目錄掃描，也不是漏洞掃描。

處理衝突而不是挑一個：Factory_Core 和 factory-core 指向同一正規化名稱。發現重複正規名稱時先中止，因為任選其中一個會隱藏路徑污染。pip、啟動工具等可列明確許可名單；不能為了全綠而忽略所有額外項。

上線證據：保留 Python build、平台、鎖定版、實際安裝清單與成品 digest。讓懷疑漂移的同事可重建同一輸入，再把核准例外綁定有效期。

延伸學習：實作、現場案例與自我檢查

本頁說明依賴與環境治理。本節提供一個 requirements 檔稽核工具：找出未固定版本、未附雜湊、名稱大小寫不同但實際重複的宣告，以及無法重現的 VCS 相依。

可實跑範例：requirements 稽核

套件名稱先依 PEP 503 正規化（大小寫、底線、點號視為相同），所以 requests 與 Requests 會被判定重複。雜湊值為示意。正式專案建議改用 uv lock 或 pip-tools 產生鎖定檔，再用本工具檢查手寫的需求檔。

下載範例 example.py

"""解析 requirements 檔，找出未固定版本、未附雜湊與重複宣告的相依套件（標準函式庫）。"""
import re

REQS = """\
pymodbus==3.16.2 --hash=sha256:aa11
requests>=2.31
pandas
fastapi==0.165.0
# 開發用
pytest==9.2.0 --hash=sha256:bb22
Requests==2.34.2 --hash=sha256:cc33
-e git+https://example.com/internal/bmslib.git#egg=bmslib
"""

LINE = re.compile(r"^(?P<name>[A-Za-z0-9_.-]+)\s*(?P<spec>[<>=!~].*?)?\s*(?P<hash>--hash=\S+)?\s*$")


def normalize(name):
    return re.sub(r"[-_.]+", "-", name).lower()          # PEP 503 名稱正規化


def audit(text):
    seen, findings = {}, []
    for n, raw in enumerate(text.splitlines(), 1):
        line = raw.strip()
        if not line or line.startswith("#"):
            continue
        if line.startswith("-e ") or "git+" in line:
            findings.append((n, line[:40], "可編輯／VCS 相依：無法重現，改用已發布的版本"))
            continue
        m = LINE.match(line)
        name = normalize(m["name"])
        if name in seen:
            findings.append((n, m["name"], f"與第 {seen[name]} 行重複（名稱正規化後相同）"))
        seen[name] = n
        if not m["spec"] or not m["spec"].startswith("=="):
            findings.append((n, m["name"], "未固定版本（應使用 == 或鎖定檔）"))
        if not m["hash"]:
            findings.append((n, m["name"], "未附雜湊，無法確認下載內容"))
    return findings


if __name__ == "__main__":
    for n, name, msg in audit(REQS):
        print(f"第 {n} 行 {name}: {msg}")

執行方式：python example.py，只需 Python 3.10 以上，無第三方套件

第 2 行 requests: 未附雜湊，無法確認下載內容

第 3 行 pandas: 未附雜湊，無法確認下載內容
第 4 行 fastapi: 未附雜湊，無法確認下載內容

工程現場案例：同一份 requirements，在兩台閘道器裝出不同版本

某專案的 requirements.txt 寫 requests>=2.31 與 pandas（無版本）。半年後新閘道器部署時裝到新版 pandas，日期解析行為改變，報表時間全部錯位；舊閘道器仍是舊版，兩邊結果不一致。另外檔案裡同時有 requests 與 Requests 兩行，實際安裝的是哪個版本取決於解析順序。

固定版本加上雜湊（pip install --require-hashes）後，任何一台機器裝出的套件都相同，下載內容被替換也會被擋下。VCS 相依則應改成發布到內部套件庫的版本。

  1. 以 uv lock 或 pip-compile 產生含雜湊的鎖定檔，部署一律從鎖定檔安裝。
  2. 手寫的需求檔只寫直接相依與允許範圍，交由工具解出完整鎖定。
  3. CI 執行本稽核工具與 pip-audit 之類的弱點掃描。
  4. 定期（例如每月）更新鎖定檔並跑完整測試，不要讓版本長期停滯。

練習題與自我檢查

  1. 為什麼 fastapi==0.165.0 只被報告缺雜湊，沒有被報告未固定版本？

    看解答

    它已用 == 固定版本，但沒有 --hash。固定版本確保版本號一致，雜湊則確保下載的檔案內容沒被替換，兩者都需要。

  2. normalize('Zope.Interface') 的結果是什麼？

    看解答

    zope-interface。PEP 503 規定把連續的 -、_、. 換成單一 -，並轉成小寫，PyPI 以此判斷名稱是否相同。

  3. 為什麼 -e git+… 被視為無法重現？

    看解答

    它指向分支的最新內容，不同時間安裝會得到不同程式碼；可編輯安裝還會直接使用原始碼目錄。即使固定 commit，也缺少發布流程的審查與雜湊驗證。

  4. 「每次都裝最新版」與「完全不更新」各有什麼風險？

    看解答

    前者讓部署不可重現，上游變更可能隨時破壞系統；後者會累積已知弱點，最後一次升級的跨度太大、風險更高。建議固定版本並定期有計畫地更新。
