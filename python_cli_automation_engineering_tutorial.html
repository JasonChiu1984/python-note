Overview

先定命令契約，再談自動化

如果參數、輸出與錯誤碼不穩，CLI 只是另一種不可維護腳本。

Architecture

plan、apply、report 要明確分層

預檢、實作與證據輸出分離，才不會把風險與結果混在一起。

Setup

標準庫也能做出可交付 CLI

先用 `argparse`、`json`、`pathlib` 跑通最小閉環，再視需求升級框架。

Configuration

dry-run、輸出路徑與 exit code 都要有政策

CLI 一旦進 CI 或交給值班同仁使用，就不能依賴口頭約定。

Example

從 plan 到 apply 再到 report 一次走完

範例專案用變更集 manifest 模擬真實自動化工作，展示預檢、安全執行與證據輸出。

Verification

同時驗 CLI 行為、輸出格式與成功訊號

不只要命令可執行，還要能穩定被測試、被 release note 引用。

Troubleshooting

命令出問題先看契約與 report

CLI 問題大多來自參數漂移、dry-run 缺位、錯誤碼不穩或輸出不可解析。

Best Practices

把 CLI 當正式交付物，而不是工具人的祕密腳本

只要命令會進排程、進 CI、交給其他工程師或現場人員，就應有正式工程品質。
