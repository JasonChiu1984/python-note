資安架構研究｜身分、應用與 OT

零信任架構：從政策決策到系統驗收

內網位置、公司所有的裝置或曾經通過登入，都不能自動取得所有資源。零信任是圍繞資源、以可驗證訊號控制請求和工作階段的做法；不是取消信任、不設防火牆，也不是買一套產品就完成。

回資訊安全教材架構授權流程IT／APIHVAC／OT遷移與驗收離線程式工單追蹤工廠介面撤銷與故障驗收證據

架構圖｜政策控制與資料傳輸分開

  1. 身分與脈絡身分服務、裝置狀態、工作負載識別與資源標籤供決策。
  2. PE 政策引擎對主體、目標、動作與風險條件判斷允許、拒絕或終止。
  3. PA 政策管理元件依 PE 決策協調建立或終止通道，向 PEP 傳達控制指令。
  4. PEP 政策執行點實際管制請求與通道；只放行符合政策的流量，並回報遙測。

控制平面：可信訊號 → PE → PA → PEP（決策及路徑控制）資料平面：主體 → PEP → 資源（僅在授權條件成立時）

PE 與 PA 在 NIST SP 800-207 的邏輯模型共同構成政策決策點（PDP）。此處 PA 是執行 PE 決策、協調通道的元件，不是管理員手動寫政策的同義詞。PEP 可以是代理、閘道或由多個協同元件組成；這是責任劃分，不是要求部署三台主機。IdP 提供身分訊號，但不是單獨的授權裁決。政策控制平面需保護完整性、授權管理、時鐘與可用性；把策略或執行點故障視為設計情境，而不是預設放行。

常見名詞不可互換：MFA 增強身分驗證，不證明裝置健康；網路分區限制傳播，不等於每個資源都授權；ZTNA 可能是遠端存取的落實方式，不代表完整 ZTA；mTLS 可驗證連線端點及保護傳輸，不保證呼叫者有權讀某筆資料。資源標籤、擁有者、允許動作及風險訊號需要持續維護。下載可編輯 Draw.io 架構圖及授權流程

流程圖｜最小權限不只決定「能不能登入」

  1. 提出請求由受管裝置或工作負載要求特定資源和動作。
  2. 取得可信訊號驗證身分與裝置／工作負載證據，核對資源與情境。
  3. 判定與執行PE 作決策，PA 協調由 PEP 建立、限制或拒絕通道。
  4. 持續評估收到撤銷、姿態過期或風險變動，重新判斷並執行回收。
  5. 記錄與驗收記錄決策理由、政策版本與時鐘，查有效回收與本地持續運轉。

把決策單位寫成「主體 × 資源 × 動作 × 條件」。身分須區分人、服務與裝置；動態條件可能含資產健康度、憑證與裝置證據時效、工作單、資源敏感度、登入風險，以及本地主管批准的時間窗。網路位置可作風險訊號，不能當成充分證明。記錄實際用哪些訊號與缺失處理；持續評估依工作階段壽命、事件與適用風險實行，不代表每封封包都要人工重新登入。

IT／API：把登入、OAuth 授權與每筆資源檢查切開

OIDC 是常用的登入身分層；OAuth access token 用於授權存取 API，ID token 不應當作 API access token。互動式客戶端依情境採授權碼搭配 PKCE；無人服務使用部署平台支援的工作負載身分及短效憑證，不共用人員帳號或長效密鑰。API 應遵循自己的 token profile：例如驗 JWT 的簽章、允許演算法、可信 issuer、audience 及有效期間；不透明 token 按受信任授權伺服器提供的機制核驗。不可只解碼字串便信任 claims。IETF OAuth 2.0 安全最佳實務。

入口閘道以 audience、scope 與身分做粗粒度限制；實際 API 仍應依使用者或服務能否存取該客戶／廠區／對象及讀寫型別判斷。服務間存取另用工作負載身分、適用時採 mTLS 與服務策略；不要把用戶層權限不受控地轉授下游。NIST SP 800-207A 討論雲原生多地環境的應用和服務層做法，並不規定所有 PLC 或每個環境都採服務網格。

拒絕原因應對外保持適當抽象、內部可追溯；日誌記決策、policy version、資源代碼、時間與關聯 ID，不留原始 token、密鑰或不必要個資。權限更新與 JWT 存續應分開設計：短效 token 並不等於即時撤銷，須量測會話終止、撤銷傳播、政策快取生命週期和重連後失效邊界。

HVAC／OT：遠端維護失效，不應使本地迴路停擺

不要要求壽命長或資源有限的 PLC 配合雲端身分代理；可在設備群的信任邊界施行 PEP，保留能驗證的分區與本地操作流程。斷開 IdP 或政策服務時，遠端新增會話依政策拒絕／隔離，既有會話只能依事前核准的限定策略及上限處置；不能自動放寬為永久信任。現場連續性透過獨立的本地 PLC、PID、操作員站及安全設計驗證。測試時用隔離台或核准維護窗，不直接在生產環境拔線。

破窗不是共用永遠可用的管理員帳號。預先定義角色、啟用條件、受保護的憑證保管與緊急授權，鎖定資源／動作／期限、雙人核准或按現場緊急程序確認，啟動即告警與保留審計。完成後終止工作階段、回收權限、必要時輪替憑證並獨立檢討。若平常連不上 IAM，也須有經演練的本地維運方式；不把現場安全依賴遠端破窗服務。

決策憑證包：哪些訊號有效、誰提供、什麼時候到期？

輸入可信來源及需記錄欄位不可當成充分證明
人與工作負載可信來源及需記錄欄位IdP 已簽身分訊號與驗證強度、可撤銷人員識別、授權時效；DMZ 代理使用獨立服務身分。不可當成充分證明HTTP 傳入的身分 header、顯示名稱、同一機房來源 IP。
裝置可信來源及需記錄欄位受管理的資產 ID、裝置憑證或 health 憑證、發行與到期、證據版本及採集時間。不可當成充分證明「公司電腦」字串；成功 MFA 不等於裝置仍受管。
資源及動作可信來源及需記錄欄位以伺服器解析的 plant-a/chw/trend、所有者與分類；將請求映射為 trend.read，不是任意標籤。不可當成充分證明僅有 GET 不等於可讀任何對象；不信任呼叫者聲稱的站點或替代 ID。
環境及工單可信來源及需記錄欄位工作單歸屬、指定範圍、核准人、時間窗、撤銷狀態及 UTC 時間；地點、風險分屬輔助訊號。不可當成充分證明快取訊號不可無限延長；無時鐘依據、工單與資源版本不符時標為未知。

追蹤 TRACE-412：把控制平面與資料平面分開驗證

階段負責點與可驗證結果記錄證據
1．入口攔截負責點與可驗證結果PEP 接住請求，正規化目標及操作，不直接開通資料路徑。用 request ID 串聯，不接受使用者自行指定內部 trace 身分。記錄證據接收時間、trace ID、資源代碼、入口 PEP。
2．決策負責點與可驗證結果PE 依 policy-17 評估。符合條件才允許；不符或無法安全驗證則拒絕；若只是驗證強度不足，可要求再驗，資料仍不可流通。再驗是此實作的中間處理，不是 NIST 定義的第三種放行結果；成功後重新評估全部條件。記錄證據政策版本、訊號新鮮度、允許／拒絕／再驗、內部原因碼。
3．布建負責點與可驗證結果PA 依決策只開短效、限資源及動作的路徑；PEP 回報已套用的政策世代和許可期限。無回執不宣告放行，不能在半部署時降級放行。記錄證據決策 ID、PA 下達時間、執行點套用時間、範圍與有效期。
4．資料傳輸負責點與可驗證結果PEP 接受通道後，資源 API 再核對每筆對象級與動作級權限。人員只讀 DMZ 提供的已批准趨勢，查 B 廠或寫入仍拒絕；不能只靠保護畫面的按鈕。記錄證據請求與對象授權、下游工作負載身分、回應狀態，不記 token 或私鑰。
5．重決策／撤銷負責點與可驗證結果工單撤回、裝置過期或到時即向 PE 重新決策；PA 停止授權、PEP 拒絕新要求並終止或限制既有通道。回頭驗證持續資料流、替代入口、重連及本地迴路是否按設計運作。記錄證據撤銷指令、各 PEP 回執、最後允許與第一筆拒絕、仍流量的介面及模式。

資料實際流向：外部人員 → 受控入口／DMZ PEP → 趨勢 API；OT 站內以獨立工作負載依核可資料流提供必要資料。批准角色看的是趨勢物件，不會取得全網層連線、設備寫入或 PLC 路徑。要把存取期限同時落實在入口與資源層；入口失效或人員停權時，PLC/DDC 的 PID、保護連鎖、看門狗及本地操作仍獨立。查核兩側允許的流向、資料新鮮度及本地告警，不靠一次入口登入判定分區完成。

依據：NIST SP 800-207 的邏輯元件、800-207A 應用／服務身分、800-82 Rev.3 的 OT、安全與可用性。

故障與撤銷｜停止授權、已發 token、推送通道是三個時鐘

OAuth 不保證一撤回就立即拒絕所有舊會話

登入後仍每筆驗授權；資源伺服器要檢查 token 簽章／issuer、audience、scope、效期及適用的發送端綁定，再以可信物件查詢與政策檢查「哪個廠區、哪筆資料、哪種操作」。token 還沒到期與工單仍能執行是兩件事。IdP 停用帳號或撤回 refresh token 主要阻止後續簽發，不能假定各 API 對已發且離線驗簽的 JWT 立刻拒絕。強制撤銷需可驗的策略更新／拒絕清單、即時檢查或內省、PEP 終止通道與資源單筆檢查，並處理快取、訊號不同步及失效時的策略。內省快取與阻塞及可用性要一起評估。

撤銷算例（非標準）：以工單取消成功寫入的 t₀=09:04:00 起算，事件派送 ≤2 s、PA 到所有必要 PEP 完成套用 ≤3 s、既有讀取串流重新檢查／終止 ≤5 s、量測時鐘誤差預算 ≤1 s。若這些步驟串行且各上界都能證明，則此示例的保守預算是 2+3+5+1=11 s。一次合成 trace：09:04:02 決策收到、09:04:05 PEP 套用、新請求拒絕，09:04:10 舊串流停止，預算含誤差到 09:04:11。收到 PA 回執不等於資料流已停止；量的是最慢必要執行點的最後允許資料、既有串流停止及使用舊憑證重新連線被拒。若替代路徑只離線驗 token、會話繞過執行點或推送無硬上界，就不能報 11 s；較長的 token 殘餘壽命或持續資料流需另量。

防禦參考：RFC 9700：受眾限制與 sender-constrained token、RFC 7009：撤銷與傳播可能延遲、RFC 7662：內省及結果快取取捨。

故障矩陣：別把遠端 fail-closed 誤作現場停機

故障新連線／新請求既有階段安全回復與證據
IAM／IdP 不可用新連線／新請求無新身分證據時拒絕或等待恢復，不能發通用暫時密鑰。既有階段示例僅可讓預先核准的低風險唯讀在短時界、證據有效且仍可撤銷時繼續；無法確認條件就停。安全回復與證據記 token、快取世代的時效及拒絕優先順序，不記 token 原文；恢復後先重新驗證。
PE／PA 或冗餘訊號失效新連線／新請求不批准新路徑或升權；缺回執不視為成功。既有階段只允許經明文政策核准的有界情境。撤銷狀態失聯時，以可驗的本地期限關閉遠端路徑。安全回復與證據記最後成功的政策世代、備援及重新同步；不能默默喚回舊有授權。
PEP 失效／分區新連線／新請求不可繞過 PEP；備援執行點未完成同步則不轉流。既有階段受影響遠端通道按設計關閉；監控既有串流是否另尋繞路。控制器本地保護保留。安全回復與證據驗切換至最新政策、負向健康檢查、撤銷複核及本地迴路仍持續。
裝置健康過期／金鑰異常新連線／新請求區分資料過期、金鑰正常輪替及疑似外洩；重新查證，否則拒絕。既有階段過期或洩漏風險按政策收回必要會話。不要無限延長舊公鑰或快取。安全回復與證據測輪替重疊期、未知發行者／金鑰、重連；恢復時以受控信任來源重驗。
稽核儲存／傳輸中斷新連線／新請求高風險寫入若無法保住必要證據則拒絕；是否准許有界低風險唯讀須明文核准。既有階段低風險假設採可持久的有界緩衝與告警；緩衝滿或記錄不完整時停止受影響遠端用途。安全回復與證據以序號、落地回執及補送查出缺口；驗資料最小化、權限限制、不可擅改。

故障策略需由設施營運、IT、資安及安全工程共同核定；不把有界降級、MFA 或預備通道當成默許的永久旁路。現場分區與安全保護不以此教材替代。設計參考 NCCoE SP 1800-35 的實作組合（不是認證）。

驗收與漸進導入｜測拒絕、撤銷、效能，以及本地能不能繼續

  • 拒絕：同廠讀成功、跨廠讀拒絕、同工單寫拒絕、舊裝置驗證拒絕；利用合成條件或核可測試環境，保留 request ID、政策版號、預期與實際受影響資源。另測直接資源、代理及舊入口是否都受相同限制。
  • 撤銷：在低、尖峰和備援切換負載下，分別跑新請求、已發 token、既有串流及重連；記最末允許、最先拒絕與所有節點的約定時鐘誤差。未能驗證端到端上界，不把第 95 百分位當保證。
  • 效能和可用性：固定資源、裝置及流量組合，量 PE 延遲、PA 套用時間、PEP 每筆處理、整體 p95/p99、樣本數、逾時、誤拒與可用性；同時檢查授權失效時遠端拒絕與本地 PLC 圈仍在安全狀態。
  • 復原和稽核：演練 IAM、政策同步與記錄通道失效，記 RTO 目標及實測；確認復原不恢復舊授權、到期工單或遺失的稽核事件未被當完備。測試 log 去除 token、密鑰與不必要個資。

導入順序：先盤點資源與本地安全邊界 → 在測試環境用 shadow 評估誤拒（不等於已防護）→ 小範圍強制核准的唯讀工單與趨勢 API → 擴至服務身分、跨區及更高風險動作。每批先寫驗收界線及叫停條件，保留已核可版號與可稽核回復程序，不回到無限制放行。

遷移、驗收與證據：以可重做的事件判斷是否成功

CISA Zero Trust Maturity Model v2.0 用身分、裝置、網路、應用與工作負載、資料五支柱，加上可視性與分析、自動化與協調、治理三項橫向能力。Traditional、Initial、Advanced、Optimal 是規劃與自評階段，不是認證、等保判定或必須追求最高等級的要求。CISA ZTMM

  1. 先盤點資源、資料流與責任人；標示不可停止的 OT 控制與人員安全依賴。
  2. 先試點唯讀 API 或低風險遠端維護，在測試環境比較允許與拒絕的影響；配置可回復政策版。
  3. 再移轉寫入與服務間身分，按資產風險分區逐步強制；每一批均有回復條件、授權人、時間窗與舊例外到期日。
  4. 將證據納入變更管理：政策測試、APP/API 判斷、PEP 執行記錄、故障演練和憑證更新成果；例外要重審或到期收回。
驗收情境應確認的結果證據
拒絕與資源界線同身分跨廠、輸出寫入、scope/audience 不符或裝置證據過期不得放行。決策碼、無資料回傳、無狀態變更、可交叉比對的 request ID。
撤銷與輪替撤銷權限後，新舊通道停止於已約定時限。憑證輪替保有授權合法通道，過渡期後拒絕舊憑證。撤銷發出與生效時間、策略／憑證版本及重連結果。
決策依賴或網路故障遠端新增存取依預案停止、告警；本地 PLC/PID、操作員站與安全聯鎖在核准測試中維持要求。實際控制迴路趨勢、警報延遲、回復時間與驗收紀錄。
破窗與復歸僅在核准資源／時間使用，完成後自動或人工回收並驗證沒有殘留權限。核准紀錄、工單、會話關閉／憑證輪替及獨立複核。

指標用可量測的拒絕命中、誤拒、撤銷上界、恢復時間、輪替成功、實際遙測覆蓋去驗收，不以啟用 MFA 或採購產品充當完成證據。

"""Evaluate fictional authorization records offline; no token processing or network."""

from dataclasses import dataclass, replace
import argparse
import json
import unittest


@dataclass(frozen=True)
class Context:
    subject: str = "maintenance-reader"
    device_compliant: bool = True
    posture_age_s: int = 20
    audience: str = "hvac-support"
    action: str = "trend:read"
    resource: str = "site-a/ahu-01"
    expires_at: int = 150
    now: int = 100
    revoked: bool = False
    dependency_available: bool = True
    approved_ticket: bool = True


def evaluate(c: Context) -> tuple[bool, str]:
    """Input is an already verified context, not raw or application-supplied claims."""
    if not c.dependency_available:
        return False, "policy_dependency_unavailable"
    if c.revoked or not 0 <= c.now < c.expires_at:
        return False, "revoked_or_expired"
    if c.audience != "hvac-support":
        return False, "wrong_audience"
    if not c.device_compliant or not 0 <= c.posture_age_s <= 60:
        return False, "posture_missing_or_stale"
    if not c.approved_ticket:
        return False, "ticket_not_approved"
    if (c.subject, c.action, c.resource) != (
        "maintenance-reader", "trend:read", "site-a/ahu-01"
    ):
        return False, "outside_policy"
    return True, "allowed_read_only"


class DemoTests(unittest.TestCase):
    def test_only_approved_read(self):
        self.assertEqual(evaluate(Context()), (True, "allowed_read_only"))
        for change in (dict(action="output:write"), dict(resource="site-b/ahu-01"),
                       dict(subject="other"), dict(approved_ticket=False)):
            with self.subTest(change=change):
                self.assertFalse(evaluate(replace(Context(), **change))[0])

    def test_session_revocation_and_expiry(self):
        for change in (dict(revoked=True), dict(now=150), dict(audience="other-api")):
            self.assertFalse(evaluate(replace(Context(), **change))[0])

    def test_stale_posture_and_dependency(self):
        for change in (dict(posture_age_s=61), dict(posture_age_s=-1),
                       dict(device_compliant=False), dict(dependency_available=False)):
            self.assertFalse(evaluate(replace(Context(), **change))[0])


if __name__ == "__main__":
    p = argparse.ArgumentParser(description=__doc__)
    p.add_argument("--test", action="store_true")
    if p.parse_args().test:
        unittest.main(argv=["lab"])
    else:
        for name, c in [
            ("approved", Context()),
            ("stale", replace(Context(), posture_age_s=61)),
            ("revoked", replace(Context(), revoked=True)),
            ("different_site", replace(Context(), resource="site-b/ahu-01")),
            ("policy_unavailable", replace(Context(), dependency_available=False)),
        ]:
            allowed, reason = evaluate(c)
            print(json.dumps({"case": name, "allowed": allowed, "reason": reason}))

延伸學習：實作、現場案例與自我檢查

本頁說明政策決策與執行分離。本節實作一個最小的政策決策點：預設拒絕，每筆請求都依角色、動作、資源、裝置狀態、MFA、工單與時段重新判斷，並回傳拒絕原因。

可實跑範例：預設拒絕的政策決策點

POLICIES 是允許清單；找不到符合的政策就拒絕。每個拒絕都帶原因，方便稽核與除錯。範例把時間固定成兩個時間點，讓輸出可重現。

下載範例 example.py

"""最小權限政策決策點（PDP）：預設拒絕，每筆請求依身分、裝置狀態、資源、動作與時間窗判斷（標準函式庫）。"""
from datetime import datetime

POLICIES = [
    {"role": "vendor", "action": "read", "resource": "ahu/*", "device_ok": True,
     "ticket": True, "hours": (8, 18)},
    {"role": "operator", "action": "read", "resource": "*", "device_ok": True},
    {"role": "operator", "action": "write", "resource": "ahu/*/setpoint", "device_ok": True, "mfa": True},
]


def match(pattern, resource):
    p, r = pattern.split("/"), resource.split("/")
    if pattern == "*":
        return True
    return len(p) == len(r) and all(a in ("*", b) for a, b in zip(p, r)) or (p[-1] == "*" and r[:len(p) - 1] == p[:-1])


def decide(req):
    for pol in POLICIES:
        if pol["role"] != req["role"] or pol["action"] != req["action"] or not match(pol["resource"], req["resource"]):
            continue
        if pol.get("device_ok") and not req["device_ok"]:
            return "拒絕：裝置狀態不符（未更新或未受管）"
        if pol.get("mfa") and not req.get("mfa"):
            return "拒絕：寫入需要 MFA"
        if pol.get("ticket") and not req.get("ticket"):
            return "拒絕：需要有效工單"
        if "hours" in pol and not pol["hours"][0] <= req["time"].hour < pol["hours"][1]:
            return f"拒絕：不在允許時段 {pol['hours'][0]}–{pol['hours'][1]} 時"
        return "允許"
    return "拒絕：沒有符合的政策（預設拒絕）"


if __name__ == "__main__":
    day, night = datetime(2026, 11, 28, 10), datetime(2026, 11, 28, 22)
    reqs = [
        ("廠商白天唯讀", dict(role="vendor", action="read", resource="ahu/01/sat", device_ok=True, ticket=True, time=day)),
        ("廠商夜間唯讀", dict(role="vendor", action="read", resource="ahu/01/sat", device_ok=True, ticket=True, time=night)),
        ("廠商嘗試寫入", dict(role="vendor", action="write", resource="ahu/01/setpoint", device_ok=True, ticket=True, time=day)),
        ("廠商無工單", dict(role="vendor", action="read", resource="ahu/01/sat", device_ok=True, ticket=False, time=day)),
        ("值班寫入無 MFA", dict(role="operator", action="write", resource="ahu/01/setpoint", device_ok=True, time=night)),
        ("值班寫入有 MFA", dict(role="operator", action="write", resource="ahu/01/setpoint", device_ok=True, mfa=True, time=night)),
        ("值班筆電未更新", dict(role="operator", action="read", resource="chiller/02/kw", device_ok=False, time=day)),
    ]
    for name, r in reqs:
        print(f"{name:<10} {r['action']:<5} {r['resource']:<16} → {decide(r)}")

工程現場案例：廠商遠端維護帳號長期開著全權限

某大樓為了方便，給空調廠商一組 VPN 帳號，登入後可以看也可以改所有點位，帳號一年沒換過。零信任的做法是把「能登入」和「能做什麼」分開：廠商只有在有工單、上班時段、使用受管裝置時才能讀取空調箱的點位，任何寫入都不在允許清單內。

範例中值班人員的寫入需要 MFA，筆電未更新時連讀取都被拒絕。所有決策都有原因，事後可以回答「為什麼那次被拒」或「是誰在什麼條件下改了設定點」。

  1. 盤點每個角色實際需要的資源與動作，寫成允許清單，其他一律拒絕。
  2. 把裝置狀態、MFA、工單與時段做成可查詢的屬性，由政策決策點統一判斷。
  3. 政策執行點（閘道器、API）每一筆請求都詢問決策點，不快取「已登入就放行」。
  4. 保留決策紀錄，定期檢視被拒絕最多的請求，調整政策或流程。

練習題與自我檢查

  1. 把 POLICIES 的順序改成第三條放第一，會影響結果嗎？

    看解答

    本例不會，因為各政策的角色與動作組合不重疊，每個請求最多只會符合一條。若政策有重疊，「第一條符合即決定」的寫法就要注意順序，通常把較嚴格的放前面，或改成全部評估後取最嚴格的結果。

  2. 「廠商嘗試寫入」的拒絕原因是「沒有符合的政策」，而不是「廠商不能寫入」。為什麼這樣比較好？

    看解答

    預設拒絕不需要為每個不允許的組合寫規則，政策清單只描述允許的事。新增角色或資源時，未明確允許的操作自動被拒絕，不會因為漏寫拒絕規則而開了後門。

  3. 時段檢查用 time.hour，若廠商在 17:59 開始一次長時間的連線，18:00 之後還能繼續讀嗎？

    看解答

    範例每筆請求都重新判斷，18:00 之後的讀取會被拒絕。這是零信任「持續驗證」的特性；實務上可在接近結束時提示使用者，而不是突然中斷。

  4. 若政策決策點本身故障，BAS 本地控制應該怎麼辦？

    看解答

    本地控制迴路不能依賴遠端決策點。決策點故障時，遠端存取應被拒絕（fail closed），但現場 DDC 的控制邏輯與本地操作必須照常運作。本頁的 HVAC／OT 章節就是在處理這個邊界。
