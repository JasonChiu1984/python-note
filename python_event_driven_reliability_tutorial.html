Overview Example Verification
Overview

先承認 at-least-once，再設計可靠處理

事件驅動系統的現實不是 magically exactly once，而是用可重複處理與故障隔離，把風險轉成可治理流程。

Architecture

把寫入、派送、消費與重放拆成可驗證元件

資料庫交易、outbox 派送器、broker、consumer、DLQ 與 replay command 都應有清楚責任邊界。

Setup

先用標準庫做 deterministic 範例

以 in-memory event store、fake broker 與 unittest 把可靠性行為做成可本機重現的最小專案。

Configuration

重試、順序、DLQ 門檻都要明確設定

沒有可見的門檻與 runbook，事件管線只會變成難以排錯的黑盒子。

Example

範例專案示範 outbox 到 replay 的完整閉環

範例包含 domain event、outbox dispatcher、idempotent consumer、poison message 隔離與 replay evidence。

Verification

驗收要同時覆蓋重試、重複、壞訊息與重放

可靠性不是 happy path 測一次而已，要驗證 delivery、dedup、DLQ、replay 與報告輸出。

Troubleshooting

故障要能被定位，不要讓 queue 默默卡死

queue lag、DLQ 堆積、重複事件與順序錯亂都需要清楚的診斷步驟與保守處理。

Best Practices

可靠性結論必須來自證據，不是口頭保證

事件驅動設計應產生可追溯的交付證據，能被 release note、營運 runbook 與事故檢討直接引用。
