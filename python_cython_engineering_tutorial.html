Cython 選型與交付流程

先判斷是不是 hot path，再選 `cdef`、memoryview、C library wrapper、nogil 或 package delivery。Cython 是工程刀，不是所有程式碼都要編譯。

Cython 簡介

先理解它解決什麼問題

Cython 把 `.pyx` 或部分 Python 語法轉成 C/C++ extension，讓 Python 保持呼叫介面，同時把熱點搬近 C 層。真正的工程價值在「邊界清楚、效能可證明、可被打包部署」。

指令說明

cython / cythonize / build_ext / build

這一章把常用指令、參數、用途與陷阱拆開。日常開發用 `cythonize -i` 快速驗證；正式交付用 `pyproject.toml`、wheel 與 CI matrix。

指令 / 參數用途適用時機常見錯誤
cython file.pyx只把 Cython 轉成 C/C++ 原始碼需要手動控制 C compiler 或檢查產生碼以為會直接產生可 import module
cythonize -i file.pyx轉 C 並編譯成目前目錄可 import extension本機快速開發、效能實驗沒有 C compiler、Python headers 或平台工具鏈
-a / --annotate產生 HTML 標註，顯示 Python interaction 熱度找出還沒被型別化的瓶頸只看顏色不看 benchmark
-j N多檔案平行編譯大型 package 有多個 `.pyx`CI runner CPU 太小時反而搶資源
-X directive=value設定 compiler directive，例如 boundscheck針對單次編譯快速驗證全域關閉安全檢查卻沒測邊界
python setup.py build_ext --inplace用 setuptools extension 在原地產生 extension需要自訂 Extension、include dirs、libraries只支援本機測試，不等於正式發佈
python -m build產生 sdist / wheel正式 package release缺 pyproject build-system 或 wheel 平台驗證
語法與型別

每個 Cython 語法都搭配工程範例

重點不是把 Python 寫成 C，而是把最昂貴的 loop、資料存取、跨語言邊界標清楚。`cdef`、`cpdef`、memoryview、`.pxd`、`nogil` 都是邊界工具。

詳細應用

從 hot loop 到 C SDK wrapper

資深專案會先問：瓶頸在哪、資料形狀是否穩定、API 邊界能不能維護、失敗時怎麼回 Python。這裡用實務場景拆解應用。

打包詳細介紹

從 pyproject 到 wheel、CI 與 PyInstaller

Cython 的交付不是把 `.pyx` 丟出去就結束。你需要 build-system、platform wheel、Python ABI、include data、CI matrix、smoke test 與 rollback 計畫。

交付檢查表

Cython 上線前要看這 8 件事

資深工程不是只追求快，而是把快、安全、可維護與可部署一起交付。

Profile evidence先有 `py-spy`、`cProfile` 或 benchmark，再決定要不要 Cython。
Minimal boundary只把 hot path 放進 `.pyx`，外層 API 保持 Python 易測試。
Typed data pathloop、memoryview、C struct、C function signature 都要清楚。
Safety directives`boundscheck=False`、`wraparound=False` 必須有邊界測試保護。
Benchmark gateCI 或 release 前保留 baseline，避免改了卻沒有真的變快。
Wheel matrix不同 OS / Python version 要分別 build 與 smoke test。
Fallback planextension build 失敗時，要知道是否允許 pure Python fallback。
Rollback保留上一版 wheel / exe，extension crash 時可以快速退回。
