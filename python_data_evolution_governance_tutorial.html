把資料升版做成可回退的工程流程

很多專案不是壞在 CRUD，而是壞在升版瞬間：新程式讀不到舊資料、backfill 半路中斷、rollback 後資料回不去。這條路線把 schema version、compat read/write、expand/contract、backfill checkpoint、drift preflight 與 rollback evidence 串成完整工程閉環。

Overview

先定義資料版本契約，再做 migration

資料演進治理的第一步不是寫 script，而是先說清楚版本、相容與回退條件。

Architecture

把相容讀寫、回填與回退拆成明確層次

compat read/write、backfill、preflight 與 rollback evidence 應各自可驗證。

Setup

本機就能模擬 schema 升版與回復

用標準庫範例就能演示 schema drift、checkpoint、resume 與 rollback read。

Configuration

用 manifest 寫出升版規則與風險邊界

沒有 manifest 的資料升版，多半只是在賭運氣。

Example

用 sample project 示範完整資料演進閉環

範例專案示範 schema manifest、compat adapter、backfill checkpoint、drift preflight 與 rollback report。

Verification

驗收要同時覆蓋升版、續跑與回退

資料演進不是 migration 跑完就算完成，還要證明能重跑、能停止、能回讀。

Troubleshooting

先比對資料版本與報告，再看應用程式

大多數資料升版事故，本質上都是版本契約或回填證據不足。

Best Practices

讓資料升版變成可交付、可回退資產

版本發布時，schema 狀態、backfill 進度與 rollback 可行性都應被記錄。
