FIELD TRIAGE / SCENARIO SELECTOR

選一個塞車情境，找到先查與解決方案

先從最接近的症狀選，不把一個指標當成確診。這些是既有唯讀觀測的判讀建議；任何工控設定變更先與責任人確認範圍、核准維護窗及回退。

目前情境連結

單一 RS‑485 從站沒回覆

症狀
某站逾時，其他正常站也在同一個掃描週期同步變慢。
先查與確認
按站對照成功率、回覆時間、重試及閘道 queue；確認慢站逾時出現後，該 RTU 埠的其他站才開始等待。CRC 同時升高則要另外查實體層。
安全處置
先在既有上位採集器做每站 deadline 與有限退避，讓故障站降低查詢優先度；保留健康檢查，顯示「逾時／舊值」，不要填 0 或用上一筆冒充即時。現場控制與告警關鍵讀取不自行變更。
驗收與回退
同輪詢量比較健康站 p95／p99、故障站辨識及資料年齡；若超出告警時限或恢復偵測變差，還原先前輪詢策略。

交換器出口有微突發

症狀
短暫丟棄，但分鐘平均使用率不高；多輸入同時寫往同一接收端或上行埠。
先查與確認
優先查該 egress 的 queue high-watermark 與 drop、雙向 port bps 和各來源的發送時刻。缺乏短時間視窗的 queue 資料時，只能記錄疑似微突發。
安全處置
先以既有監控設定錯開大批採集時刻或控制批次大小；容量、QoS 或路徑變更需在核准維護窗先驗證現有控制優先順序。
驗收與回退
同工作量與同出口比較 drop、p99、成功率；若控制佇列失去優先服務或備援容量不足，回復發送節奏或原設定。

同 VLAN 廣播／多播突然變多

症狀
同 VLAN 多台設備同時延遲或丟訊框；trunk 或設備 CPU 壓力與廣播／多播一起升高。
先查與確認
取既有每 VLAN 與每埠的廣播、多播、未知單播計數，對齊 STP 拓撲變化、MAC 移動、設備上線時間。單獨一項 MAC 移動不等於已找到環路。
安全處置
先確認是否有合法設備發現、備援切換或新增訂閱。由網路責任人於維護窗處理已確認的環路，再依模型評估 storm control 或適合的 snooping；不可盲目關閉廣播／多播。
驗收與回退
比較分 VLAN 計數、丟棄與控制延遲，複驗發現功能及備援切換；失去正常發現或備援時還原受影響設定。

多個用戶塞進同一個序列閘道

症狀
連線都成功，但加開第二套採集後，等候和逾時比單一採集明顯增加。
先查與確認
核對閘道各埠 in-flight 與待送深度、上下游入／出時間、各從站服務時間；確認多 TCP 用戶是否共用同一 Modbus RTU bus，並排除個別慢站。
安全處置
先去除重複輪詢，由採集端限速、限制同一 bus 的未完成請求，合併經現場確認可安全連讀的區段。應用逾時未必終止已送出的交易；不要直接重送寫入。
驗收與回退
比較相同點位新鮮度、佇列水位和成功率；若任何必要點變舊或誤報失聯，全程保留原採集策略以便回退。

MQTT 或資料庫接收後積壓

症狀
網路往返仍正常，但訊息等待或監控資料年齡變長，接收未必已持久化。
先查與確認
用既有訊息 ID 對齊 broker forward、應用接收、等待 worker 與 DB commit；分別確認訂閱端待送、未確認、連線池等待及鎖等待。
安全處置
限制 consumer 的並行和佇列上限，並公開積壓告警；先隔離慢報表或長交易，配合耐久性驗證再調整批次。勿以 QoS 或提前確認來隱藏未持久化風險。
驗收與回退
同輸入速率比 commit p95／p99、最舊訊息、未確認與丟棄數，測斷線後資料可追溯；若可靠性退化還原批次／並行設定。

CRC／介面錯誤開始增加

症狀
偶發失聯或速度掉檔，錯誤率增加後才出現重傳，不是單純出口排隊。
先查與確認
核對兩端協商速率、雙工、FCS/CRC 與 link flap 的同窗差值；不要把未報錯的 discard 當成壞線，也不要用歷史累計斷案。
安全處置
由責任人於核准時窗逐項驗證線材、端子、光模組或協商問題並記錄變更，先保存原狀與允許的備援路徑。
驗收與回退
比較相同流量下的雙端錯誤、重傳和連線穩定性；若出現掉檔、告警失真或備援失敗，復原上一項變更。

01 / ARCHITECTURE

一路上的每個節點，都有自己的速度和佇列

先分三件事：線速是每秒傳送位元數（例如 100 Mb/s 與 1 Gb/s）；吞吐量是實際每秒完成的交易／位元；延遲是單筆等多久。每次 20 位元組的輪詢仍可能等 300 ms 的從站逾時。高峰時同一出口的微突發可能塞滿緩衝，即使一分鐘平均利用率不高。

02 / CAUSE MATRIX

症狀與佐證：不要看到 timeout 就換交換器

瓶頸位置常見原因先核對的被動證據改善後要驗證
來源、PLC scan／採集輪詢間隔比設備更新還快、同一點被多系統查、CPU 通訊任務忙或排程重入scan 負載、來源時間／序號、應用 enqueue→send 等待、同點讀取頻率調整採樣與採集節奏；合併相鄰且允許的讀取範圍，別跨不支援或不同更新週期位址。
交換器出口多埠突發匯入窄 uplink、線路降到 100M、同一 QoS 佇列爭用雙端協商速度/雙工、各方向 bytes、出口佇列或 discard 增量；看時間相關，不只總累計對照備援／故障切換後可用容量；調整聚合、分流或容量時不破壞既有控制優先權。
交換器實體層線材、端子或光模組問題、雙工不符，亦可能有環路兩端介面 error、FCS/CRC、flap；分開記錄 discard；風暴時看每 VLAN 廣播／多播和拓撲事件在核可維護窗口找原因；不是每個丟棄都表示線材壞，也不是每個 FCS 都是塞車。
VLAN 與噪音大型廣播域、異常廣播／多播、未知單播泛洪或環路；trunk 仍共同占容量依 VLAN／時窗看正常基線與封包種類計數、上行負荷、環路事件按網段治理流量；VLAN 不增加實體頻寬，不會自動阻止同 VLAN 的廣播。變更須保留必要發現流量。
TCP Client 與 Server連線池排隊、反覆建連線、接收窗收縮、套接字資源、重傳、應用過早重試連線/請求耗時、已存在的 TCP retransmission／接收窗指標、服務端 pending/CPU；區分傳輸重傳與應用重送限制同時請求與期限，退避加抖動；重試不是提高容量，寫指令逾時尤其不可無條件重送。
Modbus TCP→RTU 單埠單從站慢或無回覆造成隊首阻塞；跨 TCP Client 也共用同一個 bus；短應用逾時未必取消已發送的 RTU 交易每站成功率／回覆時間、gateway queue、RTU timeout/CRC 及其他站的尾延遲按站隔離錯誤、限制重試、對連續故障設冷卻期（仍需健康檢查）；經驗證後按服務水位分 port/bus。

單鏈路全雙工應分開看雙方向利用率，兩方向比率直接加總可能誤導。設備若支援 QoS，需同時看 uplink、佇列、同 VLAN／跨 VLAN 流量與交換晶片指標，不能只看全埠平均。

02B / DEEP DIAGNOSIS

塞車常見原因：先判斷是「等」還是「重做」

此處的「塞車」包含設備或軟體排隊，並不等於網路達到線速。固定一筆請求的五個交界，再問：進來太多、單次服務太慢、重試放大，還是資料已過期而誤判？下載兩張可編輯 Draw.io 圖。

1｜實體線路（L1）

線材、接頭、光模組異常或速度／雙工不一致，可能先丟壞訊框，再由上層重傳；只有 delay 不表示線材故障。

佐證：查雙端速度／雙工、link flap 及 FCS/CRC、接收錯誤增量；discard 無錯誤不等於壞線。比對錯誤發生時窗，不用十年前的累計值。

2｜RS‑485 半雙工與重試

發送、靜默間隔、收發器切換和從站處理要輪流進行；一站未回覆時，主站可能空等到 timeout。TCP 用戶增加也不會增加單埠 RTU 容量。

佐證：比較每站佇列、回覆時間、CRC／逾時與重試。19,200 bit/s、8E1 的 19 字元只算線上傳送約 10.9 ms；一個 3.5 字元靜默約 2.0 ms，額外處理／切換和逾時另計，不雙算。

3｜交換器出口與微突發

多個 ingress 同時送往單一 egress 時，即使長時間平均不高，瞬間供給仍可能超過出口速率。緩衝滿時先排隊或丟棄。

佐證：看同一出口的 queue occupancy/high-watermark、drop 及輸入時間分布。僅有 1 分鐘平均時，標成「可疑」，不能宣稱已證實毫秒級突發。

4｜VLAN、廣播／多播與環路

未知單播、同 VLAN 廣播、未妥善控制的多播或意外 L2 環路，都能占用共享 uplink；VLAN 分隔不會增加 trunk 實體容量。

佐證：比較 VLAN／方向封包組成、MAC 移動和 STP 拓撲變動；一項 MAC 移動不是環路定論。被動對照既有拓撲，變更 STP、snooping 或 QoS 要循現場維護與回復程序。

5｜TCP 路徑與接收端限速

遺失或延遲可造成重傳及隊首等待；接收窗變小或為零代表接收端暫時限速，可能是應用讀得太慢，別直接歸因為交換器。

佐證：對照既有 RTT、retransmit、advertised window、接收緩衝及應用工作量。TCP 重傳與再次發送業務命令是兩回事；寫入回覆遺失不可盲目重送。

6｜PLC scan、閘道與採樣

PLC 排程、點值掃描與上位輪詢是不同週期。採得更快可能只得到同一版本的舊值，或把工作堆在同一個 PLC／閘道佇列。

佐證：比對 source timestamp／序號、PLC scan 時間、enqueue→send 間隔、每條 bus 的 in-flight。改善驗收要看點位年齡，而不只 TCP RTT。

7｜MQTT Broker／訂閱端

Broker fan-out、會話待送佇列、QoS 確認、訂閱端處理能力或中斷後恢復都可形成積壓；QoS 不等於低延遲保證。

佐證：看 publish、forward、ack 的階段時間，依實作查 in-flight、queued、dropped。MQTT 5 的 Receive Maximum 管 QoS 1/2 未確認發佈，不是 QoS 0 速率限制。

8｜應用程式、連線池與資料庫

收到資料不表示已提交。慢 SQL、串行寫檔、長交易或連線池等候會把 I/O 堵在最後一哩，也可能反壓 Broker／socket。

佐證：由接收、enqueue、worker start 到 commit 分段；查工作佇列、鎖等待與儲存延遲。不要為追求低延遲跳過持久化或吞掉失敗。

合成案例 A｜有尖峰、低平均

8 個輸入同時各 40 Mb/s，重疊 1 ms，出口 100 Mb/s。極簡模型新增待送量為 (320 − 100) Mb/s × 0.001 s ÷ 8 = 27,500 bytes。若每秒只出現一次，此 burst 的平均輸入只有約 0.32 Mb/s；實際緩衝、封包邊界、標記和其他流量另計，不能拿這個值當硬體規格。

合成案例 B｜連線低 RTT，資料仍舊

送出前等 35 ms、網路／閘道往返 15 ms、接收後 CPU 或資料庫提交再等 250 ms；同一程序單調時計得到 300 ms 端到端。若來源掃描每 500 ms，資料的 age 還要獨立由來源時間確認，不能斷言 age 就是 300 ms。

唯讀基準：用已核准的介面匯出取 ifHCInOctets、ifHCOutOctets 與實際協商 bps。單方向利用率 = 8 × Δoctets ÷ (Δseconds × link_bps)；先排除重啟／counter discontinuity、週期不一致與 wrap。octets 的統計口徑不一定含全部線路開銷，不能以其精確反推 wire occupancy。以既有記錄量 t₁−t₀、t₂−t₁、t₄−t₃；p95/p99 報樣本數、窗長與所用算法，逾時、拒絕／重送另列，不把成功樣本的分位數當全體。

原始資料：IF‑MIB／RFC 2863 · TCP／RFC 9293 · Modbus Serial Line V1.02 · OASIS MQTT v5.0 · OPC UA Sampling Interval。

04 / PASSIVE EVIDENCE

用差值與分段時間，比 CPU 體感更可靠

  • 埠速／差值：同埠同方向記錄前後 ifHCInOctets／ifHCOutOctets、間隔、協商速度；bps = Δoctets × 8 ÷ elapsed_seconds，比例再除以單方向線速。對累計器重置與回捲檢查 ifCounterDiscontinuityTime、設備 uptime 或採集世代；若無確定資料，不用負差硬展成巨量。以 SNMP 指標認定整體精確線速使用率也要考慮廠牌對 frame overhead 的計數口徑。
  • 錯誤 ≠ 丟棄：ifInErrors/ifOutErrors 是錯誤類；ifInDiscards/ifOutDiscards 可包含無錯但被丟棄的封包，並非直接證明出口佇列滿。用網管提供的 per-queue drop 或 FCS/CRC 加強判讀。
  • 應用分段：記 t_enqueue、t_dispatch、t_reply、t_commit，同一主機用單調時鐘求差；跨主機只用已同步時間分析，否則用帶相關 ID 的本機各段耗時。reply-dispatch 包含對端和路徑等候，不是純網路延遲。來源點位時間另存作 freshness，定值點應有心跳或品質判斷。
  • 尾延遲：p95/p99 要附樣本數、時窗、篩選條件和算法。下方用 nearest-rank（排序後取第 ceil(p×n) 筆），樣本少時 p99 接近最大值、容易受單筆影響；成功樣本的 p99 不包含逾時，另報丟棄／失敗率，不能將二者用一條線替代。

規範：IETF RFC 2863：介面計數器 · IETF RFC 9293：TCP／接收窗 · IETF RFC 6298：重傳定時 · Modbus.org Serial Line V1.02：單筆交易 · OPC Foundation：Sampling Interval。

05 / OFFLINE SIMULATION

一個慢站，就能拖長其他 19 站的 p95

模型每 500 ms 有一輪 20 站、輪內每 5 ms 提交一筆；一個 FIFO 單埠、最多 24 筆未完成（含執行中），正常站服務費時 20 ms，故障站服務占住 300 ms 一次，第三種情境原地再等一次 300 ms。樣本在相同虛擬時刻提交，共 12 輪、240 筆；模擬最後允許已接受項完成，不是固定觀察時間的吞吐量實測。

離線估算可先看服務預算：全健康一輪 20 × 20 = 400 ms 空間有限；一站慢 19 × 20 + 300 = 680 ms 已超過 500 ms。當限流使少部分 poll 進不了佇列，p95 仍只代表成功樣本；一定要並列 rejected 和 timeout。

"""Offline discrete-event lab. No network, device, background timing or I/O."""
import argparse
from collections import deque
from dataclasses import dataclass
import json
import math
import unittest


@dataclass(frozen=True)
class Poll:
    arrival_ms: int
    station: int


def nearest_rank(values, fraction):
    """Return the nearest-rank percentile (no interpolation)."""
    if not values or not 0 < fraction <= 1:
        raise ValueError("need samples and a quantile in (0, 1]")
    ordered = sorted(values)
    return ordered[math.ceil(fraction * len(ordered)) - 1]


def simulate(slow=False, retry=0, limit=24, rounds=12):
    """One FIFO RTU port; limit includes the in-flight request."""
    if retry not in (0, 1) or limit < 1 or rounds < 1:
        raise ValueError("invalid offline scenario")
    outstanding_finishes = deque()
    next_free = 0
    traces = []
    dropped = 0
    for cycle in range(rounds):
        for station in range(1, 21):
            # Identical offered timestamps in every scenario. Integer ms is model time.
            poll = Poll(cycle * 500 + (station - 1) * 5, station)
            while outstanding_finishes and outstanding_finishes[0] <= poll.arrival_ms:
                outstanding_finishes.popleft()
            if len(outstanding_finishes) >= limit:
                dropped += 1
                continue
            start = max(next_free, poll.arrival_ms)
            timed_out = slow and poll.station == 1
            service = 300 * (1 + retry) if timed_out else 20
            finish = start + service
            next_free = finish
            outstanding_finishes.append(finish)
            traces.append({
                "station": poll.station,
                "arrive_ms": poll.arrival_ms,
                "queue_ms": start - poll.arrival_ms,
                "service_ms": service,
                "delay_ms": finish - poll.arrival_ms,
                "timeout": timed_out,
            })
    successful = [row for row in traces if not row["timeout"]]
    latency = [row["delay_ms"] for row in successful]
    return {
        "offered": 20 * rounds,
        "completed_ok": len(successful),
        "timeout": sum(row["timeout"] for row in traces),
        "queue_rejected": dropped,
        "p95_success_ms": nearest_rank(latency, .95) if latency else None,
        "p99_success_ms": nearest_rank(latency, .99) if latency else None,
        "max_healthy_queue_ms": max((x["queue_ms"] for x in successful), default=None),
    }


class LabTests(unittest.TestCase):
    def test_nearest_rank(self):
        self.assertEqual(nearest_rank([30, 10, 20], .95), 30)
        self.assertEqual(nearest_rank([30, 10, 20], .50), 20)
        with self.assertRaises(ValueError):
            nearest_rank([], .99)

    def test_station_failure_hurts_other_stations(self):
        baseline = simulate()
        slow = simulate(slow=True)
        self.assertEqual(baseline["completed_ok"], 240)
        self.assertEqual(baseline["queue_rejected"], 0)
        self.assertEqual(baseline["timeout"], 0)
        self.assertGreater(slow["p95_success_ms"], baseline["p95_success_ms"])
        self.assertGreater(slow["timeout"], 0)

    def test_more_service_cost(self):
        self.assertGreater(simulate(slow=True, retry=1)["max_healthy_queue_ms"],
                           simulate(slow=True)["max_healthy_queue_ms"])

    def test_balanced_accounting(self):
        for slow, retry in [(False, 0), (True, 0), (True, 1)]:
            x = simulate(slow=slow, retry=retry)
            self.assertEqual(x["offered"], x["completed_ok"] + x["timeout"] + x["queue_rejected"])

    def test_bound(self):
        self.assertGreater(simulate(slow=True, limit=1)["queue_rejected"], 0)

延伸學習：實作、現場案例與自我檢查

本頁以情境找出塞車位置。本節針對最常見的 RS-485 Modbus RTU 匯流排，算出一次交易的時間組成，並示範多個上位系統共用閘道器與從站離線時，輪詢週期會怎麼惡化。

可實跑範例：Modbus RTU 輪詢週期與匯流排使用率

字元時間以 11 bits 計（起始、8 資料、同位、停止）。3.5 字元靜默在 19200 bps 以上依規範固定 1.75 ms。從站回應時間 15 ms 與離線逾時 1 s 是假設值，請以現場量測取代。

下載範例 example.py

"""RS-485 Modbus RTU 輪詢週期估算：字元時間、3.5 字元靜默、從站回應時間，找出排隊在哪裡（標準函式庫）。"""

BITS_PER_CHAR = 11          # 1 起始 + 8 資料 + 1 同位 + 1 停止（或 2 停止、無同位）


def char_time_ms(baud):
    return BITS_PER_CHAR / baud * 1000


def silent_ms(baud):
    """3.5 字元靜默；Modbus 規範在 19200 bps 以上建議固定 1.75 ms。"""
    return 1.75 if baud > 19200 else 3.5 * char_time_ms(baud)


def transaction_ms(baud, regs, slave_resp_ms):
    req_bytes = 8                                  # 位址1＋功能碼1＋起始2＋數量2＋CRC2
    resp_bytes = 5 + 2 * regs                      # 位址1＋功能碼1＋位元組數1＋資料＋CRC2
    wire = (req_bytes + resp_bytes) * char_time_ms(baud)
    return wire + 2 * silent_ms(baud) + slave_resp_ms, wire


if __name__ == "__main__":
    slaves, regs, resp = 30, 20, 15.0
    for baud in (9600, 19200, 38400, 115200):
        tx, wire = transaction_ms(baud, regs, resp)
        cycle = slaves * tx / 1000
        print(f"{baud:>6} bps：單次交易 {tx:6.1f} ms（線上 {wire:5.1f} ms），{slaves} 台一輪 {cycle:5.2f} s")
    print()
    tx, _ = transaction_ms(19200, regs, resp)
    for clients in (1, 2, 4):
        print(f"{clients} 個上位系統共用同一閘道、各自每 2 s 輪詢一次：匯流排使用率 "
              f"{clients * slaves * tx / 2000:.0%}{'  ← 超過 100%，請求開始排隊' if clients * slaves * tx > 2000 else ''}")
    tx_timeout, _ = transaction_ms(19200, regs, 1000)
    print(f"若有 1 台從站離線、逾時設 1 s：每輪多 {tx_timeout - tx:.0f} ms，"
          f"一輪變成 {(slaves - 1) * tx / 1000 + tx_timeout / 1000:.2f} s")

工程現場案例：新增能源平台後，原本 BAS 的告警延遲到好幾秒

某大樓的 30 台電表接在一條 19200 bps 的 RS-485 上，經 Modbus TCP 閘道器給 BAS 每 2 秒輪詢一次，匯流排使用率約 74%。業主再接上能源管理平台，同樣每 2 秒輪詢，使用率變成 148%：閘道器把兩邊的請求排隊，BAS 的資料延遲越積越長。

範例也顯示：一台電表離線、逾時設 1 秒時，一輪輪詢從 1.48 秒拉長到 2.47 秒，已超過 2 秒的更新目標。解法包括由一個系統輪詢後轉發給另一個（不要兩邊同時直讀）、提高鮑率、合併讀取範圍，以及縮短逾時並把離線從站暫時移出輪詢。

  1. 量測每台從站的實際回應時間與逾時次數。
  2. 計算目前的匯流排使用率，新增任何上位系統前先試算。
  3. 多個系統需要同一份資料時，只讓一個系統輪詢並轉發。
  4. 離線從站採退避重試，不要每輪都等滿逾時時間。

練習題與自我檢查

  1. 9600 bps 下讀 20 個暫存器，線上傳輸時間為什麼是 60.7 ms？

    看解答

    請求 8 bytes、回應 5 + 40 = 45 bytes，共 53 字元，每字元 11 ÷ 9600 秒 ≈ 1.146 ms，53 × 1.146 ≈ 60.7 ms。

  2. 為什麼鮑率從 38400 提高到 115200，單次交易只從 33.7 ms 降到 23.6 ms？

    看解答

    線上時間從 15.2 ms 降到 5.1 ms，但從站回應時間 15 ms 不變，成了主要瓶頸。和乙太網路速度頁的結論相同：先找出時間花在哪裡。

  3. 若改成每台電表一次讀 60 個暫存器（合併 3 次讀取），19200 bps 一輪的時間會怎麼變？

    看解答

    原本 3 次交易各約 49.4 ms，共約 148 ms；合併後只付一次從站回應與兩次靜默時間，transaction_ms(19200, 60, 15) 約 95.2 ms，省下約三分之一。合併讀取通常是最有效的改善。

  4. 逾時應該設多長？

    看解答

    略大於從站最大正常回應時間加上傳輸時間，例如量測的 P99 回應時間再加一些餘裕，而不是隨便設 1 秒。逾時太長會拖慢整輪，太短則會誤判離線。
